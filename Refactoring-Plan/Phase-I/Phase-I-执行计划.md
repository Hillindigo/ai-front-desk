# Phase I 执行计划：安全、隐私、生产运行与质量评测

> 文档状态：任务计划，待 I0 基线与决策锁定  
> 阶段目标：在 Phase H 已完成的 Web 买家—商家闭环上，补齐安全与隐私底线、可观测性、质量评测、恢复能力和可重复运行证据，使项目从“功能闭环可演示”进入“可持续运行、可度量、可恢复”的工程状态。  
> 当前分支：`dev`  
> 适用范围：生产配置安全、PII 治理、运行观测、模型与 RAG 评测、并发恢复、备份清理、部署与运维验收  
> 不包含：重新实现 Phase H Web 主路径、第三方渠道、支付退款、复杂多租户、商业级高可用或未经真实需求证明的基础设施

---

## 0. 阶段定位与完成目标

Phase I 不新增一套买家端或商家端业务流程，也不以“接更多模型、做更多页面”为目标。它承接 Phase G/H 已有的身份、门店范围、事件、审计和业务结果，在这些事实之上回答五个问题：

1. 敏感数据是否按明确边界采集、展示、记录、导出和删除；
2. 系统异常、模型失败、延迟和成本是否可以被发现、定位和统计；
3. 意图识别、字段提取、知识回答和摘要质量是否有可重复评测；
4. 并发、重启、备份恢复和重复请求是否不会破坏业务事实；
5. 项目能否在一个明确支持的运行拓扑中按文档部署、验收、回滚和恢复。

阶段完成后必须满足：

- 生产配置不存在已知默认密钥、调试泄漏或越权降级路径；
- 日志、错误响应、审计和管理页面不暴露不必要的密码、令牌或完整 PII；
- 客户数据支持受权限保护的导出、删除/匿名化及可验证的数据保留策略；
- 关键请求、Agent 轮次、知识检索和预约动作具有可关联的指标与失败记录；
- Fake 模式评测可离线重复运行，真实模型评测与人工结论单独留证，不混用证据；
- 并发、幂等、重启、索引刷新、备份和恢复有自动化或可重复验收证据；
- 所有未完成的生产能力继续标记为限制或后续任务，不因本地测试通过而冒充线上可用。

### 0.1 执行与 Git 约束

- 所有 Phase I 代码、测试和文档在 `dev` 分支完成；每个任务开始前检查分支和工作区。
- 提交格式固定为 `Phase I(类型)-标题`，标题不超过 15 个字；一个提交围绕一个独立大块事项，Bug 修复单独提交。
- 未经用户明确要求，不合并到 `main`、不推送远程、不宣称已部署。
- 保留已有未提交改动；只提交当前任务白名单文件，不执行覆盖、清理或重置。
- 涉及数据库删除、匿名化、备份清理和密钥轮换时，必须先提供 dry-run、测试数据和恢复路径，不直接对未知数据执行破坏性操作。

## 1. Phase H 交接审查与稳定边界

### 1.1 直接承接、不得重做的能力

Phase I 必须直接使用以下现有事实来源：

- 规范会话与 SSE：`/api/v1/conversations`、`/turns`、`protocol_version=v1`；
- 预约领域服务及状态机、事务冲突校验和 `idempotency_key`；
- 轮次去重 `client_request_id` 与预约幂等职责边界；
- `ConversationControl` 的 `ai_active / human_active / awaiting_human` 三态及接管审计；
- 商家服务端会话、CSRF、RBAC、门店 membership 和 active store scope；
- 按门店持有的知识服务、发布版本、来源证据及无依据拒答；
- Phase H 已完成的买家咨询—预约—商家接管 Web 主路径与契约测试。

Phase I 不得通过复制路由、绕过应用/领域服务、修改公开契约语义或在页面中增加第二事实来源来实现安全、监控或评测。

## 2. 范围与明确不纳入

### 2.1 纳入范围

1. 生产配置、密钥、Cookie、代理、CORS、CSRF、安全响应头和错误泄漏加固；
2. 买家与商家当前身份边界的安全审查、会话撤销、权限与门店隔离回归；
3. PII 分类、日志脱敏、最小展示、客户数据导出、删除/匿名化、数据保留；
4. 审计完整性、请求关联、Agent 运行、模型调用、知识检索、延迟、失败和成本观测；
5. 单进程与受支持多进程拓扑下的知识版本一致性和健康检查；
6. 意图、字段提取、RAG、摘要和业务结果的离线/真实模型/人工评测；
7. 并发、幂等、重启、故障恢复、数据库备份、恢复和清理演练；
8. 可重复启动、配置检查、迁移、健康检查、验收、回滚和运维文档。

### 2.2 明确不做

- 重写 Phase H 买家或商家 Web 主路径；
- 小程序、微信、美团、淘宝等渠道及通用 `ChannelAdapter`；
- OAuth、短信、MFA、实名/KYC 等完整消费者身份平台；
- 多门店集团管理、SaaS 租户计费和复杂角色矩阵；
- 支付、退款、发票、库存、会员、营销和外部通知；
- 微服务拆分、Kubernetes、跨区域容灾和 7×24 SLA；
- 自动替代人工处理投诉、赔付或健康安全决策；
- 仅为“以后可能用到”而引入消息队列、数据湖或复杂监控集群。

## 3. 任务拆分

### I0：基线、威胁模型与验收契约

**目标**：在写功能前锁定当前状态、支持拓扑、数据边界、质量指标与破坏性操作规则。

任务：

- 审查 Phase H 收尾文档、阶段提交、测试证据、未验证事项和当前工作区归属；
- 运行当前全量测试，记录通过、跳过、失败、警告、耗时和 Fake 网络边界；
- 建立资产与信任边界图：买家浏览器、商家浏览器、FastAPI、SQLite、知识索引、LLM/Embedding 提供商、备份文件；
- 建立威胁清单：越权、跨门店读取、CSRF、会话固定、密钥泄漏、Prompt/日志泄漏、重复写入、备份泄漏、旧索引回答；
- 建立 PII 数据字典与数据流表，标明采集目的、存储位置、展示范围、日志规则、保留期限和删除动作；
- 锁定 Phase I 支持的运行拓扑：默认单实例；若承诺多进程，必须定义知识版本传播机制和验收方式；
- 定义 SLI/SLO 与评测门槛初稿：请求成功率、P95 延迟、模型失败率、转人工率、知识拒答率、单轮 token/估算成本；
- 建立数据库迁移、数据删除、备份清理的 dry-run、确认、审计和回滚规则。

交付物：

- `Phase-I-I0-基线与决策记录.md`；
- 威胁模型与控制矩阵；
- PII 数据字典/数据流表；
- 运行拓扑、指标字典、评测矩阵和验收矩阵；
- 文件白名单、迁移/破坏性操作规则和回滚点。

验收：P0 风险均有处理归属和测试方法；没有未决的数据删除语义、支持拓扑或质量口径进入 I1。

### I1：生产配置与安全加固

**目标**：使生产模式对错误配置采取“安全失败”，并验证现有身份、权限和 Web 安全边界。

任务：

- 将开发默认值与生产配置分离；生产模式缺少会话密钥、允许来源或必要模型配置时拒绝启动；
- 禁止默认管理员密码、硬编码令牌、调试异常页和敏感配置回显；提供密钥轮换与会话失效说明；
- 固化 Cookie 的 `HttpOnly`、`SameSite`、生产 `Secure`、生命周期和撤销语义；验证登录/退出/会话过期；
- 审计反向代理与 HTTPS 边界，只信任明确代理来源，防止伪造 scheme/host/client IP；
- 收敛 CORS、Trusted Host、请求体大小、上传类型/大小、超时和基础速率限制；
- 增加 CSP、`X-Content-Type-Options`、Referrer Policy、frame 限制等安全响应头；
- 横向回归商家 RBAC、active store、客户会话归属、CSRF 及跨门店对象访问；
- 统一公开错误响应，防止堆栈、数据库路径、模型密钥、内部 Prompt 或隐藏推理泄漏；
- 为认证失败、越权、跨门店、敏感管理动作和配置异常记录脱敏安全事件。
- 明确生产"启动-就绪"语义（D12）：配置校验失败拒启；DB/迁移失败拒启或 ready 失败；知识索引不可用则进程存活但 ready 失败、不静默用旧版；LLM 暂不可用则降级/转人工不一刀切拒启；`/health/live`（进程）与 `/health/ready`（可承接）分离。

交付物：安全配置校验器/启动门禁、安全中间件或最小配置调整、安全部署模板、`tests/test_phase_i_security.py`。

验收：默认/弱生产配置不能启动；未登录、越权、跨门店和 CSRF 请求稳定拒绝；安全头、错误脱敏和会话撤销有自动化测试。

### I2：PII 治理、导出、删除与保留

**目标**：让客户数据的读取、导出、删除和留存具备明确、可审计、可恢复的规则。

任务：

- 按 I0 数据字典标注直接标识符、准标识符、业务事实、审计事实和非敏感运营指标；
- 对日志、异常、审计详情和管理页面实施字段级最小化与脱敏；禁止记录密码、会话令牌和完整认证头；
- 实现受 RBAC、门店 scope 和 CSRF 保护的客户数据导出，导出包含范围、生成者、时间、格式和审计事件；
- 设计并实现客户删除/匿名化应用服务，明确会话、消息、摘要、偏好、墓碑、预约、回访、审计和知识索引的逐实体策略；
- 已完成预约等法定/业务审计事实不得无定义硬删：保留时必须去标识化并说明原因；
- 删除流程提供预览/dry-run、幂等键、事务边界、失败恢复和结果清单；禁止只从页面隐藏数据；
- 定义在线数据、日志、临时导出、上传文件和备份的保留期限与清理任务；清理任务默认 dry-run，并记录审计；
- 验证删除后 ContextBuilder、搜索、客户后台、会话恢复和模型输入不会再次注入被删除信息。
- 按 D9 收敛为**商家侧客户治理**：导出/删除/匿名化仅由已登录商家发起（RBAC/store scope/CSRF），客户以门店内稳定 `customer_user_id` 标识；买家端维持演示身份边界，不提供买家自助数据入口。
- 按 D14 产出逐表/逐字段 PII 数据字典矩阵，覆盖全部现有表（含 `Message.metadata_json`、`AppointmentEvent.payload_json`、`AuditEvent.summary_json`、`ConversationControlEvent.content`、`user_behaviors`、旧 `user_preferences`、`user_recommendations`、评测/运行失败样本），再据矩阵定删除/匿名化动作。
- 按 D11 落实导出/备份文件级安全：专用目录+服务端文件名+最小权限、短时一次性下载令牌、明确导出 schema（禁整库 dump）、生产备份静态加密+密钥分离+校验和+版本清单、过期清理；测试覆盖路径穿越/跨门店/过期访问。
- 按 D10 落实删除↔备份恢复闭环：删除动作写删除登记/抑制记录；从旧备份恢复后先重放删除/匿名化→重建摘要/偏好/索引→再对外服务；新增"从删除前备份恢复后 PII 不可查询/不可注入"验收场景。

交付物：PII 策略文档、导出/删除应用服务与管理 API、保留/清理命令、`tests/test_phase_i_privacy.py`。

验收：跨门店不能导出或删除；重复删除不会产生不一致；删除后所有规定入口不可恢复被删除 PII；保留的业务/审计事实已匿名化且理由可追踪。

### I3：运行观测、审计与成本延迟指标

**目标**：用结构化、低敏感度的数据回答“哪次请求发生了什么、为什么失败、花了多久和多少模型资源”。

任务：

- 统一 `request_id / conversation_id / run_id / client_request_id / appointment_id` 的关联规则，禁止使用 PII 作为指标标签；
- 按 D13 落定关联 ID 信任边界：`request_id`（服务端生成，每请求唯一）、`client_request_id`（客户端幂等键，长度/字符校验，不替代服务端 ID）、`run_id`（服务端 Agent 实例，replay 引 `original_run_id`）、`idempotency_key`（仅业务命令用）；外部 `X-Request-ID` 经校验作 `external_request_id`，不替代 `request_id`。
- 建立 Agent 运行记录或等价结构：工作流、模型/提供商、Prompt/语料版本、开始/结束时间、状态、错误类别、token 用量和估算成本；
- 指标/SLI 定义测量条件：样本窗口、冷/热启动、Fake/真实模型、并发与数据规模、SSE 起止点（首事件/完整轮次）、小样本不计算 P95 或标记低置信度；成本记录含计价版本与币种。
- 为会话 turns、知识检索、模型调用、预约命令、人工接管和后台任务记录阶段耗时与稳定失败类别；
- 区分用户错误、领域冲突、模型失败、检索不足、依赖失败和系统异常，避免仅记录自由文本错误；
- 增加健康/就绪检查：数据库、迁移版本、知识索引版本、后台任务状态；就绪失败不得返回伪健康；
- 提供最小门店范围运营/质量指标查询或离线报表，验证权限、标签基数和数据脱敏；
- 定义本地阈值与告警规则文档：失败率、P95 延迟、旧索引、连续模型失败、备份过期；不因没有外部告警平台而伪造通知成功；
- 检查审计事件的操作者、门店、对象、动作、结果、关联 ID 和时间完整性。
- 观测写入不得静默丢失：指标/运行记录写入失败要有可观测 drop/error 计数，查询结果区分"无事件发生"与"观测记录丢失"；关键业务审计尽量与业务事实同事务。

交付物：指标字典、运行记录/埋点、健康检查、管理查询或报告、`tests/test_phase_i_observability.py`。

验收：一次跨角色验收可以从请求关联到 Agent 轮次、知识证据、预约结果和审计事件；指标不泄漏 Prompt 全文、令牌或完整 PII。

### I4：知识索引多进程一致性与安全降级

**目标**：消除“数据库已发布新知识，但其他进程继续静默使用旧索引”的未定义状态。

> 按 I0 D1/D2，默认支持拓扑为**单实例**。本任务按下述分支持：
> **I4-A（单实例支持边界，默认必做）**：启动门禁强制 worker=1、`/health` 暴露本地索引与数据库知识版本、文档只承诺单实例一致性。
> **I4-B（有限多进程 / 版本同步，仅在明确选择多进程时做）**：实现持久 `knowledge_version` 版本检测、本进程刷新/原子交换、刷新失败保留旧快照并标记 stale/degraded、高风险知识拒绝确定性回答转人工，及两进程/两容器视角的发布-检测-刷新-查询与并发/失败注入测试。

任务：

- 在 I0 明确默认支持单实例还是有限多进程；未通过本任务前，部署文档不得宣称多进程安全；
- 使用持久化 `knowledge_version` 作为事实源，定义进程启动、请求前/周期检查、发布后和刷新失败时的行为；
- 若支持多进程，实现轻量版本检测与本进程索引重建/原子交换，不引入当前规模不需要的分布式基础设施；
- 发布仍保持候选索引成功后再提交/交换，刷新失败保留最后可用快照并标记 `stale/degraded`；
- 对价格、政策等高风险知识，索引明确陈旧且无法刷新时拒绝确定性回答并转人工，不能静默用旧内容；
- 健康检查暴露数据库知识版本、本地索引版本、最后刷新时间和失败状态；
- 若 I0 选择单实例（I4-A）：完成启动门禁、版本 health、部署限制说明即可，不实现版本同步机制；两容器/两进程测试不作门槛。
- 若 I0 选择有限多进程（I4-B）：增加两个应用容器/进程视角的发布—检测—刷新—查询测试，以及并发发布和失败注入测试。

交付物：知识版本同步机制（I4-B）/单实例门禁与 health（I4-A）、陈旧状态与健康信息、部署限制说明、`tests/test_phase_i_knowledge_consistency.py`。

验收：I4-A：单实例下本地索引与持久版本一致、health 暴露版本、文档不宣称多进程安全；I4-B：新版本在约定时限内被所有受支持进程采用、失败可观测、旧快照不损坏、高风险旧知识不被当作当前事实。

### I5：模型、RAG、摘要与工作流质量评测

**目标**：建立可重复、可版本化、可解释的质量门禁，而不是凭演示观感判断 Agent 是否变好。

任务：

- 盘点并版本化四类评测集：意图分类、预约字段提取、知识检索/回答、会话摘要与偏好；
- 每条样本记录输入、期望结构化结果、允许变体、门店/语料版本、敏感性和人工判定规则；评测数据不得混入生产客户原文；
- 为确定性部分建立精确指标：意图准确率/混淆矩阵、字段 precision/recall、检索 Recall@K、无依据拒答率、摘要关键事实保留率；
- 对生成式回答建立人工量表：事实依据、完整性、可执行性、风险边界、是否泄漏内部信息；
- 记录模型、提供商、参数、Prompt 版本、知识版本、代码提交和运行时间，支持基线对比；
- Fake 模式只验证契约、控制流和确定性指标；真实模型评测作为独立可选运行，不纳入默认离线测试；
- 建立回归门槛：P0 安全/业务样本零容忍，统计指标不得低于已批准基线；阈值变化必须有原因和评审记录；
- 增加失败样本归档与复现入口，禁止只保留平均分掩盖高风险失败。

交付物：`evaluation/` 下的版本化数据、运行器、基线结果、人工评测模板和 `tests/test_phase_i_evaluation.py`。

验收：同一版本配置可重复生成结果；失败可定位到样本和版本；Fake、真实模型、人工结果明确分栏，未运行真实评测时标记为待验证。

### I6：并发、故障恢复、备份与数据清理演练

**目标**：证明关键业务事实面对并发、重试、进程重启和数据恢复时仍保持一致。

任务：

- 增加并发场景：同一会话重复轮次、同一时段竞争预约、接管与 AI 同时请求、重复人工回复、并发知识发布；
- 验证 `client_request_id`、预约 `idempotency_key`、控制状态和数据库事务的职责，没有重复消息、预约或状态跃迁；
- 注入模型超时/空流、Embedding 失败、数据库锁竞争、发布失败、进程中断和 SSE 断线；
- 验证重启后会话、摘要、工作流、预约、人工接管、知识版本和后台任务状态；
- 建立 SQLite 一致性备份流程，备份包含数据库、必要上传/知识源和版本清单，不复制正在写入的数据库文件冒充有效备份；
- 实现备份校验、保留和清理 dry-run；备份文件按敏感数据处理，不写入 Git；
- 在隔离临时目录执行至少一次真实恢复演练：初始化→写入验收数据→备份→破坏/替换→恢复→运行迁移和验收；
- 记录 RPO/RTO 的当前实测值和单实例限制，不作商业级承诺。

交付物：并发/故障测试、备份恢复脚本、清理任务、恢复演练记录、`tests/test_phase_i_reliability.py`。

验收：故障与恢复后关键实体数量、状态、关联 ID 和知识版本一致；重复请求不产生重复业务结果；备份可实际恢复而非只证明文件存在。

### I7：部署验收、运维手册与阶段收尾

## 6. 风险与回滚策略

| 风险 | 影响 | 缓解与回滚 |
|---|---|---|
| 安全中间件破坏现有 Web/SSE 契约 | 高 | I0 锁定契约；先加测试再启用；按独立提交回退，不复制新入口 |
| 删除/匿名化遗漏摘要、偏好或备份 | 高 | PII 数据流表、dry-run、逐实体结果清单、隔离测试库和恢复演练 |
| 日志/指标为排障记录过多敏感内容 | 高 | 默认字段白名单、哈希/截断、禁止 Prompt 全文和高基数 PII 标签 |
| 指标写入影响主业务事务 | 中 | 观测失败不得回滚已完成业务；采用独立失败边界并记录丢失状态 |
| 多进程刷新导致索引不一致或抖动 | 高 | 持久版本、原子交换、最后可用快照、退避和 stale/degraded 状态 |
| 评测集泄漏生产客户数据 | 高 | 只用合成/授权脱敏样本；数据源审查；评测资产纳入版本控制检查 |
| 追求基础设施“完整”导致阶段失控 | 中 | 以单实例/有限多进程和本项目 SLO 为边界，不提前引入微服务/集群 |
| 备份存在但不可恢复 | 高 | 隔离目录真实恢复、完整性校验、版本清单和验收查询，不以文件存在验收 |
| 导出/备份文件加密与下载泄漏 | 高 | 专用目录、服务端文件名、短时一次性下载令牌、静态加密+密钥分离、校验和、过期清理、脱敏审计（D11） |
| 从旧备份恢复后已删除 PII 复活 | 高 | 删除登记/抑制记录、恢复后先重放删除/匿名化再重建索引再验收（D10） |
| 真实模型结果不稳定 | 中 | 固定版本/参数，独立运行，保存样本级结果；不把网络评测放入默认单元测试 |

回滚原则：

1. 数据迁移必须前向兼容、幂等，并在隔离副本验证；不使用无备份的破坏性迁移；
2. 安全与观测功能按独立提交启用，出现契约回归时回退功能开关或独立提交；
3. 删除和清理默认 dry-run，只有明确授权和可恢复证据后才执行真实动作；
4. 知识刷新失败保留最后可用快照，同时标记陈旧并对高风险答案降级；
5. 观测、评测和报表失败不得伪造业务成功，也不得无必要阻塞预约事实写入；
6. 不通过 `git reset`、清理命令或覆盖文件处理用户已有改动。
