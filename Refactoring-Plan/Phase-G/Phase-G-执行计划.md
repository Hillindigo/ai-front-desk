# Phase G 执行计划：商家运营后台、权限与门店隔离

> 计划版本：2026-08-18

> 所属项目：`AIFrontDesk`  
> 前置阶段：Phase F——知识库治理与回答可信度

## 0. 阶段定位与完成目标

Phase G 的目标不是继续增加一个展示页面，而是把现有的会话、预约、知识库、偏好和服务人员能力收敛为一个商家可操作、可授权、可追溯的运营后台：

```text
商家账号登录
    → 进入有权限的门店
    → 查看会话、客户上下文和预约事实
    → 管理知识、服务、营业规则和排班
    → 接管咨询、确认/取消/改约预约
    → 创建回访任务并查看运营指标
    → 所有关键动作写入审计记录
```

完成后，商家不需要直接操作数据库即可完成一条最小日常运营闭环：

1. 运营人员可以登录并只能访问自己有权限的门店；
2. 商家可以查看会话详情、客户上下文、预约状态和回答依据；
3. 商家可以接管咨询、标记异常/投诉、添加待跟进事项；
4. 商家可以维护服务项目、价格、营业时间、预约政策、地址、联系方式、服务人员和排班；
5. 商家可以查询并确认、取消、改约预约，冲突和非法状态由预约领域服务拒绝；
6. 商家可以查看客户偏好和历史预约，并创建回访任务；
7. 知识发布、预约操作、人工接管、权限变更和失败操作可以按操作者、门店、资源和时间追溯；
8. 管理后台的读写链路有自动化测试和实际 HTTP 验收，不能只以模板渲染或数据库写入作为完成证据。

本阶段只建设“可运营的最小后台”。Phase I 仍负责更深的生产安全、PII 脱敏、成本/延迟监控、备份清理、真实模型质量和长期评测；Phase H 负责渠道接入和平台适配。Phase G 不得因为页面可见就宣称已经完成生产级平台化。

## 2. Phase G 范围与不纳入清单

### 2.1 纳入范围

1. 最小可用的商家账号、登录会话和 RBAC；
2. 门店、成员、资源和数据的服务端隔离；
3. 商家运营后台的会话工作台、门店配置、预约管理和客户运营；
4. 发布、预约、接管、配置变更和权限变更的审计；
5. 引用使用、无依据拒答、刷新失败和后台操作的基础运营指标；
6. 与上述能力对应的 API、前端页面、迁移、故障注入、HTTP 和回归测试。

### 2.2 明确不做的事情

- 不接入美团、淘宝、微信等外部渠道；
- 不做复杂文档解析、平台知识同步或外部知识源导入；
- 不把本阶段变成完整 CRM、营销自动化或自动复购决策系统；
- 不重写 Phase D 的编排、SSE v1、预约状态机或 Phase E 的摘要/偏好删除语义；
- 不把客户账号和商家运营账号混为同一身份模型；
- 不以 `localStorage`、隐藏字段、URL 中的 `store_id` 或请求体 `user_id` 作为授权依据；
- 不将 Fake LLM/Embedding 的结果描述为真实模型质量；
- 不把单进程索引锁描述为已经完成多进程生产一致性；
- 不在没有数据迁移、权限测试和回滚方案时直接删除旧 API 或旧表。

## 3. 必须在 G0 锁定的设计决策

以下决策必须在写代码前形成决策记录。若选择不同于推荐方案，必须说明原因、迁移影响和回滚方式。

### 3.1 商家身份与会话

推荐最小方案：

- 独立的商家账号实体，不复用客户 `user_id`；
- 密码只保存强哈希，不保存明文；
- 使用服务端可撤销的会话或等价的短期访问凭证；浏览器后台使用 HttpOnly、SameSite Cookie，并为写操作提供 CSRF 防护；
- `IdentityResolver` 增加真实商家身份实现，保留 `DemoIdentityResolver` 仅供显式测试夹具使用；
- 所有后台请求从服务端会话解析 `actor_id`、角色和当前门店，不信任客户端提交的权限字段。

### 3.2 角色和权限

推荐最小角色：

| 角色 | 会话查看 | 知识发布 | 门店配置 | 预约写操作 | 客户偏好 | 成员/审计 |
|---|---:|---:|---:|---:|---:|---:|
| `owner` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `manager` | ✓ | ✓ | ✓ | ✓ | ✓ | 读 |
| `operator` | ✓ | 按授权 | 读 | ✓ | 读/回访 | 无/有限 |
| `viewer` | 读 | 无 | 读 | 读 | 读 | 无 |

角色名称和权限矩阵由 G0 定稿。接口必须执行权限检查，前端隐藏按钮只能改善体验，不能作为安全边界。

### 3.3 门店边界和历史数据迁移

- 新增 `Store`、`StoreMembership` 或等价实体；
- 通过迁移建立唯一的默认演示门店，并将既有单门店数据回填到该门店；
- `Conversation`、`Appointment`、`KnowledgeDocument`、`Technician`、`TechnicianSchedule`、`Preference`、`UserBehavior` 等需要明确直接或间接的 `store_id`；`Message` 通过会话继承门店范围；预约事件通过预约继承门店范围；
- Repository 查询默认必须带门店上下文，不能由调用方忘记传参后退化为全表查询；
- `KnowledgeMeta`、索引快照和刷新锁至少按门店区分；若多进程一致性尚未完成，必须在 Done 定义中明确为阻塞项，而不是隐藏在演示说明里；
- 客户与商家成员必须使用不同的实体和权限路径。

### 3.4 审计和指标语义

审计事件至少包含：`event_id`、`actor_id`、`store_id`、`action`、`resource_type`、`resource_id`、`request_id`、`outcome`、安全的变更摘要和 `created_at`。密码、访问凭证、完整客户敏感内容和 Prompt 不得写入审计 payload。

Phase G 的基础指标至少定义：

- 知识发布成功/失败次数、刷新失败次数和当前版本；
- 有引用回答次数、无依据拒答次数、来源查看次数；
- 人工接管、投诉/异常标记、预约确认/取消/改约次数；
- 待跟进任务的创建、完成、逾期数量；
- 后台 API 的错误分类和耗时摘要。

指标必须说明统计口径、门店范围、时间范围和数据来源。真实模型质量分数和人工语义评测仍单列为 Phase I 待办。

### 3.5 人工接管语义

G0 必须决定会话的人工接管状态、谁可以接管、谁可以恢复 AI、接管期间买家消息如何展示以及每次切换是否写审计。推荐使用明确的会话控制状态或事件，不用一条不可追踪的布尔字段覆盖历史。

## 4. 目标后台模块与接口边界

后台 API 应以当前认证身份和当前门店上下文为边界。可以使用 `/api/v1/admin/...` 作为统一前缀；具体 URL 在 G0 的接口决策中定稿。若支持一个账号管理多家门店，切换门店必须先验证 membership，再由服务端保存或解析 active store context。

### 4.1 认证和门店上下文

| 能力 | 推荐接口职责 |
|---|---|
| 登录/退出 | 建立、撤销商家会话；失败不泄漏账号存在性 |
| 当前身份 | 返回 actor、角色、可访问门店和权限摘要 |
| 门店切换 | 仅允许切换到已授权门店；切换后所有查询重新按门店过滤 |
| 权限错误 | 未登录返回 401，无权限返回 403；不以空列表掩盖越权 |

### 4.2 客户咨询工作台

- 会话列表：按状态、时间、渠道、接管状态、异常/投诉和待跟进筛选；
- 会话详情：消息、摘要、偏好、预约事实、知识来源和安全的 AI 处理结果；
- 人工操作：接管、恢复 AI、内部备注、投诉/异常标记、标签和待跟进关联；
- 读取客户上下文时遵守 Phase E 的来源、删除墓碑和屏蔽消息语义；不能把隐藏审计字段直接展示给模型或前端；
- 任何人工接管和状态切换都进入审计事件；后台不会直接调用旧 Agent 入口绕过统一编排。

### 4.3 门店配置

- 门店资料：名称、地址、联系方式、时区和营业状态；
- 服务目录：服务项目、价格、时长、说明和是否可预约；
- 预约政策：提前预约、取消/改约窗口、迟到规则和冲突提示；
- 服务人员：姓名、专长、可服务项目和启停状态；
- 营业时间、休息日、临时闭店和服务人员排班；
- 所有配置变更必须经过服务层校验并记录版本或审计，不允许页面直接拼写数据库字段。

### 4.4 预约管理

- 今日/未来预约列表，按状态、时间、服务人员和客户筛选；
- 预约详情展示预约事件、来源会话、客户和冲突信息；
- 确认、取消、改约复用现有领域服务、事务和幂等键；
- 管理员操作与买家操作使用清晰的 actor 类型和权限，不通过修改请求体 `user_id` 伪造身份；
- 冲突、过期、非法状态和重复请求返回稳定错误语义并可在页面恢复；
- 不把旧 `technician_schedules` 兼容入口重新变成第二套预约事实来源。

### 4.5 客户运营

- 客户列表和详情：客户标识、会话摘要、预约历史、当前偏好和待跟进事项；
- 偏好展示与删除继续遵守 Phase E 的来源、确认、失效和墓碑语义；
- 回访任务至少包含负责人、原因、截止时间、状态、来源和完成记录；
- 活跃度和复购只做可解释的事实统计，不在本阶段引入无法验证的自动营销结论；
- 客户数据查询必须按门店隔离，并为后续 PII 脱敏、导出和删除保留边界。

### 4.6 审计与运营指标

- 审计查询支持按门店、操作者、动作、资源、结果和时间筛选；
- 知识发布/归档/刷新、预约状态变更、配置修改、人工接管、成员权限修改必须可追溯；
- 指标查询只能返回当前操作者有权查看的门店聚合；
- 事件生成与业务写入的事务关系必须明确：关键状态变更不能在业务成功后静默丢审计；
- 失败事件保留错误分类和 request_id，但不泄漏内部堆栈、Prompt、密钥或供应商原始响应。

- 实现登录、退出、当前身份、门店列表和授权门店切换；
- 将 `IdentityResolver` 接入后台 API，移除后台对请求体 `user_id` 的信任；
- 统一 401/403、会话过期、CSRF、重复登录和失败登录语义；
- 让现有知识、预约、服务人员和管理页面逐一声明所需权限；
- 为测试提供明确的 owner/manager/operator/viewer fixtures，Fake 身份不能默认为真实权限。

交付物：身份实现、RBAC middleware/dependency、权限契约、迁移和 `tests/test_admin_auth.py`、`tests/test_admin_rbac.py`。验收：未登录不可访问后台；无权限不可调用写接口；改变客户端 user_id、role 或 store_id 不能越权。

### G2：门店实体、数据迁移与租户隔离

- 新增门店和成员表，建立默认演示门店并安全回填历史单门店数据；
- 为会话、预约、知识、服务人员、排班、偏好和行为数据建立直接或间接门店边界；
- 将门店上下文注入 Repository、Service、Orchestrator 和后台 API；
- 对所有列表、详情、搜索、发布、归档、刷新和统计查询增加门店过滤；
- 将知识版本、索引快照、刷新状态和锁按门店隔离；明确单进程与多进程边界；
- 审查旧 `/api/knowledge`、旧预约和服务人员接口：要么绑定当前授权门店，要么禁用/标记迁移，不得保留全局读写旁路；
- 增加跨门店读取、ID 猜测、搜索、发布、预约操作和统计聚合的拒绝测试。

交付物：门店模型与迁移、`StoreContext`、Repository 过滤封装、每门店知识索引边界、`tests/test_store_isolation.py`、迁移回滚说明。验收：门店 A 的账号无法读取或修改门店 B 的任意客户、会话、预约、知识、服务人员、排班或指标；索引也不能返回 B 的证据。

### G3：门店配置、资源服务与审计契约

- 建立门店资料、服务项目/价格/时长、预约政策、营业时间、休息日和临时闭店的领域模型；
- 根据 G0 盘点结果决定复用、迁移或新建现有配置数据来源，先定义唯一事实来源、兼容读写路径和删除条件，禁止在未确认来源前并行建立第二套表或状态机；
- 将 `Technician`、`TechnicianSchedule` 迁移为门店内资源，保留预约领域服务使用的时间和冲突语义；
- 提供配置的创建、编辑、启停、预览和查询服务，校验时区、时间范围、价格、时长和互斥规则；
- 明确配置变更何时立即影响检索、预约可用性和前端展示，必要时使用版本或生效时间；
- 实现通用 `AuditService`/审计仓储，并接入知识、配置和成员权限变更；
- 任何兼容层调用都必须经过新的门店上下文，不能继续直接写旧表。

交付物：门店配置服务、资源/排班适配、审计事件契约、配置 API、事实来源/兼容迁移说明和相关测试。验收：配置写入有权限、有门店范围、有校验、有审计；非法营业时间或价格不会污染预约和回答事实；不存在两个并行的配置事实来源。

### G4：客户咨询工作台与人工接管

- 实现会话列表、筛选、分页、详情和恢复查询；
- 组装客户上下文、预约状态、偏好状态、知识来源和 AI 结果，但区分可展示字段与内部审计字段；
- 增加明确的人工接管/恢复 AI 状态、内部备注、标签、投诉/异常和待跟进关联；
- 定义接管期间的消息归属、并发写入、重复操作和断线恢复语义；
- 后台触发回复或继续处理时仍走 `ConversationOrchestrator` 和 SSE v1，不允许页面直接调用旧 Agent；
- 接管、恢复、标记和备注写入审计，来源卡片继续来自 assistant metadata，不由前端猜测。

交付物：咨询工作台 API、会话控制/跟进模型、`tests/test_admin_conversations.py`、HTTP 验收场景。验收：运营人员能从列表进入详情并完成接管；客户/门店边界、来源展示、SSE 终止语义和偏好删除语义保持不变。

### G5：商家预约管理

- 增加门店范围的预约列表、详情、日期/状态/服务人员筛选和今日视图；
- 将管理员确认、取消、改约映射到现有 `AppointmentCommandService`；
- 处理冲突、过期、非法状态、重复请求和并发操作，并展示确定性错误；
- 展示 `AppointmentEvent` 操作记录和来源会话，但不允许页面直接编辑状态字段；
- 补充权限、门店隔离、幂等、事务回退和重启恢复测试；
- 明确管理员操作是否需要二次确认、原因和审计字段。

交付物：后台预约 API、领域适配、预约页面、`tests/test_admin_appointments.py`。验收：管理员操作不会绕过领域状态机；冲突不产生重复预约；每次成功或失败操作都能在允许范围内追溯。

### G6：客户运营与回访任务

- 建立客户查询边界，避免把商家账号、客户 `user_id` 和外部渠道身份混为一谈；
- 提供客户列表、详情、会话摘要、预约历史、偏好和来源状态查询；
- 增加回访任务模型和状态机：创建、分派、完成、取消、逾期；
- 记录回访任务来源（会话、预约、投诉/异常或人工创建）和负责人；
- 使用已验证的预约/会话/偏好事实计算基础活跃度，不依赖仍有 skip 的旧行为分析组件；
- 为后续客户删除、导出、PII 脱敏和渠道身份映射保留接口边界，不在本阶段扩张成完整营销系统。

交付物：客户运营服务、回访任务 API、客户页面、`tests/test_admin_customers.py`、`tests/test_follow_up_tasks.py`。验收：客户数据按门店隔离；偏好删除后后台不会继续展示为 active 事实；回访任务状态和操作者可追溯。

### G7：审计查询、运营指标与质量事件

- 完成审计事件在关键业务事务中的写入和失败处理；
- 提供门店范围的审计查询和最小运营指标接口；
- 从知识发布/刷新、assistant 来源 metadata、无依据降级、人工接管和预约事件建立可复核统计口径；
- 增加 request_id、actor_id、store_id 和资源标识的结构化日志关联；
- 对错误日志做敏感字段清理，不记录密码、Cookie、token、Prompt、完整客户敏感内容或供应商原始响应；
- 提供真实模型/人工质量评测所需的事件和导出边界，但不把 Fake 评测结果写成真实模型质量结论。

交付物：审计查询 API、指标 API/页面、日志字段约定、统计口径文档和 `tests/test_audit_and_metrics.py`。验收：同一门店的关键操作可从业务记录追到审计事件；指标按门店和时间范围稳定计算；越权账号不能读取其他门店指标。

### G8：统一后台前端与权限感知交互

- 将 `/admin` 改造为鉴权后的后台壳层，包含当前账号、门店、角色、退出和会话过期处理；
- 基于 G0 的页面盘点复用已有 `/knowledge`、`/technician`、`/technician_schedule` 等页面能力；需要重写的页面必须记录原因、迁移路径和旧入口下线条件，不得默认全部推倒重建；
- 提供会话工作台、门店配置、预约管理、客户运营、知识管理和审计/指标入口；
- 页面根据权限显示操作，但所有写操作仍由 API 强制授权；
- 统一加载、空状态、401/403、冲突、失败重试和断线恢复；
- 不使用 localStorage 保存权限真相，不在前端拼装知识引用、预约状态或客户事实；
- 在浏览器或等价 HTTP 流程中验证登录→切换门店→查询→写入→刷新恢复的最小闭环。

交付物：后台模板/静态资源、权限感知导航、页面状态和前端交互测试。验收：不同角色看到并实际获得不同能力；刷新页面后权限和门店上下文仍由服务端恢复；越权请求即使手工发出也被拒绝。

### G9：故障注入、全量回归、文档与交接

- 注入登录会话过期、权限变更、迁移失败、审计写入失败、知识刷新失败、预约冲突、重复操作和 AI 服务失败；
- 验证旧接口没有未鉴权跨门店旁路，旧 API 删除条件和兼容期限被记录；
- 验证会话、预约、知识、偏好删除、SSE v1 和来源展示没有 Phase G 回归；
- 使用 TestClient/实际 HTTP 端点完成后台登录、权限、门店隔离、配置、会话、预约、客户和审计验收；
- 运行全量 `pytest -q`，记录通过、跳过、失败、警告和 Fake 模型边界；
- 更新 `README.md`、`PROJECT_MEMORY.md` 和 Phase G 收尾文档，明确本地、Fake、真实模型、单进程/多进程和线上证据边界；
- 将外部渠道、真实模型人工评测、PII/备份清理、平台化和更深安全加固交接到 Phase H/I。

交付物：`tests/test_phase_g_acceptance.py`、HTTP 验收记录、全量测试结果、Phase G 收尾文档、Phase H/I 交接清单。验收：所有 Done 条件满足且没有把未验证的生产行为标为完成。

## 6. 推荐执行顺序与门禁

推荐顺序：

```text
G0 → G1 → G2 → G3 → (G4 + G5 + G6) → G7 → G8 → G9
```

关键门禁：

1. G0 未完成决策记录前，不创建后台写接口；
2. G1 未完成前，不把现有管理页面标记为“商家后台”；
3. G2 未完成前，不允许多门店数据进入正式演示，不允许只靠页面筛选声称隔离完成；
4. G3 未完成前，不允许后台直接写配置表、排班表或知识表；
5. G4/G5/G6 必须复用已有会话、预约、知识和偏好服务，不能各自建立第二套事实来源；
6. G7 未完成前，关键管理动作不能标记为可运营，因为缺少追溯链路；
7. G8 未完成前，只能验收 API，不得宣称商家可以通过后台完成日常运营；
8. G9 的全量回归、HTTP 验收和变更边界记录完成前，不得标记 Phase G 完成。

## 8. 风险、回滚与边界

| 风险 | 影响 | 缓解与回滚 |
|---|---|---|
| 请求体身份被继续当作权限来源 | 极高 | 服务端 resolver、401/403 测试、禁止客户端决定 actor/store |
| 门店迁移漏回填或查询漏过滤 | 极高 | 默认门店回填前后计数对账、Repository 强制 scope、跨门店黑盒测试 |
| 多门店共享一个知识索引 | 极高 | 每门店快照/版本/锁；未完成多进程一致性则关闭多店演示 |
| 后台复制预约或知识状态机 | 高 | 只调用领域服务，旧入口逐一审查，增加状态/幂等回归 |
| 审计写入失败但业务已成功 | 高 | 定义事务语义；关键动作采用同事务或可靠 outbox；失败可观测 |
| 客户数据和商家账号混淆 | 高 | 独立实体、独立 resolver、不同 API 依赖和迁移测试 |
| 接管状态与 AI 并发写入 | 高 | 明确状态机、版本/锁、幂等和断线恢复；禁止布尔字段静默覆盖历史 |
| 页面隐藏按钮造成虚假安全感 | 中 | 每个写接口独立授权测试，手工构造越权请求验收 |
| Cookie 会话或 CSRF 防护实现不完整 | 高 | G0 锁定 HttpOnly/SameSite/CSRF 方案，G1 做写操作和会话失效测试；失败时关闭后台写入口，不降级为无鉴权模式 |
| Fake/本地结果被误报为生产质量 | 中 | 报告分开记录 Fake、真实模型、人工和线上证据 |
| 范围膨胀为完整 CRM 或平台化系统 | 中 | 以本计划 Done 和不纳入清单为门禁，新增需求单独立项 |

回滚原则：

1. 认证和门店上下文按独立提交，可通过功能开关暂时关闭后台入口，但不能恢复未鉴权写入口；
2. 数据迁移失败时保留原始表和回滚脚本，停止后台写入，不静默删除或重建历史数据；
3. 知识按门店回到上一份已验证快照，不删除原始文档；
4. 预约后台回归时只回退后台适配，不回退已验证的预约领域状态机；
5. 前端失败时保留可用 API 和只读页面，但不能把只读页面当作完整运营后台；
6. 审计或权限缺失时，阶段状态只能是阻塞/未完成，不能以“本地演示可用”替代安全门禁。
