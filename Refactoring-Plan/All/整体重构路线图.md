# AI Front Desk 整体重构路线图

## 1. 文档定位

这不是一份逐文件、逐函数的施工清单，而是 AI Front Desk 未来的整体演进方向。

目标是把当前的多 Agent 原型，逐步打造成为一个真正可使用的线下服务门店智能运营系统：

```text
买家
  ↓
独立 Web 买家端
  ↓
AI Front Desk Agent
  ↓
咨询｜预约｜排班｜服务人员匹配｜客户记忆｜回访
  ↓
商家管理后台
```

AI Front Desk 不是只替买家回答问题的聊天机器人，而是连接买家和商家的中间层：

- 对买家，它是一个随时可沟通的智能前台。
- 对商家，它是一个可以管理客户、预约、排班和知识的 AI 运营助手。
- 对系统，它是一个拥有业务状态、工具调用、记忆和审计能力的应用平台。

---

## 2. 最终产品形态

### 2.1 买家端

买家通过自然语言完成：

- 咨询服务、价格、地址、营业时间和预约政策。
- 选择服务项目、时长和服务人员偏好。
- 查询可预约的时间和服务人员。
- 创建预约、确认预约、改约和取消预约。
- 询问自己的历史预约和当前预约状态。
- 获得基于历史偏好的个性化推荐。

买家不需要理解系统内部的 Agent、工作流、数据库或工具，只需要像和门店前台聊天一样表达需求。

### 2.2 AI Front Desk Agent

Agent 负责理解和协调，而不是任意修改业务数据。

它主要承担：

- 识别用户意图。
- 提取预约信息。
- 结合上下文进行追问。
- 查询知识库、服务人员和排班。
- 调用预约、取消、改约和推荐工具。
- 维护当前工作流状态。
- 记住合适的客户偏好。
- 在不确定或高风险场景转交商家人工处理。

核心原则：

> Agent 负责理解、建议和编排；确定性业务服务负责校验、决策和写入。

### 2.3 商家端

商家通过管理后台完成：

- 查看客户咨询和预约。
- 查看 AI 已解决的问题和待人工处理的问题。
- 随时接管客户对话。
- 管理服务项目、价格和预约规则。
- 管理服务人员和排班。
- 管理门店知识库。
- 查看客户偏好和历史行为。
- 确认、修改或取消预约。
- 查看门店运营数据。
- 配置回访和推荐规则。

商家端不是一个单纯的数据管理页面，而是 AI Front Desk 的控制台：

```text
AI 自动处理日常问题
商家处理复杂问题和关键决策
系统记录过程并沉淀运营数据
```

## 3. 目标业务闭环

### 3.1 咨询到预约

```text
买家提出需求
  → Agent 判断意图
  → 查询门店知识
  → 追问缺失信息
  → 查询服务人员和排班
  → 推荐可用方案
  → 买家确认
  → 创建预约
  → 通知买家和商家
```

### 3.2 预约到服务

```text
预约创建
  → 商家后台可见
  → 服务人员排班锁定
  → 到店前提醒
  → 服务完成后记录结果
  → 更新客户行为和偏好
  → 判断是否需要回访
```

### 3.3 异常和人工接管

以下情况不应由 Agent 自行做最终决定：

- 客户投诉。
- 退款和赔付。
- 特殊健康情况。
- 价格或政策不明确。
- 服务人员临时无法履约。
- 预约冲突无法自动解决。
- 客户明确要求人工服务。

处理流程：

```text
Agent 识别异常
  → 创建待处理任务
  → 商家后台提醒
  → 商家接管或确认方案
  → Agent 将结果反馈给买家
  → 系统记录审计信息
```

## 4. 总体架构方向

第一阶段采用模块化单体，不急于拆分微服务。

```text
Web 接入层
  买家端页面 / 商家后台 / Web API / 流式事件
        ↓
API 与会话层
  用户身份、会话、权限、流式事件
        ↓
ConversationOrchestrator
  一次会话轮次的统一编排
        ↓
工作流层
  咨询 / 预约 / 改约 / 取消 / 回访 / 人工接管
        ↓
领域服务层
  服务项目 / 排班 / 服务人员 / 预约 / 客户 / 推荐
        ↓
基础设施层
  数据库 / LLM / Embedding / 知识索引 / 外部服务
        ↓
运营与观测层
  审计 / 日志 / 指标 / 评测 / 后台任务
```

### 4.1 Web 接入边界

当前项目只实现独立 Web，不建设美团、淘宝、微信、小程序等多平台适配器。Web 层负责接收请求、验证输入、识别当前用户和会话，并把业务请求交给应用层处理；预约、排班、客户和知识库规则不能直接写在页面组件或 HTTP 路由中。

```text
Web 买家端 / 商家后台
  → Web API 与身份校验
  → ConversationOrchestrator / Application Service
  → 领域服务
  → 结构化响应或流式事件
```

当前只保留必要的分层边界，不为了尚未存在的第二个平台提前实现通用 `ChannelAdapter`、跨平台订单映射或复杂消息协议。Web 请求模型也不应直接成为领域模型，API 层需要完成输入校验和必要转换。

只有在确定接入第二个真实平台后，才根据两个渠道已经出现的实际差异提取统一消息模型和渠道适配器，避免基于假设过度设计。

### 4.2 会话和身份层

系统需要区分：

- 买家身份。
- 商家身份。
- 店铺身份。
- 会话身份。
- 当前工作流身份。

状态不能保存在全局 Agent 对象中，而应由服务端管理并可以恢复。

### 4.3 工作流层

工作流负责业务过程，Agent 负责理解和调用工作流。

建议逐步形成：

```text
ConsultationWorkflow
AppointmentWorkflow
RescheduleWorkflow
CancellationWorkflow
HumanHandoffWorkflow
FollowUpWorkflow
```

## 5. 记忆与上下文方向

记忆系统不追求一开始就复制 Claude Code 或 pi agent 的全部能力，而是根据门店业务分层建设。

### 5.1 业务事实

业务事实必须结构化保存，不能只放在摘要里：

- 预约 ID。
- 服务项目 ID。
- 服务人员 ID。
- 预约时间。
- 预约状态。
- 订单或支付状态。

### 5.2 会话上下文

保存当前对话需要继续工作的内容：

- 最近几轮消息。
- 当前工作流。
- 已提取字段。
- 缺少字段。
- 待确认动作。
- 最近一次工具结果。

### 5.3 长期客户记忆

只保存稳定、有来源、可解释的信息：

- 偏好服务项目。
- 偏好服务人员。
- 偏好时间段。
- 服务时长偏好。
- 客户主动表达的长期要求。

长期记忆必须支持查看、修改、删除和失效。

### 5.4 轻量 ContextBuilder

保留一个简单的上下文装配模块，而不是让每个 Agent 自己拼接历史：

```text
系统规则
  → 当前用户输入
  → 当前工作流状态
  → 最近原始消息
  → 客户偏好
  → 会话摘要
  → 相关知识库内容
  → Token 预算裁剪
```

先实现“够用的上下文装配”，不急于建设复杂的语义记忆检索系统。

### 5.5 自动压缩

上下文达到预算后：

```text
保留当前工作流和关键事实
  → 保留最近若干轮消息
  → 对更早消息生成摘要
  → 记录摘要覆盖到哪条消息
  → 失败时回退到原始消息
```

压缩不能丢失：

- 未完成预约字段。
- 待确认动作。
- 用户明确的限制条件。
- 工具调用和工具结果之间的关联。

## 6. 数据和领域模型方向

最终系统应逐步形成以下核心实体：

```text
Store
User
Conversation
Message
WorkflowState
WorkflowEvent
ConversationSummary
ServiceItem
Technician
Schedule
Appointment
UserPreference
FollowUpTask
HumanHandoffTask
AgentRun
```

### 核心数据原则

1. 业务状态和聊天文本分离。
2. 预约和排班分离。
3. 客户偏好和原始行为分离。
4. Agent 输出和最终业务结果分离。
5. 所有关键写入都可以追溯。
6. 关键动作支持幂等重试。
7. 买家、商家和店铺数据必须有明确归属。

## 7. 分阶段演进路线

### Phase A：建立可测试的工程基础

目标：让项目从“能运行的原型”变成“可安全重构的项目”。

方向：

- 统一依赖注入。
- LLM、Embedding 和外部服务可替换。
- 建立 Fake LLM 测试模式。
- 固化 API 契约和核心业务行为。
- 统一日志和错误边界。
- 建立本地一键启动和测试方式。

完成后，核心测试不依赖真实模型和外网服务。

### Phase B：会话隔离和消息持久化

目标：每个买家都有独立、可恢复的会话。

方向：

- 引入用户和会话标识。
- 移除全局 Agent 状态。
- 持久化用户消息和 Agent 消息。
- 服务重启后能够恢复会话。
- 处理同一会话的并发请求。
- 前端保存并传递会话标识。

完成后，不同买家之间不会共享预约草稿、历史或状态。

### Phase C：预约和排班领域化

目标：预约成为可靠的业务系统，而不是 Agent 内部字典。

方向：

- 建立独立预约实体。
- 建立预约状态机。
- 分离排班和预约。
- 实现时间冲突校验。
- 实现事务写入和幂等处理。
- 支持确认、取消、改约和失败恢复。

完成后，Agent 即使出错或应用重启，预约状态仍然可恢复。

### Phase D：统一 Agent 编排和工具边界

目标：让 Agent 从“互相回调的机器人”变成“统一编排的业务入口”。

方向：

- 引入统一 Orchestrator。
- 一个请求只进行一次主路由。
- LLM 只负责理解、提取和生成。
- 业务服务负责校验和写入。
- 工具调用使用明确的输入输出模型。
- 统一流式事件和错误码。
- 删除旧的兼容层和重复数据访问入口。

完成后，系统行为能够被测试、回放和追踪。

### Phase E：上下文、记忆和长期对话能力

目标：让 Agent 能够持续理解当前会话，并适度记住客户偏好。

方向：

- 增加轻量 ContextBuilder。
- 增加会话摘要。
- 按 Token 预算组合上下文。
- 保留预约关键事实。
- 保存有来源的客户偏好。
- 支持偏好查看、修改和删除。
- 增加摘要覆盖范围和失败回退机制。

完成后，长对话不会无限增长，也不会因为摘要丢失业务状态。

### Phase F：知识库和回答可信度

目标：让 Agent 的咨询回答更稳定、更容易维护。

方向：

- 管理员可以维护门店知识。
- 知识内容和服务配置分离。
- 设置检索相关度阈值。
- 返回回答依据的知识来源。
- 知识更新后能够安全刷新索引。
- 无足够依据时主动说明，不编造价格和政策。

完成后，商家修改一次知识，Agent 后续回答可以使用新内容。

### Phase G：商家运营后台

目标：让商家可以真正管理 AI，而不是只能查看数据库结果。

方向：

#### 客户咨询工作台

- 查看会话列表。
- 查看客户上下文和预约状态。
- 查看 AI 处理结果。
- 接管对话。
- 标记投诉、异常和待跟进事项。

#### 门店配置

- 服务项目和价格。
- 营业时间和预约政策。
- 服务人员和专长。
- 排班和休息时间。
- 门店地址和联系方式。

#### 预约管理

- 查看今日和未来预约。
- 确认、取消和改约。
- 处理冲突和异常。
- 查看预约操作记录。

#### 客户运营

- 查看客户偏好。
- 查看历史预约。
- 创建回访任务。
- 查看客户活跃和复购情况。

完成后，商家可以通过一个后台完成日常运营，而不必直接操作数据库。

### Phase H：Web 渠道产品化

目标：把独立 Web 建设成当前项目唯一且完整可用的买家入口，并与商家后台共同跑通“咨询—预约—管理—人工接管”闭环。本阶段追求一个平台真正可用，不以平台数量作为成果。

#### H.1 明确单平台产品边界

- 买家只通过独立 Web 进入系统。
- 商家只通过 Web 管理后台处理配置、预约和会话。
- 当前不开发小程序、美团、淘宝、微信等渠道。
- 当前不实现跨平台客户合并、订单同步或消息转发。
- 演示、测试和验收都以 Web 闭环为准。

#### H.2 完善买家端核心体验

- 提供清晰的会话入口，并支持新建和继续已有会话。
- 支持自然语言咨询服务、价格、营业时间、地址和预约政策。
- 在预约过程中清晰展示已收集信息、待补充信息和待确认动作。
- 展示服务项目、服务人员、可预约时间以及冲突后的替代方案。
- 在创建、改约或取消前进行明确确认，完成后展示可核对的业务结果。
- 页面刷新或短暂断线后能够恢复当前会话和未完成流程。
- 当 AI 无法处理或买家要求人工服务时，提供明确的转人工状态。
- 对等待、失败、重试、重复提交和会话过期提供可理解的界面反馈。

#### H.3 打通商家后台协作闭环

- 新咨询和新预约能够及时出现在商家后台。
- 商家能够查看对话上下文、预约状态和关键工具执行结果。
- 商家可以接管会话，并向买家端回传人工回复。
- 商家修改、确认、取消或改约后，买家端能够看到最新状态。
- AI 处理与人工处理使用明确状态区分，避免双方同时回复或重复执行。
- 投诉、退款、规则不明确和预约冲突等异常进入待处理队列。

#### H.4 稳定 Web API 与事件契约

- 为会话、消息、预约确认、改约、取消和人工接管定义清晰的请求与响应模型。
- 统一普通响应和流式事件中的消息类型、错误码、时间与关联标识。
- Web API 只处理协议、身份、输入校验和应用服务调用，不承载领域规则。
- 所有写操作携带幂等标识，避免刷新、重试或双击造成重复预约。
- 客户端只使用公开 API，不直接依赖数据库结构或 Agent 内部状态。
- 为关键契约建立自动化测试，防止前后端在重构中发生静默不兼容。

#### H.5 完善 Web 可用性

- 支持桌面端和移动浏览器的响应式布局，但仍属于同一个 Web 平台。
- 补齐加载、空状态、失败、重试、无权限和服务不可用等页面状态。
- 为表单、对话和关键操作提供基础键盘操作及可访问性支持。
- 明确登录、退出、会话失效和重新认证流程。
- 对消息发送、Agent 处理和预约写入设置超时与安全重试策略。
- 保证关键页面可以通过稳定路径访问，便于演示和自动化验收。

#### H.6 分步交付顺序

1. 固化 Web 会话、消息和预约相关 API 契约。
2. 跑通买家咨询到创建预约的主路径。
3. 打通商家后台查看预约、接管会话和回传结果。
4. 补齐改约、取消、异常处理、刷新恢复和重复提交保护。
5. 完成桌面端与移动浏览器适配。
6. 增加端到端测试并完成完整演示验收。

#### Phase H 验收标准

至少验证以下场景：

```text
买家从 Web 发起咨询
  → Agent 使用真实门店知识回答
  → 买家提供预约信息
  → 系统查询真实服务项目、人员和排班
  → 买家确认并创建预约
  → 商家后台看到同一预约和关联会话
  → 商家修改预约或接管对话
  → 买家端看到最新结果
```

同时满足：

- 两个不同浏览器会话之间不会串线。
- 页面刷新后，会话、流程和预约状态可以恢复。
- 重复提交不会创建重复预约或重复执行关键动作。
- AI 失败时不会伪造成功结果，买家可以重试或转人工。
- 商家接管后，AI 不再继续自动回复，退出接管后可按规则恢复。
- 桌面端和移动浏览器均可完成核心闭环。
- 关键操作有日志、关联标识和审计记录。
- 主路径具备自动化端到端测试，并完成一次人工演示验收。

#### 本阶段明确不做

- 小程序客户端。
- 美团、淘宝、微信等第三方平台接入。
- 通用 `ChannelAdapter` 框架。
- 跨平台客户身份合并。
- 跨平台消息、订单和售后同步。
- 为尚未获得的第三方接口预留大量字段或兼容逻辑。

#### 未来扩展条件

只有同时满足以下条件，才启动第二个平台接入：

1. Web 主闭环已经稳定通过验收。
2. 已经明确第二个平台及其真实业务价值。
3. 已获得可使用的官方接口、测试环境和必要授权。
4. 已掌握真实消息、身份、订单和回调协议，而不是依靠猜测设计。
5. 个人维护成本仍然可控，新增渠道不会拖慢核心业务迭代。

届时先实现第二个平台的最小接入，再根据 Web 与第二个平台之间已经出现的共同点提取 `ChannelAdapter`、统一消息模型和身份映射。本阶段不提前承担这部分复杂度。

### Phase I：安全、运营和质量评测

目标：让系统具备可持续运行和演示的工程基础。

方向：

- 商家账号和角色权限。
- 店铺和用户数据隔离。
- PII 脱敏。
- 管理操作审计。
- LLM 成本、延迟和失败监控。
- 意图、字段提取、RAG 和摘要评测。
- 并发、恢复和幂等测试。
- 备份和数据清理策略。

## 8. 第一版真正可用的边界

第一版不是功能展示页面，也不是依赖预设对话才能运行的 Demo。它应当在独立 Web 上使用持久化业务数据，支持真实的会话、排班和预约状态，并让买家与商家共同完成一条可重复验证的业务闭环。

第一版不要求完成 Phase A 至 Phase I 的全部长期能力，只交付支撑核心闭环所必需的最小集合。判断标准不是“功能数量多”，而是“主流程可以完成、异常不会失控、结果能够管理和追溯”。

### 8.1 产品和使用范围

第一版按以下边界建设：

- **一个渠道**：只提供独立 Web，包括买家端和商家管理后台；桌面端与移动浏览器属于同一个平台。
- **一个门店**：只支持一个门店实例，不提供多门店切换、集团管理或多租户运营能力。
- **两类角色**：买家和商家管理员；第一版不细分店长、前台、技师等复杂后台角色。
- **一类核心业务**：围绕线下服务咨询和预约，不扩展到电商交易、库存、配送或完整 CRM。
- **一个可重复部署环境**：项目可以按文档启动、初始化基础数据并完成验收，不以商业级高可用为目标。

即使第一版只服务一个门店，业务数据仍应明确归属于当前门店；可以保留 `store_id` 等基础归属字段，但不开发多门店管理界面和跨门店流程。

### 8.2 必须跑通的核心闭环

第一版必须完整跑通以下主路径：

```text
买家从独立 Web 进入
  → 新建或恢复自己的会话
  → 询问服务、价格、营业时间或预约规则
  → Agent 基于门店知识回答，并说明无法确认的内容
  → Agent 收集服务项目、日期、时间和人员偏好
  → 系统查询真实服务项目、服务人员和可用排班
  → Agent 提供可预约方案
  → 买家明确确认
  → 确定性预约服务校验冲突并创建预约
  → 买家获得预约编号和当前状态
  → 商家后台看到预约及关联会话
  → 商家确认、修改预约或接管对话
  → 买家端看到最新业务结果或人工回复
```

除创建预约外，还必须支持预约生命周期中的最小必要操作：

- 买家查询自己的当前预约。
- 买家在规则允许时取消或申请改约。
- 商家确认、修改、取消预约并查看操作结果。
- 排班冲突时拒绝错误写入，并向买家提供可用替代时间。
- 无法自动处理时创建人工待办，而不是让流程停留在未知状态。

第一版的通知只要求在买家 Web 和商家后台内可见，不要求短信、邮件或第三方消息推送。

### 8.3 第一版必须具备的能力

#### 买家 Web

- 新建会话，并通过稳定标识恢复自己的会话。
- 发送消息并看到流式或完整回复。
- 咨询门店知识、服务项目、价格、营业时间和预约规则。
- 创建、查询、取消和改约自己的预约。
- 在关键写操作前看到待确认内容，操作后看到明确成功或失败结果。
- 看到 AI 处理中、等待人工、人工已接管、请求失败和可重试等状态。
- 刷新页面后恢复最近消息、当前流程和预约结果。
- 在桌面端和移动浏览器上完成核心流程。

#### Agent 与应用服务

- 第一版只识别咨询、创建预约、查询预约、取消预约、改约和转人工等核心意图。
- 缺少必要字段时逐项追问，不根据模糊信息直接写入预约。
- 咨询回答必须来自可维护的门店知识或结构化业务数据；依据不足时明确转人工或说明无法确认。
- Agent 只能提出建议和发起工具调用，不能绕过领域服务直接修改数据库。
- 创建、取消和改约必须由确定性服务完成身份、状态、时间冲突和幂等校验。
- 工具调用失败时返回真实失败状态，不把自然语言回复当作业务成功。
- 会话状态、预约事实和工具结果在服务重启后仍可恢复。

#### 商家管理后台

- 商家必须登录后才能访问管理能力。
- 维护门店基础信息、营业时间、预约规则、服务项目、价格、服务人员、排班和知识内容。
- 查看会话列表、消息记录、预约列表和预约详情。
- 查看预约关联的买家会话和关键处理过程。
- 确认、修改、取消预约，并看到冲突或失败原因。
- 接管和结束人工会话；接管期间 AI 不得继续自动回复。
- 查看待人工处理事项，并向买家端回传处理结果。

### 8.4 数据边界

第一版必须持久化并实际使用以下数据：

- 当前门店及其基础配置。
- 买家身份或可稳定识别买家的用户标识。
- 商家账号及最小权限信息。
- 会话、消息和当前工作流状态。
- 服务项目、价格、时长和预约规则。
- 服务人员、排班和不可用时间。
- 预约、预约状态及状态变更记录。
- 门店知识内容及必要的检索索引。
- 人工接管任务和关键操作审计记录。

“真实业务数据”在第一版中是指：数据来自数据库和可维护配置，业务写入会被持久化并可再次查询，而不是写死在 Prompt、前端常量或 Agent 内存中。开发和自动化测试可以使用固定测试数据，但验收不能依赖临时伪造的成功响应。

第一版不建立支付、退款、发票、库存、营销活动、会员积分和财务结算等领域模型。

### 8.5 自动处理和人工接管边界

满足信息完整、规则明确且校验通过时，系统可以自动：

- 回答有可靠知识依据的常见咨询。
- 查询服务项目、服务人员和可预约时间。
- 推荐符合当前规则的预约方案。
- 在买家确认后创建预约。
- 按明确规则查询、取消或改约预约。

出现以下情况时，第一版必须停止自动决策并转交商家：

- 投诉、退款、赔付或支付争议。
- 特殊健康、安全或服务风险。
- 价格、优惠、服务范围或门店政策没有可靠依据。
- 无法确认买家身份或预约归属。
- 排班冲突无法提供有效替代方案。
- 业务写入连续失败，无法确认最终结果。
- 买家明确要求人工服务。
- 其他超出核心意图范围的请求。

进入人工接管后，系统必须记录接管状态和负责人，暂停该会话中的 AI 自动回复。商家结束接管后，才能按明确规则恢复 AI 处理。

### 8.6 可靠性和安全底线

以下要求不是后续优化项，而是第一版可用的最低条件：

- 会话不串线。
- 买家只能查看和操作自己的会话与预约。
- 未登录用户不能调用商家管理接口，普通买家不能获得商家权限。
- 同一服务人员的重叠时间不能产生两个有效预约。
- 重复点击、网络重试或重复请求不能创建重复预约或重复执行取消、改约。
- 服务重启或页面刷新后，会话、工作流和预约状态能够恢复。
- 预约成功必须以数据库写入结果为准，失败或结果未知时不得向用户显示成功。
- Agent 生成内容不能替代价格、排班、身份和预约状态等结构化事实。
- 所有关键写操作必须记录操作者、时间、对象、动作和结果。
- 日志不得直接输出密码、令牌或不必要的完整个人敏感信息。
- 系统异常必须返回稳定错误语义，并给出重试或转人工路径。

### 8.7 必须通过的验收场景

第一版至少应对以下场景进行自动化或人工验收，并保存可重复执行的步骤：

1. **正常预约**：买家完成咨询、信息补充、确认和预约创建，商家后台看到同一预约。
2. **信息缺失**：买家没有提供完整日期、时间或服务项目时，Agent 继续追问且不提前创建预约。
3. **时间冲突**：两个买家竞争同一服务人员的同一时间，系统最多只允许一个有效预约，另一方得到明确失败和替代方案。
4. **重复提交**：相同确认请求重复发送，只产生一个业务结果。
5. **刷新与恢复**：买家在预约中途刷新页面或服务重启后，可以继续原流程，已成功的预约不会丢失。
6. **会话隔离**：两个买家不能看到、恢复或操作对方的消息和预约。
7. **知识不足**：知识库没有依据时，Agent 不编造价格或政策，并能够转人工。
8. **人工接管**：商家接管后可以回复买家，AI 暂停自动回复；结束接管后状态正确恢复。
9. **预约变更**：取消或改约成功后，买家端、商家后台和排班结果保持一致。
10. **权限拦截**：未登录或无权限请求无法访问商家后台及管理接口。

上述场景只要存在会话串线、越权访问、重复预约、预约结果丢失或“实际失败但页面显示成功”，第一版就不能判定为可用。

### 8.8 第一版明确不做

为控制个人项目的开发和维护成本，以下内容不进入第一版：

- 小程序及任何第三方平台接入。
- 通用多平台适配框架。
- 多门店、多商户和 SaaS 租户管理。
- 店长、前台、技师等复杂角色和细粒度权限矩阵。
- 在线支付、退款、发票、会员、积分、库存和财务结算。
- 短信、邮件、微信等外部通知渠道。
- 自动处理投诉、赔付和复杂售后。
- 复杂长期记忆和跨会话行为画像。
- 自动回访、营销活动和智能复购决策。
- 微服务拆分。
- 完全自主的多 Agent 协作。
- 商业级高并发、跨区域容灾和 7×24 小时可用性承诺。

### 8.9 第一版完成定义

只有同时满足以下条件，第一版才算完成：

- 第 8.2 节的核心闭环可以在独立 Web 上从头到尾完成。
- 第 8.3 节列出的买家端、Agent、业务服务和商家后台能力均可实际操作。
- 第 8.7 节的十个验收场景全部通过，并且关键场景有自动化测试保护。
- 不存在已知的会话串线、越权访问、重复预约、状态丢失和虚假成功问题。
- 数据库初始化、项目启动和验收步骤有明确文档，在干净环境中可以重复执行。
- 至少完成一次买家端与商家后台联合的人工演示验收，并记录遗留问题。
- 未完成内容被明确放入后续阶段，不通过临时假数据或不可追溯的手工操作伪装完成。

## 9. 最终验收标准

当以下链路成立时，AI Front Desk 才可以称为“真正可用的门店 AI 前台”：

```text
买家能够自然表达需求
  → Agent 能理解并追问
  → 系统能查询真实业务数据
  → 预约和排班不会产生明显错误
  → 商家能够查看和管理结果
  → 复杂问题可以人工接管
  → 用户偏好能够适度沉淀
  → 长对话上下文不会失控
  → 所有关键动作可追踪和恢复
```

最终产品价值不是“模型回答得多像人”，而是：

> 买家愿意使用，商家能够管理，系统能够可靠执行，业务结果可以被追溯。

## 10. 长期原则

1. 先完成一条买家到商家的业务闭环，再扩展渠道。
2. 先保证状态和数据正确，再追求更强的模型能力。
3. 结构化业务事实不能只保存在摘要或 Prompt 中。
4. Agent 可以建议，但关键业务动作必须经过确定性校验。
5. 商家必须能够查看、修改、接管和撤销 AI 行为。
6. 记忆必须有来源、边界、过期机制和删除能力。
7. 不为了“像 Claude Code 或 pi agent”而复制不适合门店业务的复杂机制。
8. 保持模块化单体，等真实业务规模证明需要拆分时再拆分。
