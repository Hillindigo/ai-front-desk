# AI Front Desk 整体重构路线图

## 1. 文档定位

这不是一份逐文件、逐函数的施工清单，而是 AI Front Desk 未来的整体演进方向。

目标是把当前的多 Agent 原型，逐步打造成为一个真正可使用的线下服务门店智能运营系统：

```text
买家
  ↓
美团 / 淘宝 / 微信 / 小程序 / 独立 Web 等渠道
  ↓
AI Front Desk Agent
  ↓
咨询｜预约｜排班｜服务人员匹配｜客户记忆｜回访
  ↓
商家管理后台
```

AI Front Desk 不是只替买家回答问题的聊天机器人，而是连接买家和商家的中间层：

- 对买家，它是一个随时可沟通的智能前台。
- 对商家，它是一个可以管理客户、预约、排班和知识的 AI 运营助手。
- 对系统，它是一个拥有业务状态、工具调用、记忆和审计能力的应用平台。

---

## 2. 最终产品形态

### 2.1 买家端

买家通过自然语言完成：

- 咨询服务、价格、地址、营业时间和预约政策。
- 选择服务项目、时长和服务人员偏好。
- 查询可预约的时间和服务人员。
- 创建预约、确认预约、改约和取消预约。
- 询问自己的历史预约和当前预约状态。
- 获得基于历史偏好的个性化推荐。

买家不需要理解系统内部的 Agent、工作流、数据库或工具，只需要像和门店前台聊天一样表达需求。

### 2.2 AI Front Desk Agent

Agent 负责理解和协调，而不是任意修改业务数据。

它主要承担：

- 识别用户意图。
- 提取预约信息。
- 结合上下文进行追问。
- 查询知识库、服务人员和排班。
- 调用预约、取消、改约和推荐工具。
- 维护当前工作流状态。
- 记住合适的客户偏好。
- 在不确定或高风险场景转交商家人工处理。

核心原则：

> Agent 负责理解、建议和编排；确定性业务服务负责校验、决策和写入。

### 2.3 商家端

商家通过管理后台完成：

- 查看客户咨询和预约。
- 查看 AI 已解决的问题和待人工处理的问题。
- 随时接管客户对话。
- 管理服务项目、价格和预约规则。
- 管理服务人员和排班。
- 管理门店知识库。
- 查看客户偏好和历史行为。
- 确认、修改或取消预约。
- 查看门店运营数据。
- 配置回访和推荐规则。

商家端不是一个单纯的数据管理页面，而是 AI Front Desk 的控制台：

```text
AI 自动处理日常问题
商家处理复杂问题和关键决策
系统记录过程并沉淀运营数据
```

## 3. 目标业务闭环

### 3.1 咨询到预约

```text
买家提出需求
  → Agent 判断意图
  → 查询门店知识
  → 追问缺失信息
  → 查询服务人员和排班
  → 推荐可用方案
  → 买家确认
  → 创建预约
  → 通知买家和商家
```

### 3.2 预约到服务

```text
预约创建
  → 商家后台可见
  → 服务人员排班锁定
  → 到店前提醒
  → 服务完成后记录结果
  → 更新客户行为和偏好
  → 判断是否需要回访
```

### 3.3 异常和人工接管

以下情况不应由 Agent 自行做最终决定：

- 客户投诉。
- 退款和赔付。
- 特殊健康情况。
- 价格或政策不明确。
- 服务人员临时无法履约。
- 预约冲突无法自动解决。
- 客户明确要求人工服务。

处理流程：

```text
Agent 识别异常
  → 创建待处理任务
  → 商家后台提醒
  → 商家接管或确认方案
  → Agent 将结果反馈给买家
  → 系统记录审计信息
```

## 4. 总体架构方向

第一阶段采用模块化单体，不急于拆分微服务。

```text
渠道适配层
  美团 / 淘宝 / 微信 / 小程序 / Web
        ↓
API 与会话层
  用户身份、会话、权限、流式事件
        ↓
ConversationOrchestrator
  一次会话轮次的统一编排
        ↓
工作流层
  咨询 / 预约 / 改约 / 取消 / 回访 / 人工接管
        ↓
领域服务层
  服务项目 / 排班 / 服务人员 / 预约 / 客户 / 推荐
        ↓
基础设施层
  数据库 / LLM / Embedding / 知识索引 / 外部平台 API
        ↓
运营与观测层
  审计 / 日志 / 指标 / 评测 / 后台任务
```

### 4.1 渠道适配层

不同平台只负责处理平台协议，不直接包含业务逻辑。

```text
MeituanAdapter
TaobaoAdapter
WeChatAdapter
WebAdapter
```

所有渠道最终转换为统一内部消息：

```text
InboundMessage
  → ConversationOrchestrator
  → OutboundEvent
```

这样不会把美团的字段、淘宝的订单结构直接写进预约业务代码。

真实平台接入依赖平台官方接口、商家授权和开放能力；在正式接入前，可以先使用 Web / 小程序作为完整验证渠道。

### 4.2 会话和身份层

系统需要区分：

- 买家身份。
- 商家身份。
- 店铺身份。
- 会话身份。
- 当前工作流身份。

状态不能保存在全局 Agent 对象中，而应由服务端管理并可以恢复。

### 4.3 工作流层

工作流负责业务过程，Agent 负责理解和调用工作流。

建议逐步形成：

```text
ConsultationWorkflow
AppointmentWorkflow
RescheduleWorkflow
CancellationWorkflow
HumanHandoffWorkflow
FollowUpWorkflow
```

## 5. 记忆与上下文方向

记忆系统不追求一开始就复制 Claude Code 或 pi agent 的全部能力，而是根据门店业务分层建设。

### 5.1 业务事实

业务事实必须结构化保存，不能只放在摘要里：

- 预约 ID。
- 服务项目 ID。
- 服务人员 ID。
- 预约时间。
- 预约状态。
- 订单或支付状态。

### 5.2 会话上下文

保存当前对话需要继续工作的内容：

- 最近几轮消息。
- 当前工作流。
- 已提取字段。
- 缺少字段。
- 待确认动作。
- 最近一次工具结果。

### 5.3 长期客户记忆

只保存稳定、有来源、可解释的信息：

- 偏好服务项目。
- 偏好服务人员。
- 偏好时间段。
- 服务时长偏好。
- 客户主动表达的长期要求。

长期记忆必须支持查看、修改、删除和失效。

### 5.4 轻量 ContextBuilder

保留一个简单的上下文装配模块，而不是让每个 Agent 自己拼接历史：

```text
系统规则
  → 当前用户输入
  → 当前工作流状态
  → 最近原始消息
  → 客户偏好
  → 会话摘要
  → 相关知识库内容
  → Token 预算裁剪
```

先实现“够用的上下文装配”，不急于建设复杂的语义记忆检索系统。

### 5.5 自动压缩

上下文达到预算后：

```text
保留当前工作流和关键事实
  → 保留最近若干轮消息
  → 对更早消息生成摘要
  → 记录摘要覆盖到哪条消息
  → 失败时回退到原始消息
```

压缩不能丢失：

- 未完成预约字段。
- 待确认动作。
- 用户明确的限制条件。
- 工具调用和工具结果之间的关联。

## 6. 数据和领域模型方向

最终系统应逐步形成以下核心实体：

```text
Store
User
Conversation
Message
WorkflowState
WorkflowEvent
ConversationSummary
ServiceItem
Technician
Schedule
Appointment
UserPreference
FollowUpTask
HumanHandoffTask
AgentRun
```

### 核心数据原则

1. 业务状态和聊天文本分离。
2. 预约和排班分离。
3. 客户偏好和原始行为分离。
4. Agent 输出和最终业务结果分离。
5. 所有关键写入都可以追溯。
6. 关键动作支持幂等重试。
7. 买家、商家和店铺数据必须有明确归属。

## 7. 分阶段演进路线

### Phase A：建立可测试的工程基础

目标：让项目从“能运行的原型”变成“可安全重构的项目”。

方向：

- 统一依赖注入。
- LLM、Embedding 和外部服务可替换。
- 建立 Fake LLM 测试模式。
- 固化 API 契约和核心业务行为。
- 统一日志和错误边界。
- 建立本地一键启动和测试方式。

完成后，核心测试不依赖真实模型和外网服务。

### Phase B：会话隔离和消息持久化

目标：每个买家都有独立、可恢复的会话。

方向：

- 引入用户和会话标识。
- 移除全局 Agent 状态。
- 持久化用户消息和 Agent 消息。
- 服务重启后能够恢复会话。
- 处理同一会话的并发请求。
- 前端保存并传递会话标识。

完成后，不同买家之间不会共享预约草稿、历史或状态。

### Phase C：预约和排班领域化

目标：预约成为可靠的业务系统，而不是 Agent 内部字典。

方向：

- 建立独立预约实体。
- 建立预约状态机。
- 分离排班和预约。
- 实现时间冲突校验。
- 实现事务写入和幂等处理。
- 支持确认、取消、改约和失败恢复。

完成后，Agent 即使出错或应用重启，预约状态仍然可恢复。

### Phase D：统一 Agent 编排和工具边界

目标：让 Agent 从“互相回调的机器人”变成“统一编排的业务入口”。

方向：

- 引入统一 Orchestrator。
- 一个请求只进行一次主路由。
- LLM 只负责理解、提取和生成。
- 业务服务负责校验和写入。
- 工具调用使用明确的输入输出模型。
- 统一流式事件和错误码。
- 删除旧的兼容层和重复数据访问入口。

完成后，系统行为能够被测试、回放和追踪。

### Phase E：上下文、记忆和长期对话能力

目标：让 Agent 能够持续理解当前会话，并适度记住客户偏好。

方向：

- 增加轻量 ContextBuilder。
- 增加会话摘要。
- 按 Token 预算组合上下文。
- 保留预约关键事实。
- 保存有来源的客户偏好。
- 支持偏好查看、修改和删除。
- 增加摘要覆盖范围和失败回退机制。

完成后，长对话不会无限增长，也不会因为摘要丢失业务状态。

### Phase F：知识库和回答可信度

目标：让 Agent 的咨询回答更稳定、更容易维护。

方向：

- 管理员可以维护门店知识。
- 知识内容和服务配置分离。
- 设置检索相关度阈值。
- 返回回答依据的知识来源。
- 知识更新后能够安全刷新索引。
- 无足够依据时主动说明，不编造价格和政策。

完成后，商家修改一次知识，Agent 后续回答可以使用新内容。

### Phase G：商家运营后台

目标：让商家可以真正管理 AI，而不是只能查看数据库结果。

方向：

#### 客户咨询工作台

- 查看会话列表。
- 查看客户上下文和预约状态。
- 查看 AI 处理结果。
- 接管对话。
- 标记投诉、异常和待跟进事项。

#### 门店配置

- 服务项目和价格。
- 营业时间和预约政策。
- 服务人员和专长。
- 排班和休息时间。
- 门店地址和联系方式。

#### 预约管理

- 查看今日和未来预约。
- 确认、取消和改约。
- 处理冲突和异常。
- 查看预约操作记录。

#### 客户运营

- 查看客户偏好。
- 查看历史预约。
- 创建回访任务。
- 查看客户活跃和复购情况。

完成后，商家可以通过一个后台完成日常运营，而不必直接操作数据库。

### Phase H：渠道接入和平台化

目标：让 AI Front Desk 可以服务不同买家入口。

方向：

- 先完善 Web / 小程序渠道。
- 再设计统一渠道适配器。
- 对接美团等本地生活平台的官方能力。
- 适配淘宝等电商平台的订单和客服场景。
- 支持微信等私域渠道。
- 统一不同平台的客户身份、消息和订单映射。

平台接入必须建立在官方接口、商家授权和可验证的权限边界上，不把平台假设直接写进核心业务。

### Phase I：安全、运营和质量评测

目标：让系统具备可持续运行和演示的工程基础。

方向：

- 商家账号和角色权限。
- 店铺和用户数据隔离。
- PII 脱敏。
- 管理操作审计。
- LLM 成本、延迟和失败监控。
- 意图、字段提取、RAG 和摘要评测。
- 并发、恢复和幂等测试。
- 备份和数据清理策略。

## 8. 第一版真正可用的边界

第一版不需要做到所有平台、所有业务全部自动化，但至少应该完整跑通一条闭环：

```text
买家从 Web 或小程序进入
  → 询问服务
  → Agent 查询知识库
  → Agent 收集预约信息
  → 查询服务人员和排班
  → 买家确认
  → 创建预约
  → 商家后台看到预约
  → 商家可以接管或修改
```

第一版应优先保证：

- 会话不串线。
- 预约不重复。
- 状态可恢复。
- 商家看得到结果。
- 商家可以人工接管。
- 知识内容可维护。
- 关键动作有记录。

暂时不要求：

- 多平台同时上线。
- 自动处理所有售后和投诉。
- 复杂长期记忆。
- 全自动营销决策。
- 微服务拆分。
- 完全自主的多 Agent 协作。

---

## 9. 最终验收标准

当以下链路成立时，AI Front Desk 才可以称为“真正可用的门店 AI 前台”：

```text
买家能够自然表达需求
  → Agent 能理解并追问
  → 系统能查询真实业务数据
  → 预约和排班不会产生明显错误
  → 商家能够查看和管理结果
  → 复杂问题可以人工接管
  → 用户偏好能够适度沉淀
  → 长对话上下文不会失控
  → 所有关键动作可追踪和恢复
```

最终产品价值不是“模型回答得多像人”，而是：

> 买家愿意使用，商家能够管理，系统能够可靠执行，业务结果可以被追溯。

---

## 10. 长期原则

1. 先完成一条买家到商家的业务闭环，再扩展渠道。
2. 先保证状态和数据正确，再追求更强的模型能力。
3. 结构化业务事实不能只保存在摘要或 Prompt 中。
4. Agent 可以建议，但关键业务动作必须经过确定性校验。
5. 商家必须能够查看、修改、接管和撤销 AI 行为。
6. 记忆必须有来源、边界、过期机制和删除能力。
7. 不为了“像 Claude Code 或 pi agent”而复制不适合门店业务的复杂机制。
8. 保持模块化单体，等真实业务规模证明需要拆分时再拆分。
