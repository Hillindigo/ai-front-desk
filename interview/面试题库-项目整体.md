## 1. 请用一到两分钟介绍这个项目，并说明你在二次开发中做了什么

**口语回答 · 当前实现**：好，我给咱们从整体上介绍下这个项目。它不是普通聊天机器人，而是给线下服务门店"看前台"用的一套 AI 系统，把客户进门之后的咨询、预约、选服务人员、记客户偏好、甚至人工接管，串成一条能真正落地的流程。

客户用大白话问一句，系统先判断他是想干嘛：问价格就去咨询，约时间就去预约。咨询的话，系统先到门店知识库把相关证据捞出来，再让模型照着证据答，不会乱编；预约的话，就一步步把项目、时间、时长、人员偏好抠出来，缺哪个补问哪个，凑齐了再查服务人员档期，最后客户点头确认，才真正把预约写进去。

我在二次开发里的主要精力放在后端和 Agent 这块：会话的持久化和恢复、统一的编排、流式输出、预约这整套状态机和对重复请求的处理、知识库的发布与检索、还有模型怎么抽象、怎么离线测试。项目本身是本地优先的模块化单体，后端是 FastAPI 加 SQLite。前端我只配合着对接口和流式协议，不碰核心业务，所以面试重点放后端和 Agent 上比较合适。

**口语回答 · 可扩展方案**：如果再往下推上线，我第一步会把数据库、缓存、异步任务这几块按实际业务压力拆开，再补分布式锁、链路追踪、模型评测和一套完整的权限体系。不过我得说清楚，现在这个项目验证到的是单机本地部署，上面这些都是我未来的规划，不是已经上线的能力。

**详细解答**：项目的核心是把"不确定的自然语言"转换成"可验证的业务动作"。设计取向是：模型只负责理解和表达，确定性代码负责状态迁移、权限、事务、冲突和幂等。一次请求进来，由统一编排器的单轮入口承接；会话运行层负责从数据库恢复当轮所需的消息、预约草稿、偏好和摘要；预约这类写操作收敛到预约业务服务，走状态机和冲突校验，模型无法绕过它直接写库。一次处理通过流式事件协议返回给前端，事件按 `开始 → 意图 → 进入工作流 → 内容增量 → 完成/失败` 的顺序给出，失败以唯一的失败事件终止，不会伪装成成功。代码依据：`src/application/orchestrator.py`（单轮编排入口 `handle_turn`）、`src/application/session_runtime.py`（会话恢复）、`src/services/appointment_service.py`（预约写入）、`src/application/events.py`（事件封装）。

**连续追问**：你认为这个项目最有技术含量的地方是什么？
答：不是单纯把模型接进来，而是把不确定的输入一步步变成可以验证、可以回滚的业务动作。最见功夫的是多轮预约、跨轮状态恢复、回答要有知识证据约束、以及预约写入这一层的并发和幂等。

## 2. 线下门店为什么需要这样一个系统，它解决了哪些具体问题

**口语回答 · 当前实现**：说实话，这行最累的就是前台。客户常问的就是那几件事——几点开门、什么价、哪个服务好——但每个客户都得从头问一遍，前台就得一遍遍答。约的时候更麻烦，时间、项目、时长、做男做女、有没有指定的服务人员，一堆信息来回确认才约得上，一个没问全就得多轮来回，人累，错也容易出。

这套系统就把"咨询、预约、推荐、记偏好"串成了一条流程：价格和营业时间这种高频问题自动答，预约信息缺什么就补问什么，档期系统自己查，客户的偏好这次记住了下次就用上，商家在后台也能统一看到所有会话和预约，不用再靠脑子记或翻本子。

**口语回答 · 可扩展方案**：往深里做，可以接回访提醒、经营报表，再往后是多个门店一起管；再往前端推，还能在客户没说话之前主动触达，比如短信提醒、回访外呼这些。

**详细解答**：业务痛点归纳为四类——重复咨询、预约信息不完整、人工查档期和匹配服务人员难、客户偏好无法沉淀。典型端到端流程是：创建会话 → 发送消息 → 意图识别 → 路由到预约或咨询工作流 → 预约侧补全字段或咨询侧检索证据 → 生成结果 → 持久化 → 流式返回给前端。后端统一以会话为载体保存这一整段交互。代码依据：`README.md`（业务与流程总览）、`app.py`（FastAPI 入口）、`src/api/chat_handler.py`（入口侧适配）。

**连续追问**：为什么不做成一张表单，反而搞这么复杂？
答：因为用户的表达不稳定，预约前往往还要咨询和推荐，没法用固定表单框住。但关键在最后一步：无论前面多灵活，最终写库前都要回到确定性的领域服务做校验，绝不让模型凭一句话就绕过规则去写库。

## 3. 你投的是后端兼 Agent 开发，这个项目里你主要覆盖哪部分，边界在哪里

**口语回答 · 当前实现**：我的活儿基本都在服务端。往细了说是这几块：会话和状态的管理、Agent 的编排、预约这一整套领域规则、知识库的检索、模型的抽象，还有测试。前端那块我基本只负责配合——按它定的接口和流式协议来对，页面上的业务逻辑、数据库结构、权限边界和分层约定，这些都在后端这一侧，是我说了算的范围。

**口语回答 · 可扩展方案**：如果团队需要，我可以往数据工程、模型评测或者部署这几个方向扩一扩，但前提是先把我现在的后端边界夯实，不能基础没稳就去摊大饼。

**详细解答**：职责边界可以精确到目录来表述：会话持久化在 `src/db/repositories/`；编排在 `src/application/`（含会话运行时、上下文构建、事件封装）；预约领域在 `src/services/appointment_*.py`（领域规则、服务、冲突与幂等）；知识检索在 `src/services/knowledge_*.py`；模型工厂在 `src/config/model_provider.py`；测试在 `tests/` 与 `evaluation/`。面试时用一句话收口——"我主要负责后端与 Agent 核心链路，前端只做协议对接"。

**连续追问**：前端改需求，你后端怎么配合？
答：前端不改后端代码，只改它自己消费的那一层；双方按接口契约和流式协议对齐，事件字段、错误码、字段命名由后端定，前端只要顺着协议消费就行，核心规则不外泄到前端。

## 4. 除了功能本身，你在这个项目里遵循了什么核心设计原则

**口语回答 · 当前实现**：我贯彻的核心原则就一句话：**模型负责理解，代码负责执行**。模型这个环节只处理自然语言的理解、抽取和表达——说白了就是"帮我把话说清楚、把意思拆明白"；但真正落地的那一步，比如状态改没改、有没有权限、事务成不成、会不会冲突、重复请求怎么防，全都在确定性的代码里，用可验证的规则来管。

这么做的好处是不依赖模型的自律。模型就算偶尔说错、写错，它也没权限去动预约库，改不了状态机。所以我的安全边界是放在接口和领域服务这一层，而不是赌模型"这次不会瞎来"。

**口语回答 · 可扩展方案**：等 Agent 变多、动作变复杂，我会给那些高风险的动作加人工确认，或者上策略引擎，让这些写操作要不要执行由明确的规则兜底，而不是让模型自己决定。

**详细解答**：这个原则落到架构上就是调用方向的硬约束：`Web → API → 编排/Agent → 业务服务 → 数据访问 → 数据库`。大模型被限制在编排和 Agent 层，不能绕过业务服务直接写预约表，也不让持久化的时机由模型现编来决定。这样做的收益：一是写操作可以收敛到少数几个可测试的领域服务；二是权限和审计能加在接口与领域服务两点上；三是模型整体替换不会破坏业务规则。代码依据：`README.md` 的架构约束节、`src/services/`（领域规则）、`src/db/`（数据访问）。

**连续追问**：为什么不能让模型直接操作数据库？
答：写库涉及事务、冲突、幂等和权限，这些要求"确定性"，而模型输出天然不确定。一旦模型直接写库、输出又不可控，可能绕过状态机、产生重复写入或越权操作。把模型挡在写操作之外，是 Agent 工程里最重要的边界之一。

## 5. 这个项目大致的技术栈和选型理由是什么

**口语回答 · 当前实现**：技术选型主打"本地优先、轻依赖"。后端用 FastAPI 出接口、也负责流式响应，数据存 SQLite，配合 SQLAlchemy 做访问；知识库的向量检索用 FAISS；模型不写死某一家，而是通过一个统一工厂来适配不同厂商。前端是服务端渲染的模板加原生 JavaScript，用 SSE 实时消费后端推来的流式事件。

为什么这么选？因为项目还在二次开发和验证阶段，我要的是单机就能把全流程跑通，方便联调也方便测试，不想一上来就被基础设施拖住。等规模上来了再考虑更重的方案。

**口语回答 · 可扩展方案**：真要上线，我会把 SQLite 换成 PostgreSQL，引入异步任务队列和共享缓存，模型调用收到统一网关后面，再补上可观测性。这些都是有明确触发条件的，不是为炫技而拆。

**详细解答**：完整技术栈为：Python、FastAPI/Uvicorn（接口与 SSE）、SQLAlchemy + SQLite（ORM 与本地持久化）、FAISS/NumPy（向量检索）、Jinja2 + 原生 JS（页面）、Pytest（测试）。模型接口兼容 LangChain 风格的 Chat Model，方便把不同厂商的对话模型和向量模型接进同一个工厂。选型取舍上：SQLite 保证零运维、单文件、事务支持好，够本地原型用；FAISS 轻量、内存可放得下演示语料；SSE 比 WebSocket 更简单且契合"服务端单向流式推送"的聊天场景。代码依据：`requirements.txt`、`README.md` 技术栈节、`src/config/model_provider.py`（模型工厂）。

**连续追问**：SQLite 能支撑生产吗？
答：单实例、低并发、本地优先场景完全够用。一旦出现多实例部署、高并发写入或需要更强的并发控制，就得迁 PostgreSQL。这个"本地原型够用 / 生产要升级"的边界，我会主动讲清楚，不糊弄。

## 6. 这套系统现在是一个"能用"的产品吗，做到什么程度了

**口语回答 · 当前实现**：我得诚实说，它现在是**本地优先的原型**，不是已经上线能直接营业的产品。功能主干是闭环的——会话能记住、编排能跑、预约这套领域规则、知识库的发布和检索、偏好管理、商家后台、还有整套离线测试，都通了，全量自动化测试稳定通过。

但要分清：目前默认是在 Fake 模型模式下验证的，也就是用模拟模型把整个流程和接口契约跑通，证明"这个设计是通的"；真实模型的质量、多进程下知识库的一致性、还有生产级的鉴权，这三块还没加固。所以我的说法是"可验证的流程早已闭环，线上那种可靠性还没到"，这两件事我得分清楚讲，不混在一起。

**口语回答 · 可扩展方案**：真上线前，我至少要补：真实模型的评测、完整身份权限、分布式并发控制、数据脱敏和备份、可观测性，再考虑接外部渠道。这是一条清晰的、有顺序的路径，不是空话。

**详细解答**：可以引用的客观事实包括——全量自动化测试稳定通过（离线、不依赖真实模型）；`evaluation/` 提供知识库评测运行器，能跑分类、抽取、召回和回答质量的量化指标；`docs/refactoring-plan/` 记录了分阶段路线（如 Phase F 知识管理、Phase G 商家后台）。要反复强调的诚实边界是：**Fake 模式通过与真实语义质量达标是两回事**——前者证明流程和契约，后者需要真实模型 + 评测集 + 人工核验才能下结论。

**连续追问**：既然还没上线，你怎么说明自己的代码质量？
答：有分层依赖约束、稳定的错误码、一套自动化测试、还有可以独立测的领域规则。我会把两件事分开讲——"可验证的工程质量"（这个我有测试和数据撑着）和"未验证的线上能力"（这个我明确标注待做），不拿前者冒充后者。

## 7. 这个项目有前端，你在里面负责多少，它会不会成为你的短板

**口语回答 · 当前实现**：前端在我这儿是个"配合型角色"。页面是服务端渲染的模板加原生 JavaScript，主要做四件事：发消息、存会话标识、实时消费后端推来的流式事件、把知识来源展示出来。真正的业务规则和权限全在后端，前端既不写库，也不能当权限判断的依据。

所以我负责的是接口和流式协议那一侧——前端只要按协议消费就行。面试的短板问题我一般这么应对：我投的是后端，前端这块我说清边界、讲清我这边的工作量，不回避，但也让大家看到我的主战场在后端。

**口语回答 · 可扩展方案**：如果真要做成产品，前端可以重构成前后端分离的独立应用，或者直接接一个现成的对话 UI 组件，只要背靠的接口和流式协议不变，后端完全不用动。

**详细解答**：前端相关代码在 `web/routes.py`、`web/templates/`、`web/static/`；会话标识存浏览器 localStorage，界面靠消费 SSE 事件构建。核心原则一句话：**前端只负责展示与收集，永不作权限来源**——因为页面代码可被篡改，任何权限判断都必须回后端重做。代码依据：`web/`、`src/api/`（流式响应侧）。

**连续追问**：如果前端缓存了会话 ID，换个浏览器还能续上吗？
答：不能直接续上——会话 ID 存在本地浏览器，换机或清缓存就没了。但如果服务端会给同一个真实的用户签发它自己的会话标识，就能跨端恢复。关键点是会话归属校验必须由后端做，前端只是替用户"拿着"那个标识而已。

## 8. 既然是二次开发，你怎么说明你新增的价值，而不是只改了别人的代码

**口语回答 · 当前实现**：我不拿"改了多少行代码"来说事，那没意义。我强调的是我补齐并固化了后端和 Agent 这一条核心链路：统一的会话编排、跨轮预约的补全、预约的整套状态机和对重复请求的处理、回答要有知识证据约束、模型的抽象、还有 Fake 离线测试，每一块都配了对应的自动化测试。

所以我的论据是"我把原本可能比较单薄、或者没闭环的部分，做成了有明确接口、有领域规则、有测试保障的完整链路"，而不是零散地动了几处代码。这个价值是可以拿出来检验的，不是嘴上说说。

**口语回答 · 可扩展方案**：如果时间再宽裕，我会继续补真实模型评测、一套完整的身份体系和多实例下的并发控制，把"流程能跑"再往"生产可靠"推一步。

**详细解答**：可以用"阶段 + 交付 + 验证"的方式把二开工作讲清楚：Phase D 会话与事件协议（会话持久化 + 流式事件协议）、Phase C 预约领域（状态机/冲突/幂等）、Phase E 偏好与摘要（跨轮上下文）、Phase F 知识管理与发布/回退语义、Phase G 商家后台（鉴权与写操作）。每一阶段都有对应的提交粒度、接口契约和测试，`tests/`、`docs/refactoring-plan/` 与 git 历史均可佐证。面试时不要报行数或文件数，改成报"阶段化交付 + 可复现验证"。

**连续追问**：你怎么区分哪些是原始代码、哪些是你新增的？
答：以阶段提交为边界。每个阶段有独立的接口、事件协议、领域规则和测试，我可以按提交粒度一一道来——哪个阶段交付了什么、加了哪些接口、对应的测试在哪，都能对得上，而不是拍脑袋说"这段是我写的"。

## 9. 为什么我要信这个项目有含金量，它和普通的小 Demo 有什么区别

**口语回答 · 当前实现**：关键区别是它不是一个"调通一个对话接口"的小 Demo，而是有一个完整的工程骨架。举个反例：很多 Demo 是"把用户的话直接扔给模型，模型回什么界面就显示什么"——没有会话、没有状态、没有校验。我这个项目把责任拆开了：模型负责理解，代码负责落地；会话能跨轮恢复，预约有一整套状态机和对重复请求的处理，回答必须带知识证据，模型可以整体切换，而且全部能离线测试。

这些是可运行、可验证、有自动化测试撑着的工程能力，而不是"能聊几句"的表面效果。所以我敢说它比小 Demo 更进一步，这也正是二开要展示的价值。

**口语回答 · 可扩展方案**：但要客观，跟成熟产品比它还差一截——没做完整身份、多实例容灾、真实模型评测。这些是我诚实承认的边界，不会拿"原型能跑"去冒充"产品能用"。

**详细解答**：可用"与纯 LLM Demo 的对照"快速建立可信度：会话持久化 vs 无状态记忆；确定性领域流程 vs 全交给模型自由发挥；证据约束回答 vs 模型想到哪说到哪；模型抽象 + Fake 测试 vs 把某家厂商写死；自动化测试 vs 手工点几下。代码依据：`tests/`（自动化验证）、`evaluation/`（评测与离线基线）、`docs/refactoring-plan/`（工程化路线）。

**连续追问**：那它和成熟 SaaS 系统性差多远？
答：主要差五块——完整身份权限、多进程下的知识一致性、真实模型质量评测、可观测性、以及外部渠道接入。这五块我现在是当后续阶段的方案记着，没有伪装成已完成。

## 10. 假设再给你两个月，你会优先推进什么，为什么

**口语回答 · 当前实现**：我第一件想做的就是**真实模型评测**。理由很直接：它决定这套东西"到底能不能放心用"。现在很多环节是在 Fake 模式下验证流程契约的——模型分类准不准、字段抽取得对不对、知识召回率高不高、回答质量行不行，这些都还没有真实数据说话。评测过了，下一步再上完整身份权限和多进程一致性。

**口语回答 · 可扩展方案**：往后我会按这个顺序推：先把数据库升级、多实例并发控制做好，再补异步任务、数据脱敏和备份、可观测性，最后才考虑接外部渠道。每走一步我都先稳住契约和边界再做下一步，不会图快乱动。

**详细解答**：优先级排序本质上是一个"先证明可用 → 再保证安全合规 → 再讲并发可靠 → 最后谈规模"的递进：**先证明可用**（真实模型评测）→ **再保证安全合规**（身份/权限/脱敏）→ **再讲并发可靠**（多实例/分布式锁）→ **最后谈规模**（渠道/多门店）。当前 `evaluation/` 已具备评测运行器的雏形（分类、抽取、召回、回答质量指标），但真实运行还需要接入真实模型和一套带标注的评测集，这一步是最该优先投入的。

**连续追问**：真实模型评测具体怎么做？
答：用带标注的评测集去跑分类、字段抽取、知识召回和回答质量这几个维度，和规则基准、人工结果做对比，统计准确率、命中率这些指标。Fake 模式只能证明接口和流程走得通，是离线契约基线，绝不能拿来当"语义质量达标"的结论。
