# AI Front Desk 面试文档导航

## 推荐组织方式

面试资料建议按照“业务价值 → 系统架构 → 核心流程 → Agent/RAG → 工程质量 → 技术选型”的顺序组织，而不是完全按照面试题出现的顺序排列。

这样做有三个好处：

1. 先让面试官理解项目解决什么问题，再进入技术细节。
2. 预约、Agent、RAG、评估和性能分别形成独立主题，方便应对连续追问。
3. 当前实现、测试验证和后续扩展方案可以在每个主题内部统一说明，避免前后表述不一致。

## 七个主题

### 主题一：项目定位与业务价值

先回答“做的是什么、为什么做、你负责什么”。

建议掌握：

- 项目整体介绍。
- 线下门店为什么需要智能前台。
- 预约系统解决了什么问题。
- 预约系统是不是正在做的项目。
- 二次开发中自己的工作范围和新增价值。
- 当前版本和生产版本的边界。

对应题目：原题 1、2、3，以及项目整体题库 1、2、3、6、8、9。

推荐开场顺序：

```text
业务痛点 -> AI Front Desk 做什么 -> 用户如何使用 -> 我负责什么 -> 当前做到什么程度
```

### 主题二：系统架构与模块划分

这一部分回答“系统怎么拆、各模块怎么协作、为什么这样拆”。

建议掌握：

- Web、API、Application、Agent、Service、Repository、Database 的职责。
- 模块化单体为什么适合当前阶段。
- 应用层为什么要统一编排。
- 模型层和业务领域层如何隔离。
- 为什么模型不能直接写数据库。
- 会话、消息、预约草稿和偏好的状态边界。

对应题目：原题 4，以及项目整体题库 4、5、后端与 Agent 试读版 2、3、10。

核心主线：

> 模型负责理解和表达，应用层负责编排，领域服务负责业务规则，Repository 负责持久化。

### 主题三：预约业务与状态机

这是项目最能体现业务落地能力的主题，建议重点准备。

建议掌握：

- 用户如何通过自然语言发起预约。
- 多轮槽位补全和缺字段追问。
- 时间、服务项目、时长、服务人员偏好等字段如何抽取。
- 服务人员档期查询和候选推荐。
- `draft → pending_confirmation → confirmed` 状态机。
- 取消、改约、过期、冲突和幂等。
- 为什么用户确认后才真正写入预约。
- 为什么 Agent 不能直接创建预约。

对应题目：原题 1、2、4、11，以及项目整体题库 D3 系列和后端与 Agent 试读版 6、7。

推荐回答顺序：

```text
自然语言输入 -> 字段抽取 -> 草稿合并 -> 缺字段追问
-> 查档期/推荐 -> 用户确认 -> 事务写入
```

### 主题四：多 Agent 与工作流编排

这一部分回答“为什么多 Agent、Agent 怎么分工、依赖如何处理”。

建议掌握：

- 任务分类 Agent、预约 Agent、咨询 Agent、用户行为 Agent 的职责。
- 为什么不把所有能力放进一个 Agent。
- Agent 之间哪些是串行依赖，哪些可以旁路执行。
- 多 Agent 如何共享状态和上下文。
- 如何避免循环调用和状态污染。
- 单 Agent 与多 Agent 的优势、成本和适用场景。
- 规则优先、模型兜底的路由策略。

对应题目：原题 7、8、9、15，以及项目整体题库 D2 系列和后端与 Agent 试读版 4、5。

核心判断标准：

> 只有在业务边界、工具权限、状态或评估目标明显不同的情况下，才拆成独立 Agent。

### 主题五：RAG、知识库与向量检索

这一部分是 RAG 追问的完整链路，建议统一背一条数据流。

建议掌握：

- 是否使用知识问答功能。
- SQLite 和 FAISS 如何配合存储。
- `KnowledgeDocument` 保存什么字段。
- 文档草稿、发布、归档和索引版本。
- 为什么使用 FAISS，以及和 Chroma、pgvector、Milvus、Qdrant 的比较。
- 当前项目如何根据场景做分块。
- 相似度阈值、关键词预过滤和证据元数据。
- 没有可靠依据时如何拒答。
- 为什么不能只依赖 Prompt 防止幻觉。

对应题目：原题 4、5、5.1、13，以及项目整体题库 D4 系列和后端与 Agent 试读版 8。

推荐统一表达：

```text
SQLite 保存正文和治理元数据
-> Embedding 转向量
-> FAISS 做相似度检索
-> document_id 回查数据库
-> published/阈值过滤
-> RetrievedEvidence 注入 Agent
-> 带来源回答或确定性拒答
```

### 主题六：评估、性能与 Agent 质量

这一部分回答“你怎么证明系统有效、快、可靠”。

建议掌握：

- RAG 的 Hit Rate、Recall@K、引用完整性和拒答率。
- 预约 Agent 的意图准确率、字段 Precision/Recall、任务完成率。
- 冲突拦截、幂等正确率、错误预约率和人工接管率。
- P0 高风险样本的零容忍标准。
- Fake 模式能证明什么，不能证明什么。
- Agent 是否具备记忆、学习和反思能力。
- 首 token 延迟和完整预约耗时的区别。
- 如何按阶段打点并统计 P50/P95。

对应题目：原题 6、10、11、12，以及项目整体题库 D5、D6 和后端与 Agent 试读版 8、9。

核心边界：

> Fake 模式验证流程和契约，真实模型评测验证语义质量；两者不能混为一谈。

### 主题七：技术选型与演进方案

最后准备技术选型，适合面试官从项目细节继续追问。

建议掌握：

- 为什么使用 LangChain，而不是 Semantic Kernel。
- 为什么使用 FastAPI、SQLite、FAISS 和 SSE。
- 为什么当前采用模块化单体，而不是一开始拆微服务。
- 什么时候从 SQLite 迁移到 PostgreSQL。
- 什么时候从 FAISS 迁移到 pgvector、Qdrant 或 Milvus。
- 生产化需要补充哪些能力：鉴权、审计、分布式锁、可观测性、异步任务和多实例索引一致性。

对应题目：原题 5.1、7、15，以及项目整体题库 5、6、10。

选型回答统一采用三段式：

```text
当前项目为什么选它
-> 它解决了当前阶段什么问题
-> 规模扩大后什么时候换方案
```

## 推荐面试复习顺序

### 第一轮：背主线

1. 一分钟项目介绍。
2. 预约系统完整流程。
3. 项目模块划分。
4. 模型负责什么、代码负责什么。

### 第二轮：准备技术深挖

1. 多轮预约和状态机。
2. 多 Agent 分工和依赖。
3. RAG 存储和 FAISS 选型。
4. LangChain 选型。

### 第三轮：准备可信度追问

1. RAG 如何评估。
2. Agent 如何评价好坏。
3. 首 token 延迟如何测量。
4. Fake 模式和真实模型的边界。
5. 当前项目是否上线、下一步怎么做。

## 统一回答模板

### 介绍项目

> 我做的是一个面向线下服务门店的 AI 前台与智能预约系统，核心是把咨询、预约、服务人员匹配、客户偏好和后续运营串成自然语言交互流程。

### 介绍设计原则

> 模型负责理解和表达，确定性代码负责状态、权限、事务、冲突和幂等。

### 介绍当前阶段

> 当前版本已经完成核心业务和工程链路验证，采用本地优先的模块化单体；真实模型质量、线上性能和多实例部署属于下一阶段加固内容。

### 介绍扩展方案

> 我会先根据真实数据和压测结果确认瓶颈，再决定是否引入 PostgreSQL、独立向量服务、异步任务或分布式锁，而不是提前为尚未出现的规模引入复杂基础设施。

## 文档维护规则

- `智能预约系统面试问答.md` 保持完整、可搜索，不按每次面试记录随意拆分。
- 其他文档用于不同复习深度，不要在多个文件里维护互相冲突的事实。
- 新增题目时先归入七个主题之一，再决定放入口语回答、详细解答还是追问清单。
- 涉及“已实现、已验证、可扩展、已上线”的表述，统一以当前代码和测试为准。
- 延迟、真实模型质量和生产能力没有实测证据时，不填写虚构数字。
