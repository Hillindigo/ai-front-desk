## 一、项目定位与业务价值

### 1. 简单介绍你的项目智能预约系统，怎么去做的？

#### 口语回答

我参与的是一个面向线下服务门店的 AI 前台与智能预约系统，项目目标是把咨询、预约、服务人员匹配、客户偏好和后续运营串成一条自然语言交互链路。用户不需要填写复杂表单，直接说“我想预约明天下午的肩颈放松”，系统就能识别意图并进入相应流程。

预约场景下，系统会从用户表达中提取服务项目、时间、时长、性别偏好和指定服务人员等信息；信息不完整就针对性追问，信息完整后查询档期并生成预约摘要。用户确认后，系统再通过确定性的预约领域服务完成冲突校验、状态迁移和幂等写入。

我在这个项目里重点负责后端和 Agent 核心链路，采用“模型负责理解和表达，代码负责业务执行”的设计。后端使用 FastAPI，数据层使用 SQLAlchemy 和 SQLite，知识问答使用 Embedding 加 FAISS，Agent 通过 LangChain 兼容接口接入模型，并通过 SSE 实现流式交互。

#### 详细解答

一次预约请求大致经过以下步骤：

1. 用户通过会话接口发送自然语言消息。
2. 会话编排器校验会话，并把用户消息持久化。
3. 系统进行意图识别，判断是预约、咨询还是其他请求。
4. 预约工作流调用预约 Agent，抽取预约字段。
5. 将本轮抽取结果和当前会话中的预约草稿合并。
6. 如果缺少字段，生成针对性的追问；如果信息完整，查询服务人员可用性。
7. 如果需要推荐其他服务人员，则保存等待确认状态。
8. 用户确认后，预约领域服务在事务中执行状态迁移、冲突检查和持久化。
9. 最终通过 SSE 逐步返回结果，同时保存 assistant 消息和相关元数据。

核心工程边界是：

- LLM 不直接写预约表。
- Agent 不绕过领域服务执行关键业务操作。
- 预约状态由代码控制，而不是由模型自由决定。
- 会话上下文和预约草稿需要持久化，不能只放在 Prompt 或进程内存里。
- 预约成功必须以数据库事务完成为准，而不是以模型生成了一句“预约成功”为准。

#### 代码依据

- 统一编排：`src/application/orchestrator.py`
- 预约工作流：`src/application/workflows.py`
- 预约 Agent：`src/agents/appointment_agent.py`
- 预约领域服务：`src/services/appointment_domain.py`
- 数据模型：`src/db/models.py`

## 二、系统架构与模块划分

### 1. 你的项目是如何分块的？

> 笔记要求的核心表述是：“在预约系统中，我根据不同场景使用不同分块策略。”

#### 口语回答

项目整体按照职责分成 Web、API、Application、Agent、Service、Repository 和 Database 几层。Web 负责页面，API 负责协议和鉴权，Application 负责会话和工作流编排，Agent 负责自然语言理解，Service 负责预约、知识库和推荐等业务规则，Repository 负责数据访问，Database 负责持久化。

在预约系统中，我根据不同场景使用不同分块策略。对于预约流程，我不会把一整段聊天记录直接交给模型，而是把当前预约草稿拆成结构化字段，例如时间、项目、时长、人员偏好和确认状态；对于知识问答，我会按知识文档的主题和语义边界组织检索单元，例如营业时间、价格、预约政策、服务介绍分别维护；对于会话历史，则按当前输入、活跃预约、偏好、摘要、最近消息和知识证据分层装配，并按 Token 预算裁剪。

这样做的原因是不同任务对上下文的要求不同：预约更重视结构化状态的完整性，RAG 更重视检索粒度和来源边界，会话上下文则更重视优先级和 Token 预算。

#### 详细解答

预约侧采用结构化槽位：

- 时间。
- 服务项目。
- 服务时长。
- 性别或服务人员偏好。
- 指定服务人员。
- 推荐服务人员。
- 是否等待用户确认。

本轮模型只返回新增或变更字段，Processor 再和已有预约草稿合并。这样用户说“改成后天”时，只更新时间，不会把之前已经确认的项目和时长覆盖掉。

RAG 侧根据知识类型选择检索单元：

- FAQ、价格、营业时间：按问答或单个事实切成较小块。
- 预约政策：按政策条款切分，每块保留完整条件和例外。
- 服务介绍：按服务项目切分，保留项目名称、适用场景、时长和注意事项。
- 长篇运营文档：按标题层级和语义段落切分，必要时保留少量重叠。
- 地址、电话、营业规则：优先维护为结构化字段，RAG 作为补充说明。

当前原型以 `KnowledgeDocument` 作为主要检索单元，保存正文、分类、关键词和 embedding，并由 FAISS 检索。严格来说，当前代码没有复杂的自动长文档切分器，因此面试中应区分“场景化分块设计”和“当前文档级实现”。

`ContextBuilder` 按以下优先级组装上下文：

```text
当前输入
> 活跃预约事实
> 待确认动作
> 长期偏好
> 会话摘要
> 最近消息
> RAG 证据
```

当 Token 超过预算时，优先裁剪知识证据，再裁剪较旧的消息、摘要和偏好；当前输入、活跃预约事实和待确认动作不能被普通裁剪丢掉。

#### 代码依据

- 目录分层：`src/api/`、`src/application/`、`src/agents/`、`src/services/`、`src/db/`
- 上下文装配：`src/application/context_builder.py`
- 知识单元：`src/db/models.py` 中的 `KnowledgeDocument`
- 预约字段抽取：`src/agents/appointment/input_parser.py`

## 三、预约业务与状态机

### 1. 介绍一下预约系统

#### 口语回答

预约系统主要解决线下门店预约过程中信息不完整、人工查档期效率低和容易重复预约的问题。用户可以用自然语言描述需求，系统会逐步收集服务项目、时间、时长和服务人员偏好，并在信息完整后查询档期。

我把预约系统分成两部分：一部分是 Agent 交互层，负责理解用户表达、字段抽取、追问和确认；另一部分是预约领域层，负责服务目录、服务人员档期、预约状态、时间冲突、幂等和持久化。前者可以使用模型，后者必须使用确定性代码。

预约状态主要是 `draft`、`pending_confirmation`、`confirmed`，另外还有 `cancelled` 和 `expired`。草稿阶段可以信息不完整，待确认阶段表示系统已经准备好但还没有最终落单，只有确认成功后才占用正式档期。

#### 详细解答

预约的核心字段包括：

- `service_type/project`：服务项目。
- `start_time`：预约开始时间。
- `duration_minutes`：服务时长。
- `technician_id`：服务人员。
- `conversation_id`：会话归属。
- `user_id`：用户归属。
- `status`：预约状态。
- `idempotency_key`：幂等键。

多轮预约的关键是区分“本轮增量结果”和“跨轮预约草稿”。本轮解析器只返回本次识别到的字段，处理器再与已有草稿合并。不能让模型每次完整重写草稿，否则可能把已确认字段覆盖成未知值。

核心流程如下：

```text
自然语言输入
  -> 结构化字段抽取
  -> 与预约草稿合并
  -> 判断缺失字段
  -> 针对性追问
  -> 信息完整后查询档期
  -> 用户确认
  -> 领域服务写入
```

预约状态流转如下：

```text
draft -> pending_confirmation -> confirmed
  |              |                 |
  +------------> cancelled <-------+

过期草稿 -> expired
```

预约时间使用半开区间 `[start, end)`。两个预约发生冲突的条件是：

```text
start1 < end2 and start2 < end1
```

因此一个预约 14:00 结束，另一个预约 14:00 开始，两者可以相邻，不会被判定为冲突。

对于网络重试，确认操作支持幂等键。相同的请求重复到达时返回之前的结果，不重复创建；同一个幂等键如果对应不同内容，则返回冲突错误。创建、确认和改约必须经过预约领域服务，并使用事务保护冲突判断和状态写入。多实例部署后，进程内锁不够，需要数据库锁、唯一约束或分布式锁。

“信息完整”和“业务确认”是两个不同状态。信息完整后只生成预约摘要或候选推荐，用户明确确认后才进入 `confirmed`。推荐服务人员只能作为候选事实保存，不能在用户确认前视为已经预约。

#### 为什么不能让 Agent 直接创建预约

预约创建涉及权限、状态、档期冲突、事务和幂等。模型输出存在不确定性，不能让它直接改变业务事实。Agent 只能提出结构化参数，最终是否允许创建，要由领域服务再次校验。

#### 代码依据

- `src/agents/appointment/input_parser.py`
- `src/agents/appointment/appointment_processor.py`
- `src/application/session_runtime.py`
- `src/services/appointment_domain.py`
- `src/services/appointment_service.py`
- `src/api/appointments.py`
- `src/db/models.py`

## 四、多 Agent 与工作流编排

### 1. 为什么设计成多 Agent？

#### 口语回答

我设计成多 Agent，主要是因为预约、咨询和用户行为分析的目标、上下文和风险都不一样。

预约 Agent 需要维护多轮槽位、查询档期和等待确认；咨询 Agent 需要做 RAG 检索、证据约束和引用；用户行为 Agent 负责记录行为、分析偏好和生成回访建议；任务分类或应用层负责任务路由和整体编排。如果把这些能力全部塞进一个 Agent，Prompt 会变长，工具权限会混在一起，状态管理和问题定位都会变困难。

多 Agent 不是让它们自由互相调用，而是通过统一编排器和工作流进行协作。这样可以给不同 Agent 配置不同 Prompt、工具、上下文和评估指标，同时把预约写入、权限、冲突和幂等放在 Agent 之外的领域服务里。

#### 详细解答

主要分工如下：

- Task Classification Agent：识别咨询、预约和其他请求。
- Appointment Agent：预约字段抽取、缺失信息追问、服务人员匹配和确认交互。
- Consultation Agent：知识检索、证据整理和咨询回答。
- User Behavior Agent：记录用户行为、分析偏好和生成回访信息。
- Application Orchestrator：统一处理会话、工作流、事件和异常。

多 Agent 的收益是职责边界清晰、工具权限可隔离、Prompt 更聚焦、评估可以按领域拆分。代价是编排和状态管理更复杂，可能增加模型调用次数和延迟，还需要更完善的日志、Tracing 和失败恢复。

只有当模块存在独立的业务边界、工具权限、状态或评估目标时，才值得拆成独立 Agent。简单任务不必为了追求多 Agent 而强行拆分。

### 2. 有没有涉及同时要调多个 Agent，或者多个 Agent 之间还有依赖关系？

#### 口语回答

有 Agent 之间的依赖和串行关系，但当前核心预约链路不是让多个 Agent 无限制并行调用，而是由编排器按工作流控制顺序。

最典型的串行链路是：先做意图识别，再进入预约或咨询流程。预约流程里先由解析器抽取字段，再由匹配模块查询服务人员，最后由领域服务做冲突和状态校验；咨询流程里先检索 RAG 证据，再把证据交给回答生成器。后一个步骤依赖前一个步骤的结构化结果，所以不能简单并行。

也有可以并行或旁路执行的任务，例如主回答完成后记录用户行为、更新摘要、写运行日志，这些不应该阻塞主流程。当前项目把行为记录和摘要处理设计成旁路，失败时不阻断主对话。

#### 详细解答

串行依赖如下：

```text
用户输入
  -> 意图识别
  -> 选择工作流
  -> 字段抽取/知识检索
  -> 业务校验
  -> 生成回答或执行写入
```

预约中：

```text
InputParser
  -> AppointmentProcessor
  -> TechnicianFinder
  -> AppointmentDomainService
```

咨询中：

```text
ContextBuilder
  -> EvidenceReader / KnowledgeService
  -> ConsultantAgent
  -> 带来源回答
```

行为记录、运行日志、会话摘要和非关键运营统计可以旁路执行，但不能和主流程争夺同一份业务写入事实。如果旁路任务失败，应该记录错误并重试，而不是修改主流程结果。

当前 Agent 之间的依赖由 Application Workflow 和部分兼容回调管理。更大规模时，可以使用显式状态图，为每个节点定义输入、输出、前置条件、超时、重试次数和失败转移。

### 3. 多 Agent 系统和单 Agent 系统最大的区别是什么？彼此有什么优势？

#### 口语回答

最大的区别是任务和决策能力如何组织。单 Agent 通常由一个模型统一理解上下文、选择工具并完成任务，链路简单，开发快；多 Agent 会根据业务职责拆成多个专业角色，由编排器负责路由和协作。

单 Agent 的优势是调用链短、延迟低、状态简单，适合目标单一、工具少、流程不复杂的场景。多 Agent 的优势是职责清晰、权限和工具容易隔离、每个 Agent 可以使用更专门的 Prompt 和评估标准，适合预约、咨询、客户运营这类目标和状态差异很大的业务。

多 Agent 的代价是编排、状态同步、错误处理和观测更复杂，还可能增加模型调用次数和延迟。因此我不会认为多 Agent 天然优于单 Agent。项目采用多 Agent，是因为预约有状态机和写操作约束，咨询有 RAG 证据约束，行为分析又是另一套运营逻辑；如果只是简单问答，单 Agent 反而更合适。

#### 详细解答

| 对比项 | 单 Agent | 多 Agent |
| --- | --- | --- |
| 结构 | 一个 Agent 负责理解、规划和工具调用 | 多个专业 Agent 分工，由编排器协作 |
| 开发成本 | 较低 | 较高 |
| 调用链 | 短，通常延迟较低 | 可能有串行或回流，延迟较高 |
| 上下文 | 集中但容易变长 | 每个 Agent 上下文更聚焦 |
| 工具权限 | 容易混在一起 | 可以按角色隔离 |
| 测试 | 端到端简单，定位问题较难 | 可按 Agent 分开评估，编排测试更复杂 |
| 状态管理 | 相对简单 | 需要显式共享状态和版本控制 |
| 适合场景 | 简单问答、单一任务、工具少 | 多业务域、长流程、权限差异明显 |

一句话总结：单 Agent 更偏向简单和低延迟，多 Agent 更偏向边界、专业化和可维护性，具体选择要看任务复杂度、工具风险、状态规模和团队维护成本。

## 五、RAG、知识库与向量检索

### 1. 你的 RAG 系统中数据库是如何存储的？

#### 口语回答

我的 RAG 不是把所有内容只存到向量库里，而是采用“关系数据库保存原始知识和元数据，FAISS 负责向量检索”的方式。

在 SQLite 的 `knowledge_documents` 表里保存知识正文、标题、分类、关键词、embedding、文档状态、文档版本、来源和发布时间等信息。知识文档默认先进入草稿状态，只有发布后的文档才能进入正式索引。FAISS 根据 query embedding 做相似度检索，检索结果再根据文档 ID 回到数据库读取正文和元数据。

知识库还有 `knowledge_meta` 表保存语料版本等元信息。索引重建时先构建候选索引，成功后再原子替换当前快照；如果构建失败，继续使用旧索引。检索结果会携带文档 ID、相似度、排名和索引版本，最后写入 assistant 消息 metadata，方便展示引用和审计。

#### 详细解答

`KnowledgeDocument` 主要保存：

- `content`、`title`、`category`。
- `keywords` 和 `embedding`。
- `status`：`draft`、`published`、`archived`、`failed`。
- `document_version` 和 `knowledge_version`。
- `source_type/source_label`。
- `created_by/updated_by`。
- `published_at/archived_at`。
- `is_active` 软删除标志。

检索流程是：

```text
用户问题
  -> Embedding
  -> FAISS 相似度搜索
  -> document_id 回查 SQLite
  -> 检查 published 状态
  -> 检查相似度阈值
  -> 生成 RetrievedEvidence
  -> 注入咨询 Agent
```

当前默认最低相关度阈值是 `0.5`，低于阈值的内容不作为可靠证据。正式索引只从 `published` 文档构建，草稿、失败和归档文档不会进入正式回答上下文。

#### 为什么不直接把正文只存 FAISS

FAISS 只解决向量近邻搜索，不适合承载完整的文档治理能力。发布、归档、权限、版本、来源、审计和软删除更适合存储在关系数据库中。因此数据库负责事实和元数据，向量索引负责检索加速。

- 表结构：`src/db/models.py`
- Repository：`src/db/repositories/knowledge_repository.py`
- RAG 服务：`src/services/knowledge_service.py`
- 容器共享实例：`src/application/container.py`

### 2. 为什么使用 FAISS？有没有对比过其他向量数据库？

#### 口语回答

严格来说，FAISS 不是一个完整的向量数据库，而是一个高性能的向量检索库和索引组件。当前项目选择 FAISS，主要是因为项目处于本地优先的验证阶段，知识库规模比较小，核心目标是先把 RAG 的检索、阈值过滤、知识发布和回答引用链路跑通。

FAISS 和 NumPy 集成比较直接，Python 生态成熟，`IndexFlatIP` 可以做精确的内积相似度搜索，不需要单独部署服务，启动时从 SQLite 读取已发布文档并在进程内构建索引，开发和测试成本都比较低。当前项目还利用 FAISS 索引快照做原子替换，重建失败时保留旧索引，能够满足单实例验证阶段的可靠性要求。

我对比过 Chroma、pgvector、Milvus、Qdrant 和 Weaviate 等方案，但目前主要是架构和工程成本层面的对比，没有做统一数据集、统一 Embedding、统一硬件和统一并发条件下的完整横向压测。当前项目的数据量和部署规模还没有达到必须引入独立向量数据库的程度，所以选择了 FAISS。

#### 详细解答

当前选择 FAISS 的原因：

1. 数据规模匹配，门店知识库文档量较小，进程内索引可以满足需求。
2. 部署简单，不需要额外启动独立向量服务。
3. `IndexFlatIP` 对当前数据量可以做精确搜索，避免过早引入近似搜索调参。
4. 和 Python、NumPy、Embedding、SQLite 的技术栈匹配。
5. Fake Embedding 可以生成固定维度向量，测试不依赖网络和外部服务。
6. 可以先构建候选索引，成功后再替换当前快照，失败时保留旧快照。

当前数据流如下：

```text
SQLite：保存正文、标题、分类、状态、版本、来源和 embedding
    |
    v
FAISS：加载 published 文档的 embedding，建立进程内索引
    |
    v
查询向量 -> FAISS 返回位置 -> document_id -> SQLite 回查正文和元数据
```

方案对比如下：

| 方案 | 优势 | 不足 | 当前判断 |
| --- | --- | --- | --- |
| FAISS | 轻量、速度快、无独立服务、适合 Python 本地部署 | 需要自己管理持久化、元数据、过滤和多实例同步 | 当前验证阶段最匹配 |
| Chroma | 上手简单，带集合和元数据能力，适合本地 RAG | 生产规模、并发和运维能力需要进一步验证 | 适合快速 Demo |
| pgvector | 向量和业务数据都在 PostgreSQL，查询和事务统一 | 需要 PostgreSQL，向量检索会增加数据库负载 | 生产结构化数据场景值得考虑 |
| Milvus | 面向大规模向量检索，分布式和扩展能力强 | 部署、运维和数据链路更复杂 | 当前规模偏重 |
| Qdrant/Weaviate | 独立向量服务，过滤、管理和服务化能力较强 | 需要额外服务、网络和版本运维 | 多实例生产可评估 |
| Elasticsearch/OpenSearch | 适合关键词、全文和向量混合检索 | 系统较重，资源和运维成本更高 | 需要混合搜索时考虑 |

更准确的面试表述是：

> 我做过方案层面的技术选型对比，主要比较数据规模、部署复杂度、过滤能力、扩展性和与现有 SQLite 架构的匹配度；但目前没有做正式的统一压测。因此我能确认 FAISS 更匹配当前项目阶段，不能把它包装成在所有场景下都比其他方案快。

如果要做正式对比，需要固定相同的知识文档、Embedding 模型、Top-K、阈值、硬件和并发条件，并统计 Recall@K、P50/P95/P99、索引构建耗时、内存占用、更新延迟和故障恢复能力。

#### 后续什么时候换方案

当知识库规模不适合单进程内存、需要多个实例共享索引、知识更新频繁、需要复杂 metadata 过滤和租户隔离，或者查询并发与可用性要求超过本地索引能力时，我会评估 pgvector、Qdrant 或 Milvus。

### 3. 有没有使用一些知识问答的功能？

#### 口语回答

有，项目中已经接入了知识问答，也就是 RAG。用户询问营业时间、服务价格、服务介绍、预约政策或会员信息时，系统先把问题转成 embedding，再从门店知识库检索相关文档。只有超过相似度阈值、并且处于已发布状态的知识，才会作为证据交给咨询 Agent。

如果知识库没有足够可靠的依据，系统会确定性地拒答或提示用户换一种问法，而不是让模型自己猜。回答中保留文档 ID、相关度、排名和索引版本，前端可以展示来源，后台也可以审计。

所以这个 RAG 不是简单的“向量搜索加 Prompt”，还包括知识文档的草稿、发布、归档、索引版本、阈值过滤、引用和无依据降级。

#### 详细解答

RAG 流程如下：

```text
用户问题
  -> Query Embedding
  -> FAISS 相似度检索
  -> 关键词预过滤和阈值过滤
  -> 只保留 published 文档
  -> 构造 RetrievedEvidence
  -> 放入统一 ContextBuilder
  -> 咨询 Agent 基于证据回答
  -> 保存来源元数据
```

安全边界包括：

- 价格和政策尽量以结构化门店数据为准。
- 没有证据时不能编造。
- 草稿不能作为正式回答依据。
- 归档文档不能继续出现在正式检索结果中。
- RAG 证据不应包含隐藏推理或无关的敏感字段。

- `src/services/knowledge_service.py`
- `src/agents/consultant/knowledge_retriever.py`
- `src/application/context_builder.py`
- `src/application/workflows.py`

## 六、评估、性能与 Agent 质量

### 1. 你的 RAG 系统是怎么去评估系统质量的？

#### 口语回答

我会把 RAG 评估拆成检索质量、回答可靠性和工程稳定性三部分，而不是只看回答是否流畅。

检索侧主要看命中率、Recall@K、相关度阈值和无依据问题的拒答率；回答侧看引用完整性、答案是否被证据支持、是否出现幻觉，以及价格、地址、政策这类高风险信息是否准确；工程侧看已发布文档是否能检索到、归档文档是否泄漏、索引重建失败后旧快照是否还能工作。

当前项目的 `evaluation/` 已经有离线契约评测，包括 `hit_rate`、`citation_completeness`、`refusal_contract_rate`、`old_version_leak` 和 `post_publish_available`，可以先把检索和知识治理的底线跑通。真实模型部分则会在这套基线上继续补充人工标注、事实一致性和回答质量评测。

#### 详细解答

评估主要包括：

1. **检索命中率**：检查 Top-K 是否命中正确主题或文档，可补充 Recall@K、MRR、NDCG。
2. **引用完整性**：证据必须携带 `document_id`、`snippet`、`score`、`rank` 和 `source_version`。
3. **无依据拒答**：没有可靠证据时，系统应确定性提示无法确认，而不是让模型补充。
4. **版本和发布契约**：草稿不能检索、归档不能泄漏、发布后可以检索、重建失败保留旧快照。
5. **真实模型人工评测**：检查答案是否被证据支持、引用是否对应事实、价格政策是否准确、是否答非所问。

Fake 模式只能证明流程和契约，不能证明真实模型的语义质量，因此真实模型评测和人工核验需要单独进行。

#### 评测命令

```bash
python -m evaluation.run_knowledge_eval
python -m evaluation.phase_i_eval
```

- `evaluation/knowledge_eval_cases.py`

### 2. 端到端的延迟是多少？

> 笔记中的定义是：Agent 从用户输入到第一个输出的延迟，也就是首 token 延迟，不是完整预约完成耗时。

#### 口语回答

这道题我会先确认统计口径：如果说的是 Agent 从用户输入到第一个可见输出的延迟，统计的是首 token 延迟；如果说的是完整预约耗时，还要包含字段抽取、档期查询、用户确认和数据库写入，两者需要分开看。

当前版本已经支持 SSE 流式输出，因此我会把首 token 作为核心体验指标，并按请求进入、意图识别、RAG 检索、首次 `assistant_delta`、工具调用、数据库提交和 `run_completed` 分阶段打点。由于实际数值会受模型 Provider、网络和部署环境影响，面试时我不会用 Fake 模式的本地耗时冒充线上指标，而是给出 P50/P95 和具体测试环境。

#### 详细解答

首 token 延迟：

```text
TTFT = 首个可见 assistant_delta 时间 - 请求接收时间
```

完整处理耗时：

```text
E2E = run_completed 时间 - 请求接收时间
```

预约业务完成耗时：

```text
预约完成耗时 = 数据库确认提交时间 - 本轮预约执行开始时间
```

建议记录：

- `request_received`
- `intent_detected`
- `workflow_started`
- `retrieval_started/retrieval_finished`
- `first_assistant_delta`
- `tool_started/tool_finished`
- `db_commit_finished`
- `run_completed/run_failed`

首 token 延迟通常由 API 排队、会话读取、意图识别、上下文构建和首次模型输出准备组成。当前没有在统一真实模型、网络和数据集条件下完成正式压测，因此面试时不填写虚构的毫秒数，而是按场景报告 P50、P95 和具体测试环境。

### 3. 你评价你的预约系统 Agent 好坏的标准是什么？

#### 口语回答

我不会只看回答是否像人，而是从任务完成、业务正确、交互体验和系统可靠性四个方面评估。

任务完成方面，看用户能不能在合理轮数内完成预约；信息抽取方面，看时间、项目、时长和服务人员偏好的字段准确率、精确率和召回率；业务正确方面，看是否错误占用档期、是否出现重复预约、是否绕过用户确认、冲突和幂等是否正确；交互方面，看追问是否针对缺失字段、回答是否清楚、是否能处理用户中途改时间或切换咨询；系统方面，看首 token 延迟、完整耗时、失败率、工具调用成功率和人工接管率。

此外还要设置 P0 级安全和业务样本，例如医疗问题、无关问题、错误时间、冲突预约和重复确认，这些问题不能仅靠平均分掩盖。高风险样本应该零容忍或单独设门槛。

#### 详细解答

评估维度包括：

- **意图和字段抽取**：`intent_accuracy`、`field_precision`、`field_recall`、时间标准化正确率、服务项目识别正确率。
- **预约业务**：预约完成率、平均完成轮数、草稿转确认率、冲突拦截率、幂等正确率、错误预约率和取消改约成功率。
- **RAG 回答**：检索命中率、Recall@K、引用完整性、无依据拒答率、事实一致性和幻觉率。
- **系统体验**：首 token 延迟 P50/P95、完整响应耗时、模型失败率、工具失败率、人工接管率和多轮上下文保持率。

P0 样本要单独设门槛：医疗问题不能被当成普通预约回答；不存在的价格、地址和政策不能编造；冲突时间不能确认成功；用户未确认不能进入 `confirmed`；重复确认不能产生重复预约。

### 4. 你的这个 Agent 项目任务完成得怎么样，有没有去学习 / 反思能力？

#### 口语回答

从工程完成度看，项目已经实现了咨询、预约、知识检索、预约状态管理、客户偏好和回访建议等核心闭环，流程、接口契约和业务规则都有对应验证。下一步的重点不是重新搭流程，而是把真实模型质量、线上性能和运营数据闭环做得更扎实。

项目已经具备受控的业务反馈和记忆能力，但定位上不是自主训练型 Agent。它可以记录用户行为、保存明确表达的偏好、生成会话摘要，并在后续会话中使用这些信息；RAG 知识库也支持发布、归档和版本管理。这属于“持久化记忆 + 业务反馈闭环”。

目前没有让 Agent 根据每次对话自动更新模型参数，也没有让它无限制地自我修改 Prompt 或自动改变业务规则。更准确地说，系统有受控的记忆、评估和改进机制，但没有未经审核的在线学习。

#### 详细解答

当前具备：

- 记录用户预约和咨询行为。
- 保存用户明确表达的长期偏好。
- 生成和恢复会话摘要。
- 对 RAG 知识文档进行发布、归档和版本控制。
- 通过评测脚本发现分类、抽取、召回和拒答问题。
- 失败时保留旧知识索引，不让错误发布污染正式回答。

当前不具备：

- 根据单次对话自动训练模型或更新权重。
- 无审核地修改 Prompt、规则或数据库结构。
- 完全自主的长期规划和无限制反思循环。
- 把用户反馈未经审核直接写成知识库事实。

如果继续扩展，可以采用受控反馈闭环：

```text
对话和结果记录
  -> 失败样本分类
  -> 人工审核和标注
  -> 更新评测集/Prompt/规则/知识库
  -> 离线回归评测
  -> 灰度发布
```

Agent 的反思也应限制在当前任务内，例如检查是否遗漏必填字段、答案是否有证据、工具调用是否成功。反思结果只能触发重试、澄清或人工接管，不能直接绕过业务规则继续写库。

## 七、技术选型与系统演进

### 1. 为什么用 LangChain 不用 Semantic Kernel?

#### 口语回答

我选择 LangChain，主要是因为当前项目是 Python 后端，而且已有代码已经基于 LangChain 的 Prompt、Chat Model、Tool、Agent Executor 和 Runnable 链路展开。它和 FAISS、Embedding、OpenAI 兼容模型的集成比较直接，能快速把预约抽取、工具调用和 RAG 流程串起来，也便于后续切换模型 Provider。

这不是说 Semantic Kernel 不好。Semantic Kernel 在插件、Planner、Memory 和微软生态整合方面也很适合，尤其是 C#、.NET 或 Azure 技术栈的项目。如果团队主要使用 .NET，或者希望和微软身份、Azure 服务深度整合，我会认真考虑 Semantic Kernel。

对我这个项目来说，选型依据是语言栈、已有代码、生态适配和开发成本，而不是单纯认为某个框架一定更先进。无论使用哪个框架，预约状态、冲突校验、权限和幂等都应该由业务代码负责，不能把框架当成业务可靠性的保证。

#### 详细解答

选择 LangChain 的原因：

1. 项目是 Python FastAPI 后端，LangChain Python 生态匹配。
2. 当前代码已经使用 Prompt、Chat Model、Tool、Agent Executor 和 Runnable。
3. Embedding、Retriever、FAISS 和 Prompt 组合比较直接。
4. 可以通过统一 Provider 工厂切换 OpenAI 兼容模型或 Fake 模型。
5. 适合快速验证预约信息抽取、工具调用、RAG 和流式输出。

Semantic Kernel 的优势包括插件和函数调用模型清晰、对微软和 Azure 生态集成较好、适合 C#/.NET 企业技术栈。因此这不是绝对优劣，而是结合语言栈、团队经验、模型适配、流式能力、RAG 支持、可观测性和升级成本做选择。

#### 追问：如果现在重新设计，还会选 LangChain 吗？

我会先做一个小规模 PoC，对比两者在模型调用、工具调用、RAG、流式输出、错误处理和测试方面的真实成本。如果项目仍然是 Python，并且已经有 LangChain 代码基础，我大概率继续使用 LangChain；如果团队切换到 .NET 或深度使用 Azure，则 Semantic Kernel 可能更合适。

#### 当前技术栈与后续演进

当前技术栈的核心取舍是本地优先和低运维：FastAPI 负责接口和 SSE，SQLAlchemy 加 SQLite 负责本地持久化，FAISS 负责向量检索，模型通过 Provider 工厂接入，前端用模板和原生 JavaScript 消费流式事件。这样单机就能把咨询、预约、RAG 和后台流程跑通，方便二次开发和测试。

后续不会一开始就把所有组件拆成微服务，而是根据真实瓶颈演进：如果需要多实例和更强并发，把 SQLite 升级为 PostgreSQL；如果知识库需要共享索引和复杂过滤，再评估 pgvector、Qdrant 或 Milvus；如果有耗时旁路任务，再引入异步任务队列；如果模型调用变多，再增加统一网关、超时、重试、限流和成本统计。

当前方案适合单实例验证阶段，优势是依赖少、部署简单、调试链路短、测试成本低。生产化需要逐步补充完整身份权限、审计和数据脱敏，PostgreSQL、数据库锁和多实例一致性，共享向量服务或 pgvector，异步任务、重试、超时和熔断，以及请求级 Trace、模型成本和质量监控。

统一的演进原则是：先根据数据和压测确认瓶颈，再替换或拆分组件，不为尚未出现的规模提前引入过度复杂的基础设施。

# 一分钟总述版

我做的是一个面向线下服务门店的 AI 前台和智能预约系统。用户可以用自然语言咨询价格、营业时间和服务信息，也可以直接发起预约。系统先做意图识别，预约场景下抽取时间、项目、时长和服务人员偏好，缺字段就继续追问，信息完整后查询档期，用户确认后才通过领域服务完成预约写入。

项目采用模块化单体，按 API、Application、Agent、Service、Repository 和 Database 分层。系统使用多个专业 Agent：预约 Agent 负责多轮字段补全，咨询 Agent 负责 RAG 知识问答，用户行为 Agent 负责偏好和回访，应用层负责统一编排。RAG 使用 SQLite 保存知识正文和元数据，FAISS 做向量检索，只有已发布且达到相关度阈值的文档才能进入回答上下文，没有可靠依据时会确定性降级。

我的核心设计原则是模型负责理解和表达，确定性代码负责状态、权限、事务、冲突和幂等。当前版本已经完成核心流程验证，下一阶段会继续围绕真实模型质量、端到端延迟和生产级多实例能力做加固。

# 面试时必须主动说明的边界

1. 项目定位是本地优先的模块化单体，核心流程已经完成验证，线上化能力属于下一阶段。
2. Fake 模式用于验证流程和契约；真实模型语义质量要通过标注集和人工评测确认。
3. 延迟要先明确首 token 或完整预约耗时，再按 Provider、网络和部署环境给出 P50/P95。
4. 当前知识检索以文档级知识单元为主，复杂长文档可以继续按主题和语义边界增强分块。
5. 系统具备持久化记忆、偏好、摘要和受控反馈，但不做未经审核的在线训练。
6. 多 Agent 由编排器控制，关键预约写入由领域服务完成。
7. SQLite 和进程内 FAISS 适合当前验证阶段，生产多实例需要升级存储、锁和索引一致性方案。

# 八、安全、权限与隐私

### 1. 当前项目的演示身份能否直接用于生产？

#### 口语回答 · 当前实现
不能。当前项目有本地演示身份和商家后台会话，用于验证资源归属、门店范围和后台操作闭环；但它不是完整生产身份系统。核心原则是不相信请求体里的用户、角色和门店字段，而是由服务端解析身份并校验资源归属。

#### 口语回答 · 可扩展方案
生产环境会接入统一认证、角色权限和门店授权，并把资源级校验做成统一服务端策略。

#### 详细解答
`DemoIdentityResolver` 只代表本地演示身份；后台写操作需要服务端会话、权限检查和 CSRF 保护。

#### 连续追问及回答
- **为什么不能相信 user_id？** 客户端字段可被篡改，不能成为授权依据。

#### 代码依据
`src/application/identity.py`、`src/api/admin/`、`PROJECT_MEMORY.md`。

### 2. 如何防止用户修改 conversation_id 越权访问其他会话？

#### 口语回答 · 当前实现
会话和预约资源都要结合当前用户做归属校验，不是拿到 ID 就能访问。预约领域服务会按预约 ID 和用户身份一起读取，未归属时不返回资源。

#### 口语回答 · 可扩展方案
生产环境会把租户、门店和角色范围一起纳入资源访问策略，并记录异常访问审计。

#### 详细解答
会话轮次入口带有 `conversation_id` 和 `user_id`；预约领域服务通过 `_get_owned` 做归属读取。

#### 连续追问及回答
- **为什么不直接返回“无权限”？** 可以统一成不可访问，减少资源枚举风险。

#### 代码依据
`src/application/orchestrator.py`、`src/services/appointment_domain.py`。

### 3. 为什么后台写操作需要 CSRF 防护？

#### 口语回答 · 当前实现
后台使用服务端会话 Cookie 时，浏览器会自动携带 Cookie。CSRF 防护用于防止第三方页面诱导已登录用户发送写请求。

#### 口语回答 · 可扩展方案
继续结合 SameSite、Secure Cookie、来源校验和权限审计，形成多层防护。

#### 详细解答
后台写操作不能只依赖“已登录”，还要校验 CSRF Token；请求体中的角色和门店不参与授权。

#### 代码依据
`README.md` 商家后台 API 说明、`src/api/admin/`。

### 4. 如何防止 Prompt Injection 影响预约？

#### 口语回答 · 当前实现
不把防线只放在 Prompt 上。模型只能理解和提出结构化建议，不能直接写预约表；确认、冲突、幂等和状态迁移都由领域服务校验。知识文档是证据，不是可执行指令。

#### 口语回答 · 可扩展方案
后续会进一步分离系统指令、用户输入和 RAG 证据，并对白名单工具和高风险动作加强确认、审计。

#### 详细解答
Agent 不绕过领域服务；内部 `[THOUGHT]`、`[SIGNAL]` 标记也会在用户可见事件前清理。

#### 连续追问及回答
- **Prompt 防注入够吗？** 不够，最终必须依赖权限隔离和确定性业务校验。

#### 代码依据
`src/application/orchestrator.py`、`src/services/appointment_domain.py`。

### 5. 如何避免内部错误和隐藏推理泄露？

#### 口语回答 · 当前实现
对用户返回稳定错误码和可读提示，不返回堆栈、内部 Prompt 或隐藏推理。日志用于诊断，也要避免记录密钥和完整敏感信息。

#### 口语回答 · 可扩展方案
生产环境补充统一日志脱敏、访问控制、留存策略和敏感字段治理。

#### 详细解答
编排器会把领域异常映射为安全提示；事件清理逻辑阻止内部标记进入 SSE。

#### 代码依据
`src/application/orchestrator.py`、`src/application/events.py`、`src/application/contracts.py`。

### 6. 用户要求删除数据时，需要处理哪些地方？

#### 口语回答 · 当前实现
当前已处理偏好删除后的墓碑、摘要失效和来源消息屏蔽，但不能说完整的数据删除、索引清理和备份治理已经完成。

#### 口语回答 · 可扩展方案
生产方案需要删除登记，联动会话、消息、偏好、摘要、索引、导出和备份恢复，避免旧备份恢复后数据复活。

#### 详细解答
偏好删除不只是改一个状态，还要避免旧摘要和来源消息继续影响后续上下文。

#### 代码依据

# 九、异常处理、并发与可靠性

### 1. 两个用户同时预约同一服务人员和时段，如何避免重复预约？

#### 口语回答 · 当前实现
确认和改约不是普通的先查再写，而是在 `BEGIN IMMEDIATE` 事务内重新检查排班和已确认预约冲突，再写入状态和事件，避免竞态窗口。

#### 口语回答 · 可扩展方案
多实例时迁移到 PostgreSQL，结合行锁、唯一约束或分布式协调。

#### 详细解答
冲突条件是半开区间重叠：`start < other_end and other_start < end`；检查和迁移在同一事务中完成。

#### 连续追问及回答
- **进程内锁够吗？** 只适用于单进程，跨实例必须依赖共享数据库或分布式锁。

#### 代码依据
`src/services/appointment_domain.py`、预约 Repository。

### 2. 幂等键和数据库事务分别解决什么问题？

#### 口语回答 · 当前实现
幂等键处理网络重试造成的同一请求重复执行；事务和冲突检查处理多个请求同时竞争资源。两者不能互相替代。

#### 口语回答 · 可扩展方案
生产中让幂等记录、业务状态和唯一约束保持跨实例一致。

#### 详细解答
相同用户、相同幂等键确认同一预约时返回原结果；同键用于不同预约返回 `IDEMPOTENCY_CONFLICT`。

#### 代码依据
`AppointmentCommandService.confirm()`。

### 3. 模型超时或 Provider 不可用时怎么办？

#### 口语回答 · 当前实现
系统返回稳定失败，不伪造“预约成功”。明确意图可由规则优先分类处理；模型分类失败回退规则结果。完整的表单/人工降级仍是后续产品化能力。

#### 口语回答 · 可扩展方案
按风险降级：预约转人工或表单，咨询无可靠依据时拒答，旁路任务异步重试。

#### 详细解答
`IntentRouter` 在规则命中时不调用 LLM，LLM 异常会回退规则结果；编排失败唯一以 `run_failed` 终止。

#### 代码依据
`src/application/orchestrator.py`、`src/application/intent_rules.py`。

### 4. 模型结构化输出异常，为什么不能直接写预约？

#### 口语回答 · 当前实现
模型可以提取候选字段，但不能直接形成确认事实。必填字段、时间合法性、服务人员可用性和状态迁移都由领域服务再次校验。

#### 口语回答 · 可扩展方案
增加严格 schema 校验、有限重试和澄清问题；但重试不能绕过业务规则。

#### 详细解答
解析器只负责提取；领域命令服务负责字段完整性、可用性、冲突和状态。

#### 代码依据
`src/agents/appointment/input_parser.py`、`src/services/appointment_domain.py`。

### 5. 数据库已提交成功但回复发送失败，以什么为准？

#### 口语回答 · 当前实现
以数据库事务结果为准，不以模型生成的成功文案为准。用户可通过预约查询、幂等重试或会话恢复得到最终业务状态。

#### 口语回答 · 可扩展方案
增加独立操作结果事件和补偿通知，避免展示失败被误解为业务失败。

#### 详细解答
确认事务写入预约状态与预约事件；SSE 只描述当前轮次，不能替代预约实体作为业务事实。

#### 代码依据
`src/services/appointment_domain.py`、`src/application/contracts.py`。

### 6. SSE 断线后如何避免重复执行？

#### 口语回答 · 当前实现
带 `request_id` 的同一轮请求会先查已持久化结果；相同输入可以重放结果，不重复落消息或执行工具；同 ID 不同内容会返回幂等冲突。

#### 口语回答 · 可扩展方案
进一步支持事件游标和 `Last-Event-ID` 续传，但不能把当前结果重放说成完整断点续传。

#### 详细解答
编排入口通过 `get_turn_by_request_id` 做重试去重，重放仍遵守唯一终止事件规则。

#### 代码依据
`src/application/orchestrator.py`、`src/application/events.py`。

### 7. 为什么摘要、行为记录失败不应回滚主预约？

#### 口语回答 · 当前实现
预约和主回复是核心路径，摘要、行为记录属于旁路。旁路失败应记录并后续补偿，不能撤销已经成功提交的预约事实。

#### 口语回答 · 可扩展方案
使用任务队列、重试和死信机制保证旁路任务最终可追踪。

#### 详细解答
编排器对摘要服务、行为记录器和草稿同步单独捕获异常，采用不阻断策略。

#### 代码依据
`src/application/orchestrator.py`。

### 8. 索引重建失败为什么还能继续回答？

#### 口语回答 · 当前实现
知识服务先构建候选索引，成功后原子替换快照；构建失败时保留旧快照。查询只会读旧快照或新快照，不会读到半成品。

#### 口语回答 · 可扩展方案
多实例下要把索引版本和发布状态放到共享存储或专门向量服务中。

#### 详细解答
服务用 `RLock` 保护不可变 `(index, doc_ids, version)` 快照；当前边界是单进程。

#### 代码依据
`src/services/knowledge_service.py`。

### 9. 直接增加多个 Uvicorn workers 有什么问题？

#### 口语回答 · 当前实现
SQLite 写并发、进程内锁和 FAISS 进程内索引不会自动跨进程一致。直接加 worker 会让每个进程维护各自索引，因此当前不能声称已支持多实例。

#### 口语回答 · 可扩展方案
先迁移共享数据库、统一索引与任务协调，再进行压测和故障演练。

#### 代码依据
`src/services/knowledge_service.py`、`PROJECT_MEMORY.md`。
