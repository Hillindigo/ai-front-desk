# 一、后端与 Agent 核心面试题

## 1. 请介绍一下这个项目，以及你在其中做了什么

### 面试官问题

请用一到两分钟介绍一下这个项目，并说明你在二次开发中的工作。

### 口语回答：当前实现

我参与二次开发的是一个面向线下服务门店的 AI 前台系统。它不是简单的聊天机器人，而是把客户咨询、预约、服务人员推荐、客户偏好和人工接管串成了一条可执行的流程。

用户用自然语言提问后，系统先判断是咨询、预约还是其他问题。咨询会先从门店知识库中检索证据，再让模型组织回答；预约会提取项目、时间、时长和人员偏好，信息不完整就继续追问，信息完整后再检查服务人员档期，最后经过用户确认才真正创建预约。

我在二次开发中主要关注后端会话持久化、统一的 Agent 编排、流式事件、预约状态和幂等、知识库发布与检索、模型适配以及 Fake 模式测试。项目当前是本地优先的模块化单体，使用 FastAPI、SQLAlchemy、SQLite、FAISS 和统一的模型接口。前端我只负责配合后端接口和流式协议，面试重点可以放在后端和 Agent 部分。

### 口语回答：可扩展方案

如果继续做线上化，我会把数据库、缓存、异步任务和知识索引服务按照实际压力逐步拆分，并补充分布式锁、链路追踪、模型评测和更完整的权限体系。但当前项目已经验证的是单实例本地部署，我不会把这些扩展方案表述成已经上线的能力。

### 详细解答

项目的核心设计是让模型负责自然语言理解和表达，让确定性代码负责状态、权限、事务、冲突和幂等。这样既保留了 Agent 的灵活性，又避免模型直接执行高风险写操作。

### 连续追问

**追问：你认为这个项目最有技术含量的地方是什么？**

答：不是单纯接入模型，而是把不确定的自然语言输入转换成可验证的业务动作，尤其是多轮预约、跨轮状态恢复、知识证据约束和预约写入的一致性。

## 2. 后端请求如何完成一轮对话

### 面试官问题

用户发送一句“明天下午做肩颈放松”后，系统内部大致经历了什么？

### 口语回答：当前实现

请求进入后，后端先校验会话是否存在、用户是否有权限，以及输入是否有效。然后把用户消息保存下来，再由统一的会话编排器处理这一轮。

编排器会先恢复当前会话的消息、预约草稿、偏好和摘要，再进行意图识别。识别成预约后，就进入预约流程；识别成咨询后，就进入知识库问答流程。预约流程会抽取结构化字段，如果缺少时间或时长就继续追问；咨询流程会先检索知识库，只把可信证据交给模型。

这一轮处理过程中，后端会通过流式事件把状态和回答逐步返回给前端，最后保存 assistant 消息，并发送一个明确的成功或失败结束事件。这样前端能实时显示，后端也能保留完整的会话记录。

### 口语回答：可扩展方案

线上环境可以在这个链路上增加请求级追踪 ID、分布式会话锁、异步任务和更完善的超时控制，方便定位慢请求和恢复中断任务。当前项目的会话锁主要解决单进程内的并发问题。

### 详细解答

当前调用方向是：Web 到 API，到应用编排，再到 Agent 或工作流，然后调用业务服务和数据访问层，最后持久化到数据库并转换为 SSE 事件。

代码依据：`src/application/orchestrator.py` 的 `handle_turn` 是规范的单轮编排入口；`src/application/session_runtime.py` 负责会话恢复；`src/application/events.py` 负责事件封装。

### 连续追问

**追问：为什么用户消息要先保存，再调用模型？**

答：模型调用可能失败，但用户的输入仍然应该保留，便于重试、审计和问题排查。同时下一轮上下文也需要看到这条消息。失败时要把本轮标记为失败，不能伪装成成功回答。

## 3. 为什么采用模块化单体，而不是一开始就拆微服务

### 面试官问题

这个项目为什么采用模块化单体？这样做有什么优缺点？

### 口语回答：当前实现

当前项目采用模块化单体，主要是因为它还处在功能验证和二次开发阶段。咨询、预约、知识库和行为分析虽然职责不同，但调用关系比较紧密，放在一个服务里更容易联调，也方便共享会话、事务和测试环境。

模块化单体并不等于所有代码混在一起。项目内部仍然按接口层、应用层、Agent、业务服务和数据访问层划分职责，规定了调用方向。比如 Agent 不能直接写预约表，必须通过预约业务服务；页面也不能直接访问数据库。

优点是开发和部署成本低，调试链路短；缺点是单个进程的故障影响范围更大，模型调用、知识索引和预约流量也共享资源。当前规模下这个取舍比较合适。

### 口语回答：可扩展方案

如果预约写入、知识检索或模型调用出现明显的独立扩展需求，再按边界拆服务。例如把预约领域独立出来，把知识索引构建放入异步任务，把模型调用放到统一网关。拆分前需要先稳定接口和数据边界，不能只是按目录机械拆分。

### 详细解答

项目的主要模块包括：接口适配、会话编排、任务分类、咨询 Agent、预约 Agent、知识服务、预约服务、偏好服务、Repository 和数据库。模块化单体允许先通过进程内调用验证领域边界，后续再根据压力和团队边界选择服务化。

### 连续追问

**追问：什么时候你会认为应该拆服务？**

答：当模块有独立的扩缩容需求、故障隔离需求、发布节奏或团队边界，并且跨模块通信契约已经稳定时再拆。单纯为了“看起来高级”而拆分，往往会引入网络、事务和运维复杂度。

## 4. 多 Agent 之间是如何分工和路由的

### 面试官问题

请说明项目中多个 Agent 的职责，以及它们如何协作。

### 口语回答：当前实现

项目中主要有任务分类、咨询、预约和用户行为分析几类 Agent。任务分类负责识别用户目标并选择后续流程；咨询 Agent 负责结合知识库回答问题；预约 Agent 负责从自然语言中抽取预约信息、补齐字段和生成确认内容；行为分析 Agent 负责记录行为、提取偏好和生成运营建议。

它们不是互相随意调用，而是由应用层或路由器统一组织。比如用户先说想预约，下一句又问价格，系统可以暂时进入咨询流程，但之前已经收集的预约草稿仍然保留。咨询完成后，下一轮可以继续补充预约信息。

比较重要的一点是，Agent 只负责理解、规划和表达，预约创建、冲突校验和权限检查仍然由确定性业务服务负责。这样能控制 Agent 的副作用。

### 口语回答：可扩展方案

如果 Agent 数量继续增加，可以引入显式的工作流图或状态图，定义每个节点的输入、输出、超时和失败转移。高风险工具还可以增加人工确认或策略引擎，而不是让模型自由决定是否调用。

### 详细解答

当前项目存在早期任务分类入口和新的应用层统一编排。面试时应说明架构演进关系：旧 Agent 负责兼容已有流程，新规范逐步把会话、状态和事件上移到应用层，避免多个入口重复管理状态。

代码依据：`src/agents/task_classification/`、`src/agents/consultant/`、`src/agents/appointment/`、`src/application/orchestrator.py`。

### 连续追问

**追问：如果用户一句话里同时包含咨询和预约怎么办？**

答：当前可以根据主要意图先进入一个流程。更完善的方案是识别多个子意图，先回答价格，再保留预约草稿，或者要求用户确认动作顺序，避免一个分类结果覆盖全部用户目标。

## 5. 为什么要规则优先、模型兜底

### 面试官问题

为什么不是所有消息都直接交给大模型分类？

### 口语回答：当前实现

当前分类采用规则优先、模型兜底。对于“确认预约”“取消预约”或明显的价格查询等表达，规则可以直接识别，就不必调用模型；只有规则没有命中，或者语义比较模糊时，才让模型辅助判断。

这样做主要有三个好处：降低延迟和调用成本；让明确命令的结果更稳定；关键路由更容易测试和审计。即使模型参与分类，它也只是决定进入哪个工作流，不能直接创建预约或修改用户偏好。

我把模型放在不确定的语言理解环节，把最终的业务执行放在确定性代码中。这是 Agent 系统里比较重要的边界。

### 口语回答：可扩展方案

可以继续增加分类置信度阈值、离线评测集、低置信度澄清和人工兜底。对于确认预约、退款或取消等动作，还可以要求模型分类、参数完整、用户确认和领域校验全部通过后才执行。

### 详细解答

`IntentRouter` 先调用规则匹配；规则结果明确且不需要澄清时直接返回，否则调用可选的模型分类器。如果模型调用失败，则回退到规则结果。这样模型不是单点依赖，分类失败也有确定性降级路径。

### 连续追问

**追问：规则会不会越来越复杂，最后难以维护？**

答：会，所以规则只适合处理高确定性、高风险或高频命令，不能把所有自然语言都硬编码。规则达到复杂度上限后，可以使用结构化分类模型或工作流状态约束，并保留规则作为前置拦截和安全兜底。

## 6. 预约 Agent 如何支持多轮补全

### 面试官问题

用户第一次只说“我想做肩颈放松”，系统如何继续完成预约？

### 口语回答：当前实现

系统不会因为字段不全就直接创建预约。预约 Agent 先从本轮输入中抽取项目、时间、时长和人员偏好等字段，再和当前会话里的预约草稿合并。

如果只识别到项目，系统会发现时间、时长等必填信息缺失，于是生成针对缺失字段的追问。用户下一轮补充时间后，系统只更新时间，之前的项目仍然保留；直到信息完整，系统才查询可用服务人员并生成待确认结果。用户明确确认后，才进入正式预约。

草稿状态会和会话绑定，并且可以保存到数据库。这样服务重启或缓存失效后，还能恢复之前的预约上下文。这里模型负责抽取，字段合并、必填判断和状态迁移由代码完成。

### 口语回答：可扩展方案

可以把字段抽取改成带 schema 校验的结构化输出，并加入时间标准化、用户纠错和槽位置信息。对于长流程，还可以使用显式工作流状态保存每个节点和重试次数。

### 详细解答

多轮预约的关键是“本轮增量结果”和“跨轮草稿”分离。本轮解析器只返回本次识别到的字段，处理器再与历史草稿合并。不能用模型每次完整重写草稿，否则可能把已确认字段覆盖成未知值。

代码依据：`src/agents/appointment/input_parser.py`、`src/agents/appointment/appointment_processor.py`、`src/application/session_runtime.py`。

### 连续追问

**追问：用户说“改成后天”，你如何知道改的是预约时间而不是新建预约？**

答：要结合当前会话是否有活跃草稿、上一轮工作流和字段状态判断。更稳定的做法是把当前预约草稿作为结构化上下文传给解析器，并要求输出字段变更意图，再由状态机决定是否允许修改。

## 7. 预约如何保证状态正确、时间不冲突和请求不重复

### 面试官问题

预约确认是写操作，项目如何处理状态、并发冲突和重复提交？

### 口语回答：当前实现

预约流程使用明确的状态机，草稿、待确认和已确认是不同状态，取消和过期也有单独状态。模型不能跳过确认直接把草稿变成已确认，所有状态迁移都要经过预约业务服务。

时间冲突使用半开区间判断。如果一个预约两点结束，另一个两点开始，它们可以相邻；只有真正重叠才冲突。创建或改约时，冲突检查和写入放在同一个事务里，避免两个请求同时检查到空闲后都写入。

对于网络重试，确认操作支持幂等键。相同的请求重复到达时返回之前的结果，不重复创建；同一个幂等键如果对应了不同内容，则返回冲突错误。当前单进程还用会话锁减少同一会话的并发修改。

### 口语回答：可扩展方案

多实例部署后，进程内锁不够，需要数据库行锁、唯一约束或分布式锁，并把幂等键做成数据库唯一索引。数据库也可以从 SQLite 升级到 PostgreSQL，使用更强的并发控制。

### 详细解答

冲突条件是：两个时间区间 `[start1, end1)` 和 `[start2, end2)` 满足 `start1 < end2` 且 `start2 < end1` 时重叠。当前预约领域还定义了稳定错误码，例如预约冲突、状态非法和幂等冲突。

代码依据：`src/services/appointment_domain.py`、`src/services/appointment_service.py`、`src/api/appointments.py`。

### 连续追问

**追问：为什么只做一次“查询有没有冲突”不够？**

答：因为查询和插入之间有竞态窗口。两个并发请求都可能查到空闲，然后同时插入。必须让检查和写入处于同一事务保护范围，并配合锁或约束。

## 8. RAG 知识库如何避免模型胡编

### 面试官问题

如果用户询问价格或营业政策，系统如何保证回答有依据？

### 口语回答：当前实现

咨询流程不会直接把用户问题交给模型，而是先从门店知识库里检索。只有已经发布的文档才能进入正式索引，草稿、发布失败和归档内容不能作为正式依据。检索结果要达到相关度阈值，并保留文档、分数和索引版本等证据。

满足阈值的证据会被放进回答上下文，模型需要根据这些内容回答；如果没有可靠证据，系统就确定性地提示暂时无法确认，而不是让模型凭经验补充价格、地址或政策。回答保存时还会记录证据元数据，方便前端展示来源和后续审计。

所以防止胡编不是只靠提示词，而是靠文档发布状态、检索阈值、无证据降级和证据留痕共同完成。

### 口语回答：可扩展方案

价格和政策这类高风险信息可以优先查询结构化数据库，知识库只补充说明。检索侧还可以增加混合检索、重排序、引用覆盖率评测和知识版本回滚。

### 详细解答

当前链路是：文本向量化、FAISS 检索、阈值过滤、证据注入、模型生成、证据元数据持久化。索引采用候选快照构建，成功后再原子替换；如果重建失败，继续使用上一份可用快照。

代码依据：`src/services/knowledge_service.py`、`src/services/knowledge_publish.py`、`evaluation/`。

### 连续追问

**追问：Fake Embedding 能证明检索效果好吗？**

答：不能。它只能证明索引创建、查询和接口流程能离线运行，不能证明真实语义召回率、回答质量和线上延迟。真实效果需要评测集和人工核验。

## 9. 为什么要抽象模型 Provider，并加入 Fake 模式

### 面试官问题

项目为什么不在 Agent 内直接写死某个模型？Fake 模式有什么价值？

### 口语回答：当前实现

项目通过统一的模型工厂，根据环境配置创建不同的聊天模型和向量模型。Agent 只依赖统一接口，不需要知道具体厂商的 SDK、密钥、模型名称和地址，因此切换模型时不需要改业务代码。

Fake 模式用于离线测试。测试时可以使用不联网的模拟聊天模型和固定维度向量模型，验证分类、预约字段抽取、知识检索流程、流式事件、异常处理和数据库写入，同时不会消耗真实模型额度。

但 Fake 模式只能证明流程和接口契约，不能证明真实模型的理解能力、召回质量、生成质量或实际成本。这个边界需要在面试时主动说清楚。

### 口语回答：可扩展方案

可以在统一 Provider 层继续增加超时、重试、熔断、限流、成本统计和模型版本标签，并建立真实模型回放集，定期评估分类、抽取、召回和回答质量。

### 详细解答

当前支持 Azure、OpenAI 兼容接口以及若干兼容厂商配置，聊天模型和 Embedding 模型可以分别配置。Fake 模型根据输入关键词返回预设结果，避免测试依赖网络和调用次数。

代码依据：`src/config/model_provider.py`。生产配置还需要拒绝 Fake Provider、占位密钥和不安全跨域配置。

### 连续追问

**追问：模型调用失败时应该重试吗？**

答：分类和生成可以做有限次、带退避的重试；但写操作必须先保证幂等，不能因为重试产生重复副作用。超过重试上限后返回稳定错误码，不把内部堆栈直接返回给用户。

## 10. 会话状态如何持久化、恢复和隔离

### 面试官问题

系统如何避免不同用户的对话状态串在一起？服务重启后还能继续预约吗？

### 口语回答：当前实现

项目以会话 ID 和用户 ID 作为状态边界。每个会话有自己的消息、预约草稿、状态和运行锁，获取会话时会校验用户归属。用户 A 的预约字段不会写进用户 B 的会话，也不会依赖一个全局 Agent 保存所有人的状态。

内存中的会话对象只是缓存和运行时加速，数据库才是事实来源。服务重启或缓存失效后，系统会根据会话 ID 从数据库恢复会话元数据和最近消息；预约草稿、正式预约、偏好和摘要也按各自的持久化规则恢复。

同一会话内，当前进程使用异步锁串行处理，避免两轮消息同时修改同一份草稿。这个锁只解决单进程问题，所以我不会说它已经解决了多实例并发。

### 口语回答：可扩展方案

线上多实例部署时，需要把会话锁和幂等判断放到共享数据库或分布式协调组件中，并考虑缓存一致性、会话过期、消息顺序和断线重连。长流程 Agent 还可以把每一步状态存成可恢复的工作流记录。

### 详细解答

`SessionManager` 负责创建、缓存和恢复会话；`ConversationSession` 持有消息、预约草稿和会话锁。数据库访问采用每次调用独立的短生命周期 Session，避免 Agent 处理期间长期占用数据库事务。

代码依据：`src/application/session_runtime.py`、`src/db/repositories/`、`tests/test_session_isolation.py`、`tests/test_session_runtime.py`。

### 连续追问

**追问：为什么不直接把所有上下文放进 Prompt？**

答：Prompt 不是可靠存储，也不适合承载权限、状态和审计信息。数据库保存事实，应用层按优先级构建上下文，模型只接收本轮需要的只读信息。

## 口语表达调整示例

> 用户通过会话接口发送一轮消息，后端由统一的会话编排器处理，再通过流式事件把处理过程和最终结果返回给前端。
