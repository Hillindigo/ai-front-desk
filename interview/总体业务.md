# D1.1 项目解决的业务问题与用户流程

## 面试问题

请介绍 AI Front Desk 按摩房智能预约系统解决的业务问题，以及用户从咨询到预约的完整流程。

## 满分口语回答

我做的是一个面向线下服务门店的 AI 前台系统，核心目标不是简单做一个聊天机器人，而是把咨询、预约、服务人员推荐、客户偏好和后续运营串成一个可执行的流程。传统门店前台经常需要人工回答营业时间、价格和服务介绍，还要反复确认时间、项目、时长以及服务人员偏好，信息不完整时还要多轮追问，人工成本和出错率都比较高。

系统入口是 FastAPI 提供的会话接口和网页聊天页面。用户输入自然语言后，系统先识别意图，再把请求路由到预约或咨询流程。咨询请求由知识库检索证据后回答；预约请求由预约智能体抽取项目、时间、时长和人员偏好，缺少信息就继续追问，信息完整后检查档期、生成推荐或等待确认。预约确认和取消等结果会写入 SQLite，并通过 SSE 增量返回给前端。用户的会话、消息、预约草稿和偏好可以跨轮次恢复，商家则可以在后台查看会话、预约和知识库。

架构上我采用网页、接口、应用编排、智能体、业务服务、数据访问和数据库分层。智能体负责任务理解和流程协作，业务服务负责可测试的业务规则，数据访问层负责和数据库交互，数据库负责持久化。这样既保留了大模型处理自然语言的灵活性，也把预约冲突、幂等、权限和证据阈值等关键规则放在确定性代码里。

## 详细解答

- 业务痛点：重复咨询、预约信息不完整、人工查档期、服务人员匹配困难、客户偏好无法沉淀。
- 典型流程：创建会话 -> 发送消息 -> 意图识别 -> 进入 `appointment`/`consultation`/`unrelated` 工作流 -> 追问或检索 -> 生成结果 -> 持久化 -> SSE 返回。
- 预约关键字段：开始时间、服务时长、项目、性别或人员偏好、服务人员。旧代码中的字段仍使用 `technician`，产品文案统一称为服务人员。
- 当前边界：模拟模式可离线验证流程；真实模型质量、生产鉴权、多进程索引一致性和外部渠道仍需后续加固。

## 关联源码

`README.md`、`app.py`、`src/application/orchestrator.py`、`src/application/session_runtime.py`、`src/api/chat_handler.py`、`src/agents/appointment_agent.py`。

## 追问要点

为什么不直接做一个表单？因为用户表达不稳定，且预约前需要咨询、推荐和多轮补全；但最终写库前必须回到确定性领域服务校验。

# D1.2 五层架构职责与依赖方向

## 面试问题

请说明项目的分层架构，以及各层之间如何依赖。

## 满分口语回答

项目整体可以概括为网页、接口、应用编排、智能体、业务服务、数据访问和数据库几个层次。网页层负责页面和浏览器交互，接口层负责请求协议、流式响应、鉴权、参数校验和错误处理；应用层负责会话运行时、上下文构建、事件和工作流编排；智能体层负责自然语言任务理解，比如分类、咨询和预约；业务服务层承载预约冲突、知识检索、偏好和推荐等可复用业务能力；数据访问层和数据库负责模型、连接以及持久化。

正常调用方向是网页到接口，接口到应用层或智能体，智能体调用业务服务，业务服务通过数据访问层访问数据库。大模型只负责语义理解和文案生成，不能绕过 Service 直接写预约数据。这样的分层让我们可以替换模型、单独测试预约规则，也能把安全边界放在 API 和领域服务中。

当前代码还保留了一些历史兼容依赖，例如旧智能体会调用部分接口或回调，项目图上也能看到循环依赖。这说明架构正在从早期以智能体为中心的模式向应用层统一编排迁移。文档和新接口应优先使用 `src/application`、`src/api` 和业务服务，旧入口只保留适配职责。

## 详细解答

- Web：`web/routes.py`、`web/templates/`、`web/static/`。
- API：`src/api/`，提供会话、预约、知识、偏好和后台接口。
- Application：`orchestrator.py`、`session_runtime.py`、`context_builder.py`、`events.py`。
- 智能体：`src/agents/`，负责分类、预约、咨询、行为分析。
- 业务服务和数据库：`src/services/`、`src/db/`，保存领域规则和数据访问仓库。
- 依赖原则：业务规则不应依赖页面；持久化不应由 LLM 决定；跨轮状态由会话持久化承载。

## 关联源码

`README.md`、`app.py`、`src/application/`、`src/api/`、`src/agents/`、`src/services/`、`src/db/`。

## 面试提醒

不要只背“五层”名称，要能说明每层为什么存在，以及预约冲突、权限、幂等为什么必须在模型之外实现。

# D1.3 FastAPI 启动与系统初始化

## 面试问题

FastAPI 应用如何启动？知识库、服务人员和后台任务在哪里初始化？

## 满分口语回答

入口是根目录的 `app.py`。它先把 `src` 加入 `sys.path`，创建 FastAPI 实例，注册 CORS、Trusted Host、安全响应头、限流和异常处理器，再批量挂载 API 路由与 Web 路由。应用在 startup 事件中调用 `initialize_system`：通过 `get_container()` 获取共享容器并初始化知识库，然后初始化默认服务人员，启动推荐调度服务，最后启动预约草稿清理后台任务。

初始化采用降级启动策略。模型或知识库依赖失败时，应用仍然可以启动，`app.state.initialization_error` 会记录脱敏后的错误信息，聊天能力返回稳定错误提示，而页面和健康相关接口仍可访问。但如果 `APP_ENV=production`，会先执行生产配置校验，配置不合规就拒绝启动，这避免把开发期降级行为误带到生产。

shutdown 时会停止预约清理任务，并关闭共享容器释放数据库和索引资源。这个设计的关键是把长生命周期资源放在容器中统一管理，避免每个请求重复初始化模型、数据库和知识索引。

## 详细解答

启动核心：`create_app()`；初始化核心：`initialize_system()`；清理核心：`shutdown_event()`。

- `SecurityHeadersMiddleware` 和 `RateLimitMiddleware` 使用纯 ASGI，兼容 SSE。
- 知识库初始化会加载或播种 published 文档并构建 FAISS 快照。
- 推荐服务 scheduler 和预约草稿 TTL 清理是后台任务。
- `StaticFiles(directory="web/static")` 提供前端静态资源。

## 关联源码

`app.py`、`src/application/container.py`、`src/services/appointment_cleanup.py`、`src/services/recommendation_service.py`、`src/config/settings.py`。

## 追问

为什么初始化失败不直接让应用挂掉？本地演示和运营页面仍需要可用；但生产配置门禁必须先拦截危险配置。

# D1.4 Web/API/Agent/Service/DB 端到端链路

## 面试问题

请结合一次用户发消息的过程，说明系统从 Web 到数据库的完整调用链路。

## 满分口语回答

以用户发送“明天下午做肩颈放松”为例，浏览器在首页提交消息。规范入口是 `POST /api/v1/conversations/{id}/turns`，兼容入口 `/chat/stream` 会转发到 `ProcessUserInput_stream`。API 层先校验会话、用户归属和输入参数，然后把消息交给会话运行时或编排器。编排器读取当前预约草稿、长期偏好、摘要、最近消息和知识证据，识别意图并发送 `run_started`、`intent_detected`、`workflow_started` 等事件。

如果是预约，预约工作流调用解析器抽取字段，再由预约业务服务和数据访问层做状态与档期校验；如果信息不完整，就产生追问并保存当前草稿；如果信息完整，则生成待确认结果，确认后在事务中写入预约。咨询请求则由知识服务读取不可变的 FAISS 快照，超过可信阈值的证据交给咨询智能体生成回答。最终消息和证据元数据写入 SQLite，并通过 `assistant_delta` 和唯一的 `run_completed` 事件返回前端。

所以大模型负责理解和表达，应用层负责编排，业务服务负责业务规则，数据访问层负责持久化；任何失败都会转换成稳定的 `run_failed` 事件和领域错误码。

## 详细解答

核心链路：`web/routes.py` -> `src/api/chat_handler.py`/会话接口 -> `src/application/session_runtime.py` -> `src/application/orchestrator.py` -> 智能体或工作流 -> 业务服务 -> 数据访问仓库/SQLite -> SSE。

## 关联源码

`web/routes.py`、`src/api/chat_handler.py`、`src/api/appointments.py`、`src/application/events.py`、`src/application/orchestrator.py`、`src/services/appointment_service.py`、`src/db/repositories/`。

## 关键设计

事件只描述当前轮，跨轮预约状态由持久化草稿承载；隐藏的 `[THOUGHT]`、`[SIGNAL]` 不进入用户事件流。

# D2.1 任务分类智能体的总控职责

## 面试问题

任务分类智能体在多智能体系统中承担什么职责？

## 满分口语回答

任务分类智能体是早期的流程入口，职责是先判断用户请求属于预约、咨询还是其他问题，再把请求交给对应的处理流程。它会协调状态管理、任务判断、请求路由、无关问题处理和结果流式传递，并通过回调支持预约流程与分类流程之间的回流。对应的代码类名是 `TaskClassificationAgent`，但面试口头表达时我会重点讲它的职责，而不是反复背类名。

它同时提供普通调用和流式调用两种方式。分类结果会先被归一化，再更新当前会话状态，最后路由到预约、咨询或其他问题处理流程。预约过程中如果用户突然询问价格，预约流程可以把当前问题交回分类流程，由咨询流程回答；回答结束后，原来已经收集的预约信息仍然保留，不会因为临时切换话题而丢失。

当前项目又增加了 `src/application/orchestrator.py` 和会话运行时，说明新架构正在把会话和事件编排上移到应用层。面试时我会说明：这个分类智能体属于早期兼容入口，新的规范会话入口由应用层统一编排，两者不是重复创建两个总控。

## 详细解答

- 初始化依赖：模型、共享状态、分类器、路由器、无关处理器。
- `classify_task_stream`：逐 token 传递分类和下游响应。
- 回流：`handle_unrelated`/`handle_unrelated_async` 重新分类。
- 状态：`SharedState` 记录当前工作阶段，避免流程跳转丢失上下文。

## 关联源码

`src/agents/task_classification_agent.py`、`src/agents/task_classification/`、`src/application/orchestrator.py`。

## 追问

为什么不让每个智能体自己判断？会造成重复分类、状态不一致和路由逻辑分散；中心化入口更容易审计，但复杂度上升后应由应用层统一编排。

# D2.2 任务判断与流程处理如何分工

## 面试问题

任务判断模块和流程处理模块如何分工？

## 满分口语回答

我把“判断用户想做什么”和“执行具体流程”分开。前者只负责把自然语言映射成有限的任务类别，不直接修改预约或咨询数据；后者负责接收判断结果、更新当前状态、处理异常、调用对应业务流程，并提供普通和流式两种接口。这样分类提示词可以独立替换，流程测试也可以使用模拟模型完成，不必真的调用下游流程。对应的代码名称分别是 `TaskClassifier` 和 `ClassificationProcessor`。

在实际系统中，分类结果不能完全信任模型。类别需要归一化，未知类别应进入 other 或错误兜底；真正的预约创建仍由预约领域服务做最终校验。当前 `FakeChatModel` 通过“只返回类别英文名”的提示匹配 appointment/query/other，测试可以离线覆盖路由流程。

## 详细解答

- `TaskClassifier`：模型调用、类别解析和分类提示。
- `ClassificationProcessor`：状态更新、智能体调用、流式内容透传、重置。
- `StateManager`：保存当前共享状态和会话阶段。
- 测试重点：分类正确、未知输入、下游异常、回流和状态不串会话。

## 关联源码

`src/agents/task_classification/task_classifier.py`、`classification_processor.py`、`src/config/model_provider.py`、`tests/test_task_classification_agent.py`。

## 常见误区

不要说“分类器决定预约成功”。分类器只决定走哪条工作流，预约成功取决于参数完整性、可用性、事务和冲突规则。

# D2.3 多智能体之间的状态共享

## 面试问题

多个智能体之间如何共享状态？如何避免不同会话互相污染？

## 满分口语回答

早期智能体层通过共享状态和状态管理器保存当前任务阶段，例如正在分类、预约或咨询。分类入口会把同一个状态管理器传给路由器和处理器；预约流程需要把无关问题交回分类流程时，先更新当前阶段，再继续处理。这些概念在代码中对应 `SharedState`、`StateManager` 和 `StateEnum`。

但共享状态不能做成全局变量。当前项目的新规范是以 `conversation_id` 为边界，把消息、预约草稿、摘要和偏好持久化到 SQLite，由 `SessionRuntime`/`ContextBuilder` 在每轮读取并生成上下文。Agent 内部的共享状态只服务当前运行，不承担跨用户持久化。测试中有会话隔离检查，确保用户 A 的预约字段和用户 B 不串线。

因此我会把状态分为三类：瞬时编排状态、会话历史状态和领域持久化状态。瞬时状态可以在内存里；会话和预约事实必须由数据库承载；长期偏好需要显式来源、可修改和可删除。

## 详细解答

- `SharedState`：当前智能体流程状态，对应代码中的共享状态对象。
- `StateManager`：读写状态、重置和暴露当前信息。
- `conversation_id`：持久化边界。
- 数据库状态：预约 draft、messages、preferences、summary。

## 关联源码

`src/config/constants.py`、`src/agents/task_classification/state_manager.py`、`src/application/session_runtime.py`、`src/application/context_builder.py`、`tests/test_session_isolation.py`。

## 设计取舍

内存状态快但重启丢失、进程间不共享；持久化状态可靠但需要版本和并发控制，所以两者职责必须分开。

# D2.4 请求路由与流程回流

## 面试问题

请求路由器如何分配任务？不同智能体之间如何回流？

## 满分口语回答

请求路由器会根据分类结果选择预约、咨询或其他问题处理流程，并把当前会话状态传给下游。路由不是一次性转发，因为对话中可能发生意图切换。例如用户先说“预约肩颈放松”，随后追问“多少钱”，预约流程会把这条消息交回分类流程，再转给咨询流程回答。咨询结束后，原来的预约历史仍然保留，下一轮可以继续补充时间。代码中的路由器名称是 `AgentRouter`。

回流必须有边界，否则容易出现无限循环。当前实现通过显式 callback 和状态更新完成回流；新 Application 编排则应进一步记录 run、workflow 和事件，限制同一轮的最大跳转次数，并在异常时输出稳定失败事件。模型只负责建议意图，Router 和领域服务负责真正的控制。

## 详细解答

- 正向：classifier -> router -> appointment/consultant/unrelated。
- 回流：下游 callback -> classification processor -> router。
- 状态保护：回流不清空已收集预约字段。
- 风险控制：最大跳转次数、未知类别兜底、异常转 `run_failed`。

## 关联源码

`src/agents/task_classification/agent_router.py`、`src/agents/task_classification/classification_processor.py`、`src/agents/appointment_agent.py`、`src/application/orchestrator.py`。

## 追问

回流和重新开始不同：回流只是重新识别当前消息，预约草稿和会话上下文仍然存在。

# D2.5 单智能体与多智能体的取舍

## 面试问题

单智能体和多智能体的主要区别是什么？为什么本项目采用多智能体？

## 满分口语回答

单智能体会把意图识别、知识问答、预约字段抽取、档期判断和客户分析都放在一个提示词或工具集合里，早期实现较快，但上下文会变长，工具权限边界不清，错误定位和测试也更困难。多智能体则按业务职责拆分：咨询模块负责知识问答，预约模块负责预约信息补全和流程，用户行为模块负责记录和偏好分析，分类或应用层负责统一编排。

本项目采用多智能体的主要原因是业务边界天然不同，预约有状态机和事务约束，咨询有检索增强生成的证据阈值，行为分析有异步和隐私要求。拆分后可以为不同智能体设置不同提示词、工具和评估指标，也能减少单个智能体的认知负担。

代价是编排复杂、跨智能体状态共享、延迟增加和调试困难。因此我不会为了“多智能体”而拆分，而是只拆出有独立状态、权限、数据或评估目标的模块。对于简单场景，单智能体更划算；当前项目用中心化编排控制复杂度。

## 详细解答

优点：职责清晰、权限隔离、可独立测试、便于替换实现。
缺点：调用次数和延迟增加、状态一致性难、回流可能循环、观测要求高。
判断标准：业务边界、工具风险、上下文规模、独立演进和团队维护成本。

## 关联源码

`src/agents/`、`src/application/orchestrator.py`、`src/application/workflows.py`、`tests/test_orchestrator.py`。

## 真实题

# D3.1 预约智能体的主流程

## 面试问题

请介绍预约智能体如何完成一次预约。

## 满分口语回答

预约智能体是预约流程的主控制器。每轮对话先把用户表达抽取成结构化字段，再合并到当前预约草稿。如果字段不完整，就继续追问缺少的信息；如果用户临时提出无关问题，就把当前消息交回分类流程；如果信息完整，就查找匹配的服务人员并生成待确认结果。代码中的主类是 `AppointmentAgent`，解析器、匹配器、文案生成器和流程处理器分别承担具体职责。

推荐服务人员需要用户确认时，流程会收到 `[SIGNAL]recommendation_pending`，此时不能立即重置；只有真正完成、取消或结束后才恢复分类状态并清空预约状态。当前生产级预约接口已进一步把创建、确认、取消和改约收敛到 `AppointmentService`，在事务中执行冲突校验和幂等处理。因此智能体负责自然语言交互，领域服务负责最终写库。

## 详细解答

流程：解析 -> 合并状态 -> 无关回流/缺字段追问/完整处理 -> 推荐确认 -> 预约持久化 -> reset。
关键状态：`finished`、`awaiting_confirmation`、`appointment_history`。

## 关联源码

`src/agents/appointment_agent.py`、`src/agents/appointment/appointment_processor.py`、`src/services/appointment_service.py`、`src/api/appointments.py`。

## 追问

为什么需要 reset 时机控制？过早 reset 会丢失推荐确认上下文，过晚 reset 会把上一单信息带到下一单。

# D3.2 预约历史字段设计

## 面试问题

预约流程中的预约历史保存哪些信息？为什么这样设计？

## 满分口语回答

早期 `AppointmentAgent` 的 `appointment_history` 保存预约对话中逐步补全的字段，包括 `gender`、`start_time`、`duration`、`project`、`preference`、`technician` 和 `technician_name`。这些字段分别表示性别偏好、开始时间、服务时长、项目、其他偏好以及最终匹配的服务人员。每轮 InputParser 只返回本轮识别到的信息，Processor 再合并到历史中，缺少的字段保持原值，从而支持多轮对话。

需要注意，内存字典只是 Agent 运行态，不能作为可靠订单状态。当前项目通过会话预约草稿持久化跨轮状态，正式预约由数据库模型和 Appointment Service 管理，并使用明确的状态机。字段命名上，代码仍兼容 `technician`，产品层称为服务人员；这是历史数据兼容造成的边界，后续可以通过迁移统一。

字段设计的原则是区分用户事实、模型推断和系统结果。用户说的时间和项目可以进入草稿；推荐出来的 technician 需要标记为候选，不能在用户确认前视为已预约；最终确认则由领域服务写入 confirmed 状态。

## 详细解答

- 输入事实：项目、时间、时长、偏好。
- 推断结果：候选服务人员、缺少字段。
- 业务结果：draft、pending_confirmation、confirmed。
- 生命周期：跨轮保留，完成/取消后清理或归档。

## 关联源码

`src/agents/appointment_agent.py`、`src/agents/appointment/appointment_processor.py`、`src/db/models.py`、`src/services/appointment_domain.py`。

## 常见误区

不要把“推荐了技师”说成“预约成功”，确认和冲突校验之间必须有明确边界。

# D3.3 预约信息的结构化抽取

## 面试问题

预约信息抽取模块如何把自然语言变成预约字段？如何处理模型输出不稳定？

## 满分口语回答

`InputParser` 通过结构化提示要求模型只输出预约 JSON，字段与 `appointment_history` 对齐，例如项目、时间、时长、性别、服务人员偏好、confirmation、info_complete、unrelated 和 missing_info。它先通过 `parse_stream` 收集内部模型输出，再由 `parse_data` 解析 JSON。内部 JSON 不直接流给用户，避免把英文字段和推理标记暴露在聊天页面。

模型输出只能作为候选数据，不能直接写数据库。解析层需要处理 Markdown code fence、空字段、未知值、类型错误和非法 JSON，并将异常转换成可理解的追问或稳定错误。之后 AppointmentProcessor 还要做字段归一化、完整性判断、时间格式校验和业务规则校验。当前 FakeChatModel 用预设 JSON 覆盖完整预约、缺字段、确认、取消和无关请求，保证测试不依赖真实模型。

## 详细解答

解析链路：prompt -> stream 文本 -> `parse_data` -> schema/默认值 -> Processor 校验。
必须区分 `未知`、`None`、空字符串和用户明确否定；confirmation 也不能覆盖已有预约字段。

`src/agents/appointment/input_parser.py`、`src/config/model_provider.py`、`tests/test_appointment_agent.py`。

# D3.4 预约流程对完整和不完整信息的处理

## 面试问题

预约流程处理模块如何分别处理完整和不完整的预约请求？

## 满分口语回答

`AppointmentProcessor` 位于解析和主 Agent 之间。它先把解析结果合并进预约历史，并根据必填字段判断是否完整。缺字段时，它通过 `missing_info` 或历史状态生成下一步追问，保证一次只问最重要的信息，避免用户负担过重。完整时，它调用 `TechnicianFinder` 查找候选服务人员，再由 `MessageBuilder` 生成用户可读的确认文案；必要时发出推荐待确认信号。

完整并不等于可以直接落库。正式 API 还要检查服务项目是否存在、时间范围是否合法、服务人员是否可用、预约状态是否允许转换，并在事务内处理冲突。确认成功后才是 confirmed，失败则保留草稿或返回稳定领域错误。这样 LLM 负责补全体验，Processor 和 Service 负责把自然语言流程转成可控业务流程。

## 详细解答

不完整：保持已收集字段、生成缺失字段追问、保存 draft。
完整：候选匹配、展示摘要、等待确认或进入领域服务。
异常：解析失败给出 parse error，冲突返回 `APPOINTMENT_CONFLICT`，重复确认使用幂等结果。

## 关联源码

`src/agents/appointment/appointment_processor.py`、`technician_finder.py`、`message_builder.py`、`src/services/appointment_service.py`。

## 关键取舍

“完整”是信息层概念，“可确认”是业务层概念，两者不能混用。

# D3.5 推荐确认、无关请求与 reset 时机

## 面试问题

预约推荐确认、无关请求和状态 reset 如何处理？

## 满分口语回答

预约流程有三个容易出错的边界。第一，服务人员推荐只是候选结果，系统会设置 `awaiting_confirmation`，等待用户明确确认；收到 `[SIGNAL]recommendation_pending` 时把 `finished` 改回 False，不能清空历史。第二，用户在预约过程中问价格或营业时间，预约流程通过 `unrelated_callback` 回到分类器，由咨询流程回答，但已经收集的项目和时间继续保留。第三，只有预约真正完成、用户取消或明确结束时才重置；过早重置会导致确认时找不到上下文，过晚重置会污染下一次预约。

当前规范会话 API 把这些状态进一步持久化为预约草稿和事件。事件只记录当前 run，不能靠事件重放恢复业务状态。reset 本质上是状态机迁移，而不是简单清空 Python 字典，所以生产实现要配合数据库事务和并发控制。

## 详细解答

- 推荐：候选 -> pending_confirmation -> confirmed/cancelled。
- 无关：当前消息重新分类，不丢已有草稿。
- reset：终态之后执行；异常一般保留可恢复状态。

## 关联源码

`src/agents/appointment_agent.py`、`src/agents/appointment/appointment_processor.py`、`src/application/events.py`、`src/services/appointment_domain.py`。

## 面试提醒

重点说“推荐不等于确认”“回流不等于重置”“事件不等于状态源”。

# D4.1 强结构数据不分块策略

## 面试问题

按摩房项目中哪些数据不适合做普通文本分块？为什么？

## 满分口语回答

服务项目、营业规则、预约政策、服务人员和档期这类数据具有明确结构，不能简单把它们当成长文章按字符切块。比如价格、时长、状态和服务人员性别是字段级事实，切开后可能出现“价格”和“项目”分离，模型就会拼错；档期更不能只靠向量相似度判断，而要由数据库和时间区间规则确定。

当前项目把知识文档保留为 content、category、keywords、status、version 等结构化记录，服务人员和预约则走独立 Repository/Service。RAG 只用于检索咨询证据，预约可用性由 AppointmentService 使用半开时间区间和事务冲突校验处理。因此“不分块”不是完全不用 Embedding，而是保留结构化实体作为原子检索单元，必要时把一条完整记录序列化成嵌入文本。

## 详细解答

- 强结构事实：项目价格、时长、营业规则、人员状态、预约状态。
- 处理方式：字段存储、原子记录、确定性查询、规则校验。
- RAG 边界：检索提供证据，不负责最终计算或预约确认。

## 关联源码

`src/services/knowledge_service.py`、`src/services/technician_service.py`、`src/services/appointment_service.py`、`src/db/models.py`。

# D4.2 长文本递归字符分块策略

## 面试问题

长文本进入 RAG 前如何分块？当前项目如何处理分块边界？

## 满分口语回答

长文本分块要兼顾语义完整和检索粒度。通用做法是优先按标题、段落、句子等自然边界递归切分，再用固定 chunk size 和 overlap 控制长度。overlap 可以保留跨块上下文，但不能过大，否则索引膨胀、结果重复。对于本项目，知识管理 API 的文档是以已发布文档为原子索引单元，`KnowledgeService` 当前没有一个独立的 RecursiveCharacterTextSplitter 实现；所以我不会把“递归分块”说成当前已经上线的代码，而会把它作为长文档扩展策略。

当前实现通过 document content、keywords 生成 embedding，发布后构建 FAISS 快照。如果未来接入长篇门店手册，应在发布流水线中完成 chunk 版本化，并保留 document_id、chunk_id、offset、source_version，回答时按 chunk 证据引用，避免草稿和旧版本混用。

## 详细解答

分块原则：自然边界优先、长度上限、适度 overlap、元数据可追溯、版本可回滚。
当前边界：已有知识文档检索，不是完整的递归分块框架。

## 关联源码

`src/services/knowledge_service.py`、`src/services/knowledge_publish.py`、`src/services/knowledge_contracts.py`。

诚实区分“当前实现”和“演进方案”，比硬说用了某个 splitter 更可信。

# D4.3 知识加载、Embedding 与 FAISS 索引

## 面试问题

知识库如何加载、向量化并建立 FAISS 索引？

## 满分口语回答

启动时容器初始化 `KnowledgeService`，先从数据库读取当前门店的文档；空库时播种默认知识，默认状态是 published。构建索引时只读取 published 文档，把正文和关键词拼成 embedding 输入，使用 `embed_input` 生成向量，再创建 FAISS `IndexFlatIP`，同时保存 FAISS 位置到 document_id 的映射。

查询时先生成 query embedding，必要时做关键词预过滤，再搜索候选并应用 `min_score` 阈值、分类过滤和 published 双重校验，最后返回分数、排名、文档 ID 和 `source_version`。发布新知识不会直接修改线上半成品，而是先构建候选索引，成功后通过锁原子替换快照；失败则保留旧快照。这样查询要么读旧版本，要么读新版本，不会读到一半索引。

## 详细解答

流程：DB published -> 文本拼接 -> embedding -> FAISS -> `(index, doc_ids, version)` 快照 -> 检索过滤 -> Evidence。
关键参数：`min_score=0.5`、`max_candidates`、`source_version`。

## 关联源码

`src/services/knowledge_service.py`、`src/services/text_embedding.py`、`src/application/container.py`。

# D4.4 RAG 质量评估指标

## 面试问题

你如何评估按摩房 RAG 系统的质量？

我会把评估拆成检索、回答、业务和安全四层。检索层看 Recall@K、Precision@K、MRR 或命中率，重点确认价格、营业时间和取消政策的正确文档是否进入候选；回答层看答案是否被证据支持、引用是否正确、低分时是否拒答；业务层看咨询解决率、预约字段补全率、冲突误报率和最终预约成功率；安全层看草稿、归档文档是否泄漏，是否出现编造价格、地址或政策。

# D5.1 向量模型的创建与配置

## 面试问题

## 详细解答

支持：azure、openai、qwen、deepseek/zhipu 兼容配置以及 fake。

# D5.2 服务人员专长匹配流程

## 面试问题

系统如何完成服务人员专长匹配？

## 满分口语回答

`find_best_match_indices` 接收目标文本和候选文本列表。它先对所有候选生成 embedding，创建 FAISS `IndexFlatL2` 并加入候选向量，再对目标文本生成 embedding，搜索全部候选，最后返回按距离排序的候选下标。调用方根据下标映射回服务人员，再逐个检查档期。

这里使用的是 L2 距离，返回顺序表示相似度排序，但不是最终推荐结果。真正推荐还要叠加性别偏好、服务项目、指定人员优先级和可用性；如果偏好候选没有空闲，当前逻辑会回退到全部人员。生产优化可以缓存服务人员 embedding，避免每次请求重复调用 Embedding API，并把索引和实体版本绑定。

## 详细解答

空候选返回空；候选向量 -> FAISS -> 目标向量 -> indices -> 业务筛选与档期校验。

## 关联源码

`src/services/text_embedding.py`、`src/agents/appointment/technician_finder.py`。

## 追问

为什么不直接选最相似的人？因为相似不代表当时有空，也不代表符合用户明确性别和项目偏好。

# D5.3 服务人员画像与推荐

# D5.4 Embedding 缓存与性能成本

## 面试问题

Embedding 调用有哪些成本？项目如何优化服务人员推荐性能？

## 满分口语回答

# D7.4 首字延迟与完整响应延迟

## 面试问题

如何定义和优化首字延迟与完整响应延迟？

## 满分口语回答

我会把端到端延迟拆成请求排队、会话加载、意图分类、检索、工具或数据库调用、模型首段输出和完整响应几个阶段。首字延迟是用户提交后到收到第一段可见回答的时间；完整响应延迟是收到运行完成事件的时间。流式输出主要改善感知延迟，不会自动减少总耗时。

## 详细解答

指标：首字节时间、首个可见片段时间、完整响应时间、模型调用次数、检索增强生成命中率和 P95 延迟。
风险：把模拟模式或本地单进程数据当成生产性能结论。

# D9.1 FastAPI 与模型适配组件的选型

LangChain：消息/模型/Embedding 抽象和 provider 适配。
边界：业务状态机、权限、事务和审计不交给框架或模型。

# D9.2 模型供应商工厂与模拟模式

## 面试问题

模型供应商工厂如何设计？模拟模式解决什么问题？

## 满分口语回答

`create_chat_model` 和 `create_embedding_model` 读取环境变量，根据 provider 返回具体实现。Chat 支持 Azure、OpenAI-compatible、Qwen、DeepSeek、Zhipu 等配置；Embedding 也可以独立指定 provider、模型、key 和 base URL。调用方只依赖 LangChain 的统一接口，所以切换供应商不需要修改 Agent。

模拟模式是测试隔离的关键：设置 `MODEL_PROVIDER=fake` 后返回模拟聊天模型，设置 `EMBEDDING_PROVIDER=fake` 后返回固定维度的模拟向量模型，不访问网络，也不消耗真实额度。模拟模型按输入关键词返回预约 JSON、分类结果或示例回答，适合验证路由、状态、SSE 和错误契约；它不能证明真实模型的语义质量、召回率或延迟。对应的代码名称是 `FakeChatModel` 和 `FakeEmbeddings`。

## 详细解答

配置工厂 -> 统一接口 -> 智能体；测试工厂 -> 模拟模型 -> 离线可重复。
切换模型后需重新检查提示词、JSON 解析、向量维度和索引版本。

## 关联源码

`src/config/model_provider.py`、`.env.example`、`tests/conftest.py`、`requirements.txt`。

# D9.3 测试策略与模拟模型边界

## 面试问题

项目如何测试智能体、检索增强问答、预约流程和接口？

## 满分口语回答

测试分四层。单元测试验证解析器、状态机、时间区间、证据阈值和偏好规则；集成测试使用临时 SQLite 验证 Repository、Service 和事务；API/验收测试验证会话、预约、SSE、后台权限和前端契约；评测测试使用知识 case 验证检索命中和无依据拒答。

# D9.4 鉴权、门店隔离与隐私边界

## 面试问题

AI Front Desk 如何处理鉴权、门店隔离、CSRF 和客户隐私？

## 满分口语回答

系统把客户身份和商家运营身份分开。客户会话查询必须校验 conversation_id 与 user_id 归属；商家后台通过服务端 session Cookie 解析身份，再按 store membership 和 RBAC 权限访问资源。写操作使用 CSRF token，客户端提交的 user_id、role、store_id 不能作为权限来源。安全中间件还提供 Trusted Host、CORS、响应头、限流和错误脱敏。

知识库正式回答只读 published 文档，草稿和归档不进入索引；偏好删除使用 inactive、tombstone、摘要失效和来源消息屏蔽，防止旧缓存复活。日志和事件不能记录隐藏推理、API key 或不必要的 PII。当前项目已经有本地模拟模式的安全和隐私测试，但真实生产仍需接入身份提供商、密钥管理、备份删除重放、多进程部署和审计告警。

## 详细解答

边界：身份由服务端解析；授权由角色/门店/资源共同决定；隐私删除要覆盖所有来源。
测试重点：越权、跨店读取、CSRF、错误回显、草稿泄漏、已删除偏好复活。

## 关联源码

`src/api/admin_auth.py`、`src/api/core/security.py`、`src/application/identity.py`、`src/services/customer_privacy.py`、`tests/security/`、`tests/privacy/`。

# D9.5 当前实现边界与生产演进

## 面试问题

如果把当前原型上线，还缺哪些关键工作？

## 满分口语回答

当前项目已经具备本地模拟模式下的会话、咨询、预约、知识发布、商家后台和安全测试闭环，但它仍是本地优先原型。上线前我会优先补齐四类工作：第一是真实模型评测、提示词版本、超时、重试、降级和成本监控；第二是 PostgreSQL、正式 migration、多进程会话和知识索引一致性；第三是接入真实身份、密钥管理、审计、备份恢复和 PII 删除；第四是把主动推荐的生成、落库、发送、频控和退订闭环完成。

## 详细解答

已实现：模拟流程、SQLite、SSE、检索增强生成发布治理、预约状态机、后台 RBAC 基础。
待加固：生产 DB、多进程、真实 LLM 质量、主动推荐发送、外部渠道、隐私/备份、可观测性。
