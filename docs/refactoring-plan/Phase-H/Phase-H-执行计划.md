# Phase H 执行计划：Web 渠道产品化与买家—商家闭环

> 文档状态：任务计划，待 H0 基线与契约锁定  
> 阶段目标：在现有会话、预约、知识和商家后台边界上，完成一个可恢复、可验收的独立 Web 买家端，并与商家后台跑通“咨询—预约—管理—人工接管”闭环。  
> 当前分支：`dev`  
> 适用范围：买家 Web、商家 Web 工作台、Web API/事件契约、端到端验收  
> 不包含：第三方渠道、通用渠道适配框架、生产级身份系统、PII/备份/多进程和真实模型质量建设

---

## 0. 阶段定位与完成目标

Phase H 不是重新建设知识库、预约领域或商家权限，而是把 Phase B～G 已形成的服务端边界变成一条真实可操作的 Web 产品链路：

```text
买家 Web
  → 会话与知识咨询
  → 预约信息收集与确认
  → 预约领域服务写入
  → 商家后台查看同一会话和预约
  → 商家接管、修改或处理异常
  → 买家 Web 看到最新业务结果
```

阶段完成后必须满足：

1. 买家可以在桌面浏览器和移动浏览器中新建、恢复和继续会话；
2. 买家可以基于当前门店真实发布知识完成咨询，并通过自然语言完成预约主路径；
3. 预约创建、确认、改约、取消和重复提交仍由既有预约领域服务决定，前端不直接写数据库；
4. 商家可以从后台找到关联会话和预约，查看上下文，接管会话，并将人工处理结果反馈给买家；
5. 刷新、短暂断线、服务失败、会话过期和重复操作都有明确且可恢复的界面状态；
6. 主路径有自动化端到端测试和一次人工演示证据，未验证的线上能力不被标记为完成。

Phase H 的产品边界只有一个渠道：独立 Web。桌面端和移动浏览器属于同一个 Web 平台，不开发小程序、美团、淘宝、微信或其他第三方入口。

### 0.1 执行与 Git 约束

- 所有 Phase H 代码、测试和文档提交必须在 `dev` 分支完成；开始每个任务前检查 `git branch --show-current` 与 `git status --short`。
- 提交格式固定为 `Phase H(类型)-标题`，标题不超过 15 个字；一个提交只包含一个独立事项，不提交未归属的工作区修改。
- 未经用户明确确认，不合并到 `main`、不推送远程、不宣称已部署；推送成功也不等于线上或鉴权验收完成。
- 发现现有未提交改动归属不清时，暂停相关提交并请用户裁定，不以“看起来属于 Phase H”作为默认依据。

## 1. Phase G 交接审查与当前基线

### 1.1 必须承接的稳定边界

Phase H 应直接使用以下现有边界，不得在页面层复制一套事实来源：

- 买家会话：`api/conversations.py`、`application/orchestrator.py`、会话/消息 Repository；
- 买家流式轮次：`POST /api/v1/conversations/{conversation_id}/turns`，SSE `protocol_version: v1`；
- 预约领域命令：`services/appointment_domain.py`、`api/appointments.py`；
- 知识检索与来源：`services/knowledge_service.py`、`GET /api/v1/conversations/{id}/sources`；
- 商家身份、门店上下文、RBAC、CSRF：`api/admin_auth.py`、`application/admin_permissions.py` 及 Phase G 管理 API；
- 商家会话工作台：`api/admin_conversations.py`、`services/admin_workbench.py`；
- 商家预约、客户、审计和指标接口：`api/admin_appointments.py`、`api/admin_customers.py`、`api/admin_audit.py`；
- 当前 Web 页面入口：`web/routes.py`、`web/templates/index.html`、`web/templates/admin_dashboard.html`。

### 1.2 当前基线事实与待核对事项

H0 必须重新核对以下事项后才能创建 H1 及后续功能提交：

- `dev` 当前存在未提交的代码、测试和路线图修改；必须逐项记录归属，不得把已有改动自动纳入 Phase H；
- 当前买家页面已经通过 `localStorage` 保存 `conversation_id`，但这不等于生产身份认证或跨设备恢复；
- `/chat/stream` 是兼容入口，Phase H 的新页面默认使用 `/api/v1/conversations` 和 `/turns`，不得继续扩大旧入口语义；
- `TurnRequest` 仍包含兼容性的 `user_id`，买家身份边界必须在 H0 明确，客户端字段不能被当作权限来源；
- Phase G 交接明确指出完整浏览器交互、人工回复闭环、复杂筛选分页和商业级性能尚未完成；这些是 H 的产品化重点，但不等于 H 承诺生产级可用；
- Fake LLM/Embedding 可以用于离线自动化和 HTTP 验收，但不能证明真实模型质量或线上部署行为。

交付物：

- **未提交改动表**：文件、变更摘要、初步证据、候选分类、用户裁定、是否纳入 H、后续动作。

验收：

- H0 前不创建买家端业务功能或人工回复接口提交；
- H0 先运行 `git status --short`、`git diff --name-only` 和必要的逐文件 diff，按“Phase H 遗留/Phase G 收尾/用户其他会话改动”三类建立归属表；
- 对归属不清的文件记录证据和候选分类，明确提交清单前请用户裁定；不得自行把 `api/knowledge*.py`、`services/knowledge_*.py` 等文件归入 Phase H；
- 用户裁定后，Phase H 只对白名单文件建立提交；暂不纳入的改动保持原样，另行记录，不通过清理或重置解决；
- 每个关键动作均能指向现有 API/应用服务/领域服务，不允许页面直接访问 Repository；
- 明确哪些事项是本地 Fake 验证、哪些事项需要浏览器人工验证、哪些事项仍属于 Phase I；
- 原有未提交改动得到逐项归属，未授权文件不被清理、覆盖或提交。

## 2. 范围与不纳入清单

### 2.1 纳入范围

1. 买家 Web 会话入口、会话恢复和核心聊天状态；
2. 咨询、知识来源、预约信息收集、确认结果和预约状态展示；
3. 重复提交、断线重试、会话过期、错误和转人工反馈；
4. 商家会话工作台、关联预约查看、人工接管和人工回复；
5. 商家修改/确认/取消/改约后的买家端状态刷新；
6. Web API 与 SSE 契约稳定化、请求关联标识和关键写操作幂等；
7. 桌面/移动响应式布局、键盘可用性和基础页面状态；
8. TestClient/API 契约、浏览器端到端和人工演示验收证据。

### 2.2 明确不做的事情

- 小程序、微信、美团、淘宝或其他第三方渠道；
- 通用 `ChannelAdapter`、跨平台消息模型、订单同步和客户身份合并；
- 生产级买家注册、实名、OAuth、短信登录或多因素认证；
- PII 脱敏、客户导出/删除、备份清理和数据保留制度；
- 多进程/多实例知识索引一致性和生产部署高可用；
- 真实模型语义质量、人工评测、成本监控和线上 SLO；
- 完整 CRM、营销自动化、支付、退款和外部通知系统；
- 为未来渠道预留未经真实协议证明的大量字段或兼容逻辑。

## 3. 任务拆分

### H0：基线、交接审查与 Web 契约锁定

任务：

- 审查 Phase G 收尾文档、自动化测试、HTTP 验收记录和未完成清单；
- 盘点买家端、商家端页面与 API 的现状，标出兼容入口、规范入口和待删除/待收敛入口；
- 固化会话、消息、预约、接管、人工回复、来源和错误状态的公开契约；
- 明确买家演示身份与商家服务端身份的边界，禁止将客户端 `user_id`、`role`、`store_id` 作为权限来源；
- 定义浏览器刷新、短断线、重试、重复提交、会话过期的状态转换和可恢复动作；
- 建立 H 阶段文件白名单、提交边界、验证矩阵和回滚策略。

交付物：`Phase-H-G0-基线与决策记录.md`、契约表、状态机、验收矩阵。  
验收：关键设计决策没有未决的安全或数据一致性问题进入 H1；已有修改没有被混入 H0 之外的提交。

### H1：买家 Web 会话与咨询体验

涉及范围：`web/routes.py`、`web/templates/index.html`、`api/conversations.py`、必要的会话应用服务和前端测试。

现状：规范会话创建、恢复和 SSE turns API 已存在，首页已有本地会话 ID 提示。  
缺口：公开契约尚未在 H0 形成版本化基线，页面刷新、断线、过期和双会话隔离尚未有完整浏览器证据。  
目标：在锁定的会话/SSE 契约上完成买家端可恢复体验，不让页面自行解释内部状态。

H1 前置门槛：H0 必须先锁定会话创建/读取、turns 请求响应、SSE 事件包、错误码、`client_request_id` 和会话归属约定；H1 不得在这些关键契约仍待定义时开工。

任务：

- 将新建会话、继续会话和恢复历史统一到规范会话 API；旧 `/chat/stream` 只保留兼容验证，不作为新页面主入口；
- 展示当前会话标识对应的消息历史、发送中状态、连接状态、失败原因和可执行重试；
- 保证回答中的知识来源、无依据拒答和内部错误使用不同的用户可见状态，不渲染 `[THOUGHT]`、`[SIGNAL]` 或内部异常细节；
- 处理会话不存在、归属不符、服务不可用和会话过期，不通过删除本地状态掩盖服务端错误；
- 明确“新建会话”与“继续当前会话”的交互，避免多个浏览器标签页误用同一演示会话；
- 使页面在刷新后从服务端恢复会话和最近消息，`localStorage` 只作为客户端导航提示，不作为权限或业务事实来源。

交付物：买家会话页面、状态处理、`tests/test_buyer_conversation_web.py` 或等价测试。  
验收：两个不同会话不会串线；刷新可恢复；空消息、失败和重试均有稳定行为；页面不泄漏隐藏推理或内部错误。

### H2：咨询到预约的买家主路径

涉及范围：`application/orchestrator.py`、预约 API/领域服务、知识来源接口、买家模板及相关测试；只在发现契约缺口时修改后端，不重写预约状态机。

现状：预约状态机、命令服务、可用性查询和知识来源接口已存在。  
缺口：买家端是否已接通服务目录、服务人员、可预约时间和预约结果展示，必须由 H0 逐项核对；当前不能把后端存在等同于买家闭环已存在。  
目标：复用现有领域服务和门店配置事实，补齐买家端呈现、确认、恢复和错误路径。

任务：

- 让买家能看到已收集的服务项目、服务人员、时间、时长和待补充字段；
- 在创建、确认、改约和取消前展示明确的确认动作，结果展示预约 ID、状态和关键时间信息；
- 查询并展示真实门店服务目录、服务人员和可预约时间；冲突时显示可理解的替代方案或转人工路径；
- 所有关键写入使用稳定请求关联标识和预约幂等键；浏览器刷新、重试和双击不得创建重复预约；
- 预约领域错误映射为稳定的用户可见状态，不能把失败响应渲染为成功卡片；
- 知识回答只使用已发布且有依据的门店事实，预约政策、价格和地址不由页面硬编码；
- 确认主路径中的数据由服务端持久化，页面重载后仍可查询当前预约和未完成动作。

交付物：预约过程卡片/状态展示、必要的 API 响应模型调整、`tests/test_buyer_booking_flow.py`、重复提交与冲突测试。  
验收：完成“咨询→获取门店事实→补齐预约信息→确认→生成预约”的主路径；失败不伪造成功；冲突和重复提交均可证明没有重复业务写入。

### H3：商家 Web 工作台与人工接管闭环

涉及范围：`api/admin_conversations.py`、`services/admin_workbench.py`、商家模板/静态资源、审计事件和后台测试。

现状：Phase G 已提供商家身份、RBAC、门店范围、会话控制和后台壳层。  
缺口：可操作的会话工作台、服务端人工回复动作和买家端回读是否完整，需以当前代码和 HTTP 测试逐项确认；不能仅凭后台页面可见宣称闭环。  
目标：在既有权限、接管状态和审计边界上补齐商家操作界面与人工回复闭环。

任务：

- 将后台壳层扩展为可用的会话工作台：列表、状态筛选、会话详情、预约关联、来源和异常/投诉标记；
- 增加服务端受权限和门店范围保护的人工回复动作，人工消息必须写入同一会话事实来源并产生审计/控制事件；
- 实现接管、人工回复、恢复 AI 的明确状态机；接管期间禁止 AI 自动继续处理同一会话，恢复后按规则重新允许 AI；
- 将买家请求的转人工状态与商家待处理队列关联起来；
- 商家确认、取消、改约或备注后，保证买家端可以通过刷新或约定的轮询/事件机制读取最新状态；
- 对无权限、跨门店会话、重复操作、已关闭会话和失效 CSRF 请求返回稳定错误，不依靠隐藏按钮保证安全。

交付物：商家工作台页面、人工回复 API/应用服务、`tests/test_admin_handoff_web.py`、HTTP 验收记录。  
验收：商家可以从会话列表进入详情、接管并回复；买家可看到人工结果；接管状态下不会出现 AI/人工双重回复；每个管理动作可追溯。

### H4：Web API、SSE 与幂等契约全局审计

涉及范围：`api/conversations.py`、`api/appointments.py`、`api/admin_*.py`、`application/events.py`、Pydantic 请求/响应模型和契约测试。

现状：H0 已锁定会话/SSE/预约写接口的关键契约基线；当前实现已有部分协议版本、关联字段和幂等/去重机制。  
缺口：需要跨接口审计字段命名、错误码、关联 ID、终止事件、重试边界和旧接口兼容性；只有发现明确缺口时才按变更控制补充，不在 H4 首次定义主契约。  
目标：验证 H1～H3 使用的契约在全局上仍一致、可追踪、可幂等，并收敛已发现的差异。

任务：

- 以 H0 契约基线为参照，审计会话、消息、预约动作、人工接管和人工回复的请求/响应模型、关联 ID、时间字段和公开错误码；仅对已确认缺口做最小补充；
- 审计普通 JSON 响应和 SSE 事件中的会话、轮次、预约、接管状态表达，避免前端依赖内部对象字段；
- 复核 SSE 的 `run_started`、唯一终止事件、序号单调性、断线边界和失败语义；
- 统一客户端请求去重与预约幂等的职责：前者防止轮次重复处理，后者防止预约命令重复写入；
- 确保 API 层只做协议、身份/门店校验和应用服务调用，不把预约或接管规则写入路由；
- 对规范接口建立契约测试，并记录旧兼容接口的保留条件，不在本阶段无证据删除消费者仍在使用的接口。

交付物：公开契约表、API/SSE 契约测试、错误码映射表、兼容接口迁移说明。  
验收：前端只依赖公开契约；重复请求和失败重试不会产生不可见副作用；SSE 每轮只有一个终止事件，隐藏推理不进入事件或页面。

### H5：响应式、可访问性与可恢复性

涉及范围：买家和商家 Web 模板、静态资源、页面路由和浏览器自动化。

现状：买家和商家已有 Jinja 页面入口，部分前端交互测试可复用。  
缺口：桌面/移动视口的核心路径、键盘操作、超时、重试、空状态和服务不可用状态尚未统一验收。  
目标：在不复制业务逻辑的前提下，为同一 Web 平台补齐可理解、可操作、可恢复的页面状态。

任务：

- 为桌面和移动浏览器提供同一套核心流程，不通过复制两套业务逻辑解决响应式问题；
- 补齐加载、空数据、无依据、失败、重试、无权限、服务不可用、会话失效和重新认证状态；
- 为消息输入、确认按钮、接管/恢复和预约关键操作提供键盘可用性、焦点反馈、语义标签和基础可读性；
- 为消息发送、Agent 处理和预约写入设置明确超时与安全重试策略，区分可重试和不可重试错误；
- 页面使用稳定路径和可识别的状态标识，便于 TestClient、Playwright 或人工演示定位；
- 不把浏览器缓存、DOM 状态或隐藏字段当作权限、门店或预约事实来源。

交付物：桌面/移动布局、无障碍检查记录、`tests/test_web_resilience.py` 或等价浏览器测试、截图/录屏证据。  
验收：桌面与移动浏览器均能完成主路径；刷新和短断线后可以继续；关键按钮和错误反馈可通过键盘与可见状态理解。

### H6：端到端验收、回归与交接

现状：Phase G 已有后台 HTTP 验收和全量测试记录。  
缺口：Phase H 尚缺买家咨询到预约、商家处理、人工回传和买家回读的跨角色浏览器证据。  
目标：验证完整 Web 闭环，并区分自动化、本地 HTTP、浏览器人工、真实模型和线上部署证据。

任务：

- 使用 TestClient 或实际本地服务端点完成登录后台、买家咨询、预约、商家查看、接管/回复和买家回读；
- 使用浏览器自动化完成至少一条桌面路径和一条移动视口路径；
- 注入知识检索失败、模型失败、预约冲突、重复提交、CSRF 失败、会话过期和人工接管等故障；
- 运行与改动直接相关的测试，再运行项目全量测试，分别记录通过、跳过、失败、警告和环境限制；
- 在 Fake 模式确认没有真实 LLM/Embedding 网络请求；若使用真实模型，只记录独立的待评测结果，不把其当作自动化质量门禁；
- 更新 `README.md`、`PROJECT_MEMORY.md` 和 Phase H 收尾/交接文档，明确本地、浏览器、线上和真实模型验证边界；
- 只提交 Phase H 白名单文件，不提交现有工作区中未归属的修改；提交前复核 `dev` 分支、`Phase H(类型)-标题` 格式和用户确认边界。

交付物：`tests/test_phase_h_acceptance.py`、端到端验收记录、桌面/移动证据、Phase H 收尾与 Phase I 交接文档。  
验收：下节 Done 清单全部满足；所有未完成生产能力仍标记为待验证或 Phase I，不以本地页面可见替代线上验收。

## 4. 推荐执行顺序与阶段门禁

执行顺序：

```text
H0 基线与契约
  → H1 前置契约门槛
  → H1 买家会话
  → H2 咨询到预约
  → H3 商家接管闭环
  → H4 契约与幂等收敛
  → H5 响应式与可恢复性
  → H6 端到端验收与交接
```

门禁：

1. H0 未完成前，不创建买家端业务功能提交；
2. H0 产出的会话/SSE/预约写接口契约基线未锁定前，不开始 H1 页面开发；
3. H1 未完成前，不把当前首页标记为“可恢复买家端”；
4. H2 未完成前，不把咨询或预约页面标记为业务闭环；
5. H3 未完成前，不宣称商家后台支持人工接管或人工回复；
6. H4 未完成前，不宣称 API 对刷新、重试和双击安全；
7. H5 未完成前，不宣称桌面/移动浏览器均可完成核心流程；
8. H6 全量回归、HTTP/浏览器证据和交接文档完成前，不标记 Phase H 完成；
9. 任何涉及生产身份、PII、备份、多进程、真实模型质量或第三方渠道的新增需求，必须另行拆分到 Phase I 或独立阶段。

## 6. 风险、回滚与边界

| 风险 | 影响 | 缓解与回滚 |
|---|---|---|
| 页面继续把 `localStorage` 当成身份或业务事实 | 高 | H0 固化身份边界；服务端重新读取会话和预约；错误时清理导航提示而不伪造状态 |
| 买家与商家使用不同事实来源 | 高 | H2/H3 统一调用现有领域服务和后台 API；端到端验收必须核对同一预约 ID/会话 ID |
| 重试导致重复预约或重复人工回复 | 高 | 区分 `client_request_id` 与预约 `idempotency_key`；故障注入验证重复请求结果 |
| 接管状态未阻断 AI | 高 | 服务端状态机和应用层检查优先于页面按钮；增加接管期间的并发/顺序测试 |
| SSE 断线后客户端重复执行写操作 | 高 | 轮次和命令分别去重；终止事件和服务端状态查询作为恢复依据，不以客户端已显示文本判断成功 |
| 页面扩张为多渠道平台 | 中 | H0 不纳入清单；没有真实第二渠道、官方接口和测试环境不提取适配框架 |
| 当前未提交修改被错误纳入 H | 高 | 保留 H0 文件归属表；提交前只按白名单 `git diff` 和 `git diff --check` |
| Fake 模式通过被误认为真实模型质量 | 中 | 所有报告单列 Fake/真实模型/人工评测边界；真实质量继续交接 Phase I |

回滚原则：

1. 页面功能优先通过独立模板/静态资源和小范围 API 适配提交，避免破坏现有规范 API；
2. 契约变更先增加兼容读取和测试，再删除旧消费者依赖；
3. 任何无法证明幂等或状态一致性的写操作，不上线到主路径，回退到只读/人工处理路径；
4. 不使用 `reset`、清理命令或覆盖操作处理已有工作区修改。
