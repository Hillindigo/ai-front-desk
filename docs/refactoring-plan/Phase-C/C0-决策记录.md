## 3. 决策清单

### D1：旧 busy 排班记录处置
- **决策**：一次性归档迁移——5 条 legacy busy 记录 `status` 改为 `'archived'`（保留记录供审计，不静默删除）。
- **依据**：无法映射为 Appointment（缺归属）；若保留 'busy' 会被新可用性查询误判为占用。
- **影响**：归档后新可用性查询不把它们当作占用；旧接口按 status 过滤 'busy' 的查询不再返回它们（演示库可接受）。
- **回滚**：归档前备份 SQL；`UPDATE technician_schedules SET status='busy' WHERE status='archived'` 可还原。
- **执行时机**：C3 开始时执行一次。

### D2：TechnicianSchedule 新语义
- **决策**：`TechnicianSchedule` 仅表示"服务人员工作时间/休息/不可用时间块"，不再承担预约记录职责；`appointment_id` 字段**保留但弃用**（新代码不写入，旧接口兼容响应仍可读）。
- **依据**：计划 3.4；删除字段会破坏 `api/technician.py` 的 ScheduleResponse 兼容结构。
- **回滚**：字段保留，无数据损失。

### D3：Appointment 模型与状态机
- **决策**：按计划 3.1/3.2 落地；状态集合 `draft / pending_confirmation / confirmed / cancelled / expired`；终态不可恢复；`expires_at` 用于 TTL。
- **活跃草稿约束**：同一 `conversation_id` 最多一个 `status IN (draft, pending_confirmation)`；新意图先归档旧草稿（cancelled/expired）。
- **TTL**：draft/pending_confirmation 过期时间默认 24 小时；清理任务标记 expired 并保留事件（可重复执行）。

### D4：时间区间与冲突规则
- **决策**：半开区间 `[start_time, end_time)`；冲突判定 `A.start < B.end AND A.end > B.start`；`end <= start` 拒绝；相邻不冲突；cancelled/expired 不参与；改约排除自身。

### D5：幂等范围
- **决策**：创建/确认必须支持 `idempotency_key`，数据库级唯一约束 `(user_id, idempotency_key)`；重复提交返回原预约；同键不同内容返回 `IDEMPOTENCY_CONFLICT`；取消/改约接受 `request_id`（可选，不强制唯一）。

### D6：SQLite 并发边界
- **决策**：确认/改约事务使用 `BEGIN IMMEDIATE`；WAL 已开启（Phase B SessionManager）；`busy_timeout=5000ms`；可重试锁冲突有限重试（3 次，间隔 100ms 递增）；不宣称跨进程一致性。
